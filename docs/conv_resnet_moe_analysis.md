# conv + ResNet + MoE 作为主干：理论分析

> **本文只做理论分析，没有跑任何代码验证。** 所有"实测"数字都来自本工程已有文档
> （`docs/dev_sacmoetb_2026_09.md`、`docs/dev_sacmoetb_architecture.md`、
> `docs/xiangqi_capacity.md`、`src/rl/convdqn.cpp` 的注释），
> 所有"估算"都标了算式，所有"推理"都标了等级。
> 分析对象：`SACAZMoETbAgent` 现在的 `SparseMoE<TransformerBlock<15,315>, E=4, TopK=1>`
> 主干（d_model = 1263，共享口径唯一参数 57,586,536，叶子估值 4.02 ms/模拟）。

---

## 0. 结论（先给答案，理由在后面）

| 组件 | 判断 | 一句话理由 |
|---|---|---|
| **conv** | **应该做，这是三个里收益最确定的** | 现在的 TB 专家**在结构上根本没有空间概念**：它把一个 1263 维向量当成无结构的词袋，用一次 `d_k×d_k` 的门控线性变换加工它。而象棋恰好是"局部模式 + 平移等变"最典型的场景。这一改是**修一个建模错误**，不是"换个更强的网"。 |
| **ResNet** | **应该做，而且是 conv 的必要条件** | 卷积的收益来自**堆层数**（3 层感知野 7×7，5 层 11×11 覆盖整个 9 列棋盘），而不是堆通道数。没有残差，5 层以上的梯度在这套"按张量归一到单位长度"的 RMSProp 下很难稳定。 |
| **MoE** | **暂时不要做，或者最后做，且必须换路由语义** | MoE 在本工程的分工是"参数量不按算力付费"，而 conv 之后**计算量成为瓶颈、参数量变得极便宜**（下面 §3 的预算）——它要解决的那个问题在 conv 之后基本消失了。同时它带来三个本工程最缺的东西的反面：样本效率、路由统计稳定性、批大小要求。 |
| **组合结论** | conv+ResNet 值得做；**MoE 应该等到 conv+ResNet 已经工作、且确实被容量卡住之后** | 而且届时的 MoE 不该按"学习到的门控"路由，应该按**局面阶段 / 棋盘区域**路由（§5）。 |

还有一个**顺带的重要发现**（§7）：对齐表示（19 平面 + 8100 动作）之所以在本工程实测
亏 200 Elo，原因是"策略头从 8,192 参数涨到 518,400"。**卷积头天然不需要那个稠密大矩阵**
——`conv 32ch → 1×1 → 90 路` 只要 2,970 个参数。也就是说，
**conv+ResNet 有可能把"对齐表示"从劣势翻成优势**，这是一个独立于主线的潜在红利。

## 1. 现在的主干到底在算什么：它是"无空间"的

### 1.1 状态编码本身是**有**空间的

`src/chessstate.h` / `src/sacazagent.h`：

```
CELLS = 90 = 10 行 × 9 列          ← 正好是标准二维棋盘张量 (C, 10, 9)
cell  = canonicalCell(x, y, color) = x*9 + y     （黑方视角 x → 9-x 镜像）
平面  = type*2 + (是己方?0:1)       ← 14 个棋子平面
STATE_DIM = 17 × 90 + 3 = 1263      ← 棋子区是连续的一段: 平面 strided 布局
```

也就是说，**输入的 token 是带二维坐标的**，`plane*90 + x*9 + y` 这个下标里，
格子就是格子，邻接关系就是 `±1 / ±9`。这是卷积最理想的输入形态，
`Conv2d` 甚至已经支持 `(inC, 10, 9)` 的张量形状（`conv2d()` 的 `x.shape` 就是 `(C,hi,wi)`）。

### 1.2 而 TB 专家把这份空间结构**扔掉**了

`TransformerBlock<15, 315>` 建在 `d_model = STATE_DIM` 上，它的"注意力"是：

```
x_norm1 (1263)                                  ← 一个扁平向量, 没有 token 维度
for i in 0..14:
    q_i = Wq_i · x_norm1     (84)
    k_i = Wk_i · x_norm1     (84)
    z_i = softmax(q_i · k_iᵀ / √84)   ← 这是个 84×84 的**系数矩阵**, 不是序列注意力
    head_i = z_i · v_i
a = concat(head_0..14) (1260)
out = Wo · a                                     ← 1263 × 1263
```

关键点：**输入是一个向量，不是一串 token，所以这里没有"位置"这个概念**。
`z_i` 是一个 `84×84` 的标量矩阵，它逐元素乘 `v_i`，等价于
"用一个 `d_k×d_k` 的可学习门控去门控 `v_i` 的各个维度"。整块的数学形式是

```
注意力路:  Wo · concat_i[ (z_i(x) ⊙ (Wv_i x)) ]      z_i(x) = softmax(二次型(x))
```

——它**没有空间归纳偏置，也没有任何跨位置交互**，因为根本不存在"位置"。
模型要靠**数据**从零学会"某个格子的某个子和它 ±1 / ±9 的邻居有什么关系"，
而这份关系在每个平面上、每个位置都要**独立学一遍**（没有权重共享）。
`Wo` 那 1263×1263 = 1,595,169 个权重是**全连接**的：`(planeA, cellA)` 与
`(planeB, cellB)` 之间的关系，每一个都要一个自己的参数。

这不是"这个网不够强"的问题，是**它被喂进去的信息形态与它的结构不匹配**：
输入带二维结构，结构里被抹掉了。这正好对应文档里那句实测结论
——`6.20 ms` 的前向里 FFN 只占 `0.11 ms`（1.8%），**代价几乎全在那一项
`~9·d_model²` 上**。钱花在"用 150 万参数重新发现自己能免费拿到的邻接关系"上。

## 2. conv 的理论依据：三条，按强度排序

### 2.1 平移等变与权重共享（最强的一条）

象棋在**绝大多数格子**上是平移不变的：一个"车在空线上"的模式、
"马被蹩腿"的模式、"兵过河"的模式，在整个棋盘上是**同一个模式**。
卷积把这件事写成结构：

```
一个 3×3×14→C 的卷积核 = 126C 个参数, 在 90 个格子上**共享**
一张全连接/注意力的同一件事 = O(90² × 14 × C) 量级的参数, 而且不共享
```

具体到本工程：`Wo` 一层是 **1.59 M** 参数，而
`Conv2d(14→32, k=3, pad=1)` 是 **4,032** 参数（14×32×9），
而且它作用于全部 90 个格子。**参数效率差约 400 倍**，而这 400 倍不是"压缩"，
是**同一个函数被正确地共享了**——它表达的是同一个东西。

这一点在本工程的语境下格外要紧：文档已经反复记录**"参数/数据比是本工程的头号瓶颈"**
（`docs/sac_regression_2026_09.md`：策略头参数量 63 倍 ⇒ 掉约 200 Elo；
`docs/xiangqi_capacity.md` 的结论是"容量买得到、棋力买不到"）。
卷积是唯一一种**"加表达能力但不加参数"**的改动。

### 2.2 深度换感知野：正确的那条 scaling 轴

棋盘只有 **10×9 = 90 格**，这是一个非常小的空间。于是：

```
3 层 3×3 (pad=1)  →  每个位置感知野 7×7
5 层 3×3 (pad=1)  →  感知野 11×11  ⊃ 整个 9 列棋盘（横向全通）
```

也就是说 **5 层卷积之后，棋盘上的任意两点之间已经只有一条 O(1) 的路径**——
不需要注意力，不需要全连接。对比现在：TB 专家的 FFN 只有 `1263→315→1263`
（一层隐层），而注意力那一路只有**一次** `Wo` 混合。**现在的深度不足以做棋盘级的推理，
但它花在宽度上的代价比深度大两个数量级。**

### 2.3 α/β 引擎与 NNUE 的旁证

象棋/国际象棋工程几十年的实际做法是 **小容量 + 深搜索**（`docs/xiangqi_capacity.md` §3
已经论证了这一点）。而 NNUE/AlphaZero 这一系的评估函数，其成功案例毫无例外地建立在
**卷积或等价的位置局部特征**之上——**没有一个是"把棋盘拍平成一个向量再上全连接/注意力"**。
本工程的 TB 专家主干，在这一点上是孤例。这不是"没人试过"，是**这条路在棋类上从未成功过**。

## 3. 但有一个硬约束：卷积的**计算**代价，不是参数代价

这是本节最重要的一条，也是决定"值不值得做"的地方。**卷积的参数极便宜、算力不便宜。**

把本工程实测的标尺拿来算（`src/rl/convdqn.cpp` 注释：
`ConvDQN` 的 rollout 每步约 160 次前向，那个朴素卷积实现约 **10 ns/MAC**；
注意这是**未优化**的实现——没有 im2col、没有 SIMD 展开）：
`tflearn` 那个经典的 ResNet-CIFAR 在 `118×118` 输入、每层 64 通道下
`3.8 M MAC` ⇒ 实测 **10 ms**（即 `2.6 ns/MAC`），参数量 ~10.6 M。

现在按本工程的真实尺寸算（`10×9`，输入 14 通道，一层 = `outC × 14 × 9 × 90 MAC`）：

```
每层 MAC = outC × 14 × 9 × 90 = outC × 11,340        (第一层, inC=14)
每层 MAC = outC × C  × 9 × 90 = outC × C × 810        (后续层, inC=C)

C=32, 3 层:  32×11,340 + 2×(32×32×810) =  363K + 1,659K ≈ 2.02 M MAC / 专家
C=32, 5 层:  363K + 4×829K               ≈ 3.68 M MAC / 专家
C=64, 5 层:  726K + 4×3,317K             ≈ 14.0 M MAC / 专家
```

换算成时间（用 `10 ns/MAC` 的**悲观**档，也就是本工程朴素的 `conv2d` 不加优化）：

| 方案 | MAC/专家 | 悲观 10ns | 乐观 2.5ns | 参数/专家（约） |
|---|---:|---:|---:|---:|
| C=32, 3 层 | 2.02 M | 20.2 ms | 5.1 ms | 33 K |
| **C=32, 5 层** | **3.68 M** | **36.8 ms** | **9.2 ms** | **52 K** |
| C=64, 5 层 | 14.0 M | 140 ms | 35 ms | 205 K |

而**现在的 TB 专家实测前向是 6.20 ms / 专家**（`dev_sacmoetb_2026_09.md` §1.3）。

对照着读，结论很清楚：

* **C=32 一档的卷积骨干，量级上与现在的 TB 专家相当**（乐观档更快，悲观档更慢），
  但**参数量小 100~200 倍**（52 K/专家 vs 7.17 M/专家）；
* **C=64 及以上直接出局**——单次叶子估值就跑不起；
* 加上 MoE（每模拟 2 次骨干前向：在线 + 目标）与 `E=4`，代价还要再乘上去。

也就是说：**"conv+ResNet+MoE" 在参数上几乎免费，但在算力上是实打实的开销，
而算力正是本工程唯一真正稀缺的资源**（`docs/xiangqi_capacity.md` §3.1：
参数量 ×10 ⇒ 模拟次数 ÷10，而模拟次数就是棋力）。
这是一个必须靠**实测**才能定的数字，不是能靠推理拍板的东西——
所以下面 §8 给的是一个"先测单层代价"的最小验证路径，而不是"照着做"。

> **一个能显著改变这张表的杠杆**：`E:\home\code\chess\src\rl\conv2d.hpp` 的
> `conv2d()` 是朴素的 7 重循环（它至少已经把 `posOf()` 的开销 hoist 出去了，
> 注释里记了这件事）。把它换成 im2col + `Tensor::MM` 的 GEMM
>（库里已经有 `ikkj/kikj/ikjk` 三种形状），`10 ns/MAC` 这一档很可能掉到 `1~2 ns/MAC`。
> 也就是说：**"先优化 conv2d"这件事本身，可能就是把 conv 骨干从"跑不起"变成"划得来"的那一步**，
> 而且它是一个独立、可单独验证、不影响任何既有 agent 数值的改动。

## 4. ResNet 为什么是 conv 的**必要条件**（而不是"顺手加的好东西"）

1. **感知野靠层数**（§2.2）。3 层只有 7×7，5 层才覆盖整盘。
   而"能不能堆 5 层"完全取决于残差连接——没有它，5 层卷积在
   本工程这套优化器下几乎必然退化。
2. **本工程的优化器有一个特殊性质，使残差更重要**：
   `Optimize::RMSProp` 的 `clipGrad` 做的是 `dw /= dw.norm2()`
   （`dev_sacmoetb_2026_09.md` §2.5 B5 实测记录），**每个张量的梯度被归一到单位长度**。
   于是：梯度的**大小信息被抹掉**，深层的小梯度不会"自然衰减"，
   但也**不会有任何机制把深层与浅层区分开**——每层都拿满步长往前走。
   在这种"恒步长" regime 里，恒等映射的残差路是**唯一**一个能让深度网络
   在训练早期就有一个"至少不比浅层差"的起点的结构。没有残差，
   第 5 层的初始随机投影会直接破坏前 4 层学到的东西。
3. **稀疏 MoE 与残差流天然兼容**（这一条只有在 MoE 版本里才有意义）：
   `SparseMoE::forward` 里 `o = Σ_{i∈S} gate_i · expert_i(x)`，而 `Σ gate_i = 1`
   （top-1 时 `=1`）。放进残差流里，未被选中的专家对残差流贡献**恰好为 0**，
   而不是"贡献一个随机初始化的噪声"。这是 top-k MoE 在残差网络里
   比在稠密堆叠里更稳的一个具体原因。

**但有一个本工程特有的坑，必须在设计里绕开**（这是本节最实用的一条）：

`src/rl/layer.h` 里的三个 `LayerNorm` 变体，**做的是对"整个张量"的均值/方差**：

```cpp
// LayerNorm<Fn, LN::Def>::forward
Tensor::MM::ikkj(op, w, x);
u = op.mean();                       // ← scalar: 整个张量的均值
float sigma = op.variance(u);        // ← scalar
gamma = 1.0/std::sqrt(sigma + 1e-9);
o[i] = Fn::f((op[i] - u)*gamma + b[i]);
```

把 `(C, 10, 9)` 张量喂给它，得到的是**全张量一个标量均值、一个标量方差**——
这会把空间信息抹平（而且它其实是"线性层 + 标量归一 + 激活"，
不是真正的 LayerNorm，`gamma` 甚至是 forward 里算出来的一个 scalar 缓存、
不是可学习的 per-channel 参数）。

**结论**：conv 残差块**不能直接用现有的 `LayerNorm`**。可选的三条路：
(a) 写一个 per-location / per-channel 的归一化（正确但要新代码 + 新数值契约）；
(b) `LN::Pre` 那支同样是全局标量统计，同样不行；
(c) **不用归一化**，靠"残差支路初始化到接近恒等"（把最后一层卷积的权重初始化缩小）
——在只有 5 层、且 `clipGrad` 已经把每层步长钳死的设定下，这是最省事且可辩护的选择。
另外 **BatchNorm 不能用**：本工程是"一条样本一次更新"（`batchSize=4`，
而且 MCTS 推理前向与训练前向共用同一批层对象，见 `resetBatchStats()` 那段注释），
running statistics 会被推理前向污染——这和 `SparseMoE` 的批统计遇到的是**同一个问题**。

## 5. MoE：为什么我建议**不要**和 conv 一起上

### 5.1 MoE 在本工程的分工，被 conv 取消了

`sparse_moe.hpp` 开头那段注释把 MoE 的卖点写得非常准确：

```
参数量  ~ E × (每个专家)
计算量  ~ k × (每个专家)      ← 与 E 无关
```

它成立的**前提**是"参数量是你缺的、算力是你有的"。而在 conv 之后这个前提反过来了：

| | 现在（TB 专家） | conv+ResNet（C=32, 5 层） |
|---|---:|---:|
| 参数/专家 | 7.17 M | ~52 K |
| MAC/专家 | — （前向 6.20 ms） | 3.68 M |
| **参数 : 算力比** | 偏"参数重" | **偏"算力重"** |

**一个 52 K 参数的 5 层卷积专家，本身就已经不占参数了。** 再套一个 E=4 的 MoE，
把参数从 52 K 变成 208 K（对一个 data 只有几千条的自对弈工程来说仍然是巨大的），
代价是：

1. **算力不降反升**：MoE 省的是"没被选中的专家的算力"，
   而 conv 的算力本来就集中在被共享的那几层上；
2. **路由统计在 `batchSize=4` 下是噪声**：`addAuxGradient()` 用的是**批内平均场近似**
   （注释里自己写明了"严格来说这不是精确的批梯度"）。批 4、每批还要和
   MCTS 的几十次推理性前向区分开（`resetBatchStats()` 就是在处理这件事），
   门控的 `f_i`（选中比例）在 `E=4, k=1` 下只能是 `{0, .25, .5, .75, 1}` 这几个值
   ——这是一个信噪比很低的监督信号。Switch Transformer 那一系要求 MoE 有效，
   前提是**大批**（几千 token/批），本工程是 4。
3. **样本效率变差**：`E=4, k=1` 下每个专家每条样本只见到 `1/4` 的数据，
   而"参数/数据比失衡"正是本工程已经用 200 Elo 买过的教训。

### 5.2 如果一定要用 MoE，路由语义必须换

现在（和标准 NLP MoE 一样）是**学习出来的门控**：`gate = softmax(Wg·x)`。
在 1263 维的扁平输入上，`Wg` 自己都不知道什么是有意义的分区，
所以它只能靠辅助损失硬掰成"大致均衡"（文档记录过坍缩到 `{0,29,0,0}` 的事故）。

而象棋有一个**免费的、语义明确的专家划分**，而且它恰好与"该用哪个专家"高度相关：

| 路由键（都是**零参数**的，从状态里直接算） | 为什么它是好的分区 |
|---|---|
| **局面阶段**：子力总数 / 总手数 | 开局（子多、空间紧）与残局（子少、通路多）的**最优表示确实不同**，这是象棋教科书级别的共识；`CTX_MATERIAL` / `CTX_TEMPO` 已经在状态里了（`chessstate.h`） |
| **棋盘区域**：己方半场 / 河界 / 对方半场 / 九宫 | 与"过河兵"、"九宫攻防"这些**规则性的**模式一一对应 |
| **是否被将 / 无吃子进度** | 将军局面与平稳局面的评估函数差别极大 |

这才是"专家特化"在棋类上真正能特化成的东西——**而不是让 `Wg` 在 1263 维里瞎找**。
`ISparseMoE` 接口是现成的（`addAuxGradient` / `usageSnapshot` / `resetBatchStats`），
换成"外部指定 top-1"的实现只需要加一个"按给定下标强制路由"的入口，
而且**辅助损失的整个问题都消失了**（硬分区不需要均衡损失）。

### 5.3 一个必须走对的设计约束：**专家里不要放空间层**

如果 MoE 的两个分支各自持有一套完整的卷积栈，那个"空间归纳偏置"就被
拆成了 `E` 份，每份只能看 `1/E` 的数据——**这正好抵消掉 §2.1 参数共享的全部好处**。

正确的切法是（这也是 ResNet + MoE 文献里的主流做法，通常叫 **shared trunk + sparse
pointwise experts**）：

```
共享的、每层都跑的：  所有 3×3 空间卷积（空间归纳偏置在这里，一份）
MoE 里稀疏的：        **只在 1×1（逐点）卷积上分专家** —— 空间结构已经被前面的
                      conv 编码完了，专家只需要对"已经空间化的表示"做不同的通道混合
```

这样：空间先验保留了，容量真的按专家数增长了，算力只在最便宜的那种层上乘以 `E`，
而且路由完全可以在**池化后的全局表示**上做（语义可控）。

## 6. 一个具体的候选结构（纯粹为了把上面的论证落到参数上）

```
输入:  14 个棋子平面 → reshape 成 (14, 10, 9)      ← 零成本的 reshape, 数据已经是这个布局
       + 坐标/区域平面: 行 ramp / 列 ramp / 河界 / 九宫 (共 4 个, 见下面的"必须注意")

骨干:  Conv(14→32, 3×3, pad=1) + Tanh                (4,032 参数, 0.36 M MAC)
       [残差块 × 4~5]  每块:  Conv(32→32,3×3) + Tanh + 残差
                                                (9,216 参数/块, 0.83 M MAC/块)
       Concat: 扁平化(32×90=2,880) ⊕ 3 个上下文标量
                                                ← 全局信息只在这里进 (见下)

头部:  Linear(2883 → 64)                             (184 K 参数)
       → 三个头各自 Linear(64 → 128)                 (8.2 K × 3)
```

量级：**骨干 ~52 K 参数、3.7 M MAC；在线+目标两份骨干、每模拟 2 次前向 ⇒ ~15 M MAC/模拟**。
即使在悲观档（10 ns/MAC）也在"跑得起但要测"的边界上；乐观档（2.5 ns/MAC）比现在还快。

### 6.1 四条必须一起做的配套（少一条就会静默变差）

1. **坐标/区域平面必须加。** 2D 卷积的平移等变在象棋上是**部分错误**的：
   **河界**（兵/象/士的走法在河两侧不同）、**九宫**（只有 3 列 × 3 行，
   将/士永远不出宫）、**兵的过河状态**、**象的塞眼**——这些是**绝对坐标依赖**的。
   最省的解法是加 2 个 ramp 平面（`row/9`、`col/8`）+ 2 个区域平面（河界、九宫），
   代价 4 个输入通道、0 个额外参数、`4×32×9 = 1,152` 个 MAC。
   **不加这两个 ramp，网络无法区分"同一条线上的两个不同位置"，
   这是一个确定的、可预测的性能损失。**（国际象棋引擎走的也是"绝对坐标特征"这条路。）
2. **全局信息要有入口。** 卷积只用 3×3 核，`material count`（子力总数）、
   `repetition`（重复次数）、`tempo` 这类**全盘量**在纯卷积里没有任何通路
   （除非堆到感知野覆盖全盘 + 有 pooling）。现在这 3 个上下文标量本来就在
   `STATE_DIM` 的尾部（`CTX_BASE = 1260..1262`），
   那就在**头之前**把它们 concat 进去，别指望卷积自己发现它们。
   ——顺带说明：这 3 个标量和 14 个平面**语义不同**，混在一起做卷积是没有意义的，
   现在它们只是被"一起丢进同一个大向量"。
3. **动作头必须空间化，否则前功尽弃。** 现在的头是 `Linear(64 → 128)`
   （128 槽哈希）。如果骨干是空间化的、头却把一个 `(32,10,9)` 拍平成 2,880 维再去乘
   一个稠密矩阵，那 184 K 参数里绝大部分花在**重新学"哪个格子对应哪一路输出"**上。
   更好的做法：`Conv(32→90, 1×1)` 让每个格子直接输出 90 个"走到哪"的 logits
   （对齐表示的 8100 动作），或者至少先 `1×1` 降到 8 通道再拍平。
   **这一条是"要不要顺手把表示换成对齐表示"这个悬案的解药**（见 §7）。
4. **权重文件与既有 agent 的隔离。** 层的类型序列变了 ⇒ 权重指纹变了 ⇒
   旧的 `weights/sacaz_shared_agent_*` 一律载不进来。
   本工程已经有一套成熟的隔离做法（一个骨干一个类、权重前缀独立、
   `test_sacaz` 里用 SFINAE 探针钉住"另一个类没被动"），**照抄它**：
   新建一个 `SACAZConvResNetAgent`，不碰 `SACAZMoETbAgent` / `SACAZAgent` / 两个还原版。

## 7. 顺带发现：conv 可能让"对齐表示"翻案（独立红利）

`docs/sac_regression_2026_09.md` / `sacazagent.h` 顶部记录的实测：

```
改前 1263 / 128 槽 :  72.5%  [61.9, 81.1]
对齐 1710 / 8100   :  45.0%  [34.6, 55.9]      ← 净亏约 200 Elo
机制: 策略头参数 8,192 → 518,400 (63 倍), 而瓶颈 h=64 不动 ⇒ 参数/数据比失衡
```

注意这个归因：**"对齐表示更差"的真正原因是"8100 路输出的稠密策略头"，
不是"1710 维状态"或"8100 路动作空间本身"**。

而卷积头让 8100 路输出**不需要**那个稠密大矩阵：

```
稠密口径:  h=64 → 8100      = 64 × 8100 + 8100     = 526,500 参数
卷积口径:  Conv(32→90, 1×1) = 32 × 90  + 90        =   2,970 参数
           在 90 个格子上共享"输出 90 个目标格"这一个映射
```

**参数减少 177 倍**，而它表达的是一个**更强的先验**（"从任意格子出发的走法分布"
在空间上是同构的）。同时，对齐表示的 5 个上下文平面在卷积下是**天然兼容**的
（`writeContext` 那一段就是"每平面铺 90 个相同的值"），
而改前表示的 3 个标量尾巴反而不兼容空间布局。

**所以 conv 这条线有一个额外的、值得单独设一个 A/B 的假设**：
`conv+ResNet + 对齐表示 + 卷积策略头` 有可能同时拿到
"状态/动作表示正确（无哈希碰撞、与 PPOMCTS 同构）"和"参数/数据比健康"。
这是一个**用现有实测数据可以先行预测、且理论上自洽**的方向。

## 8. 风险清单与"哪些是推理、哪些必须实测"

### 8.1 【推理】我比较有把握的

* 现在的 TB 专家没有空间归纳偏置、没有跨位置交互（这是读代码的**事实**，不是推理）；
* 3×3 卷积在象棋上比全连接/门控线性更参数有效（§2.1 的 400 倍算式）；
* 5 层 pad=1 卷积覆盖整个 9 列棋盘（算术事实）；
* 现有的 `LayerNorm` 是全局标量归一，直接用会抹平空间信息（读代码的事实）；
* BatchNorm 在本工程不可用（读代码的事实：推理与训练前向共用层对象）；
* 加坐标 ramp 平面是必要的（河界/九宫是绝对坐标依赖，规则事实）；
* 动作头必须一起空间化，否则空间骨干的收益会被头吃掉（结构推理）。

### 8.2 【必须实测】我没有把握的，而这恰恰是决定性的

| # | 问题 | 为什么必须测 | 最小测法 |
|---|---|---|---|
| 1 | **朴素 `conv2d()` 的真实 ns/MAC** | §3 那张表的全部结论都挂在这一个数上（差 4 倍就换结论） | 写一个小 bench：`Conv2d(32→32,3,3,pad=1)` 在 `(32,10,9)` 上做前向 + 反向，跑 1000 次取中位数。**不需要碰任何 agent** |
| 2 | **im2col 化之后能快多少** | 如果是 4 倍，整个方案从"跑不起"变"划得来" | 同上，两个实现对照 |
| 3 | conv 骨干的实际启动/收敛 | 参数少不等于学得好；`clipGrad` 的恒步长 regime 对卷积是否友好**未知** | 一条 `learnBatch` 的损失轨迹对照，跟 `test_sacaz` [12b] 那套协议同形 |
| 4 | 卷积 + 坐标平面能否真的学出河界/九宫 | 需要看第一层核的可视化或消融（去掉 ramp 平面后的差值） | 消融：有/无 ramp 平面 |
| 5 | MoE 在 `batchSize=4` 下是否还在坍缩 | 文档记录过 `{0,29,0,0}`；换成 conv 专家后路由分布**完全未知** | `usageSnapshot()` 已经在打印了，直接看 |
| 6 | **等时间对局** | 这是唯一真正要紧的判据。本工程已有口径：`bench_sacaz_vs_ab --budget=175`，A/B 三臂同种子同起步权重（`dev_sacmoetb_2026_09.md` §2.5 C7 给了完整实验设计，**直接套用**） | 按 C7 那张表跑 |

### 8.3 【明确的负面/风险】

* **深度换宽度的代价是延迟，本工程买延迟的能力很有限**：
  一次叶子估值现在是 4.02 ms，175 ms 的界面预算跑 ~43 次模拟
  （刚过分支数 ~39 的地板）。**任何让叶子估值变慢的改动，代价是"一次深挖都没有"**
  （`dev_sacmoetb_2026_09.md` §3.3 的结论：16 < 39 时 π 目标退化成"把先验前 16 名抹平"）。
  conv 骨干的延迟必须落进"还能维持 40 次模拟"的窗口里，这是硬指标。
* **`clipGrad` 是全工程最不可预期的变量**：它把每个张量的梯度归一到单位长度 ⇒
  **有效步长恒等于 `lr`，与梯度大小无关**。这意味着"换个参数化"（比如加残差、
  加归一化、加 MoE 门控）对训练轨迹的影响**不能靠"梯度更小/更大"来推理**——
  文档里那次 `[12b]` 断言不稳定（`冲过头再弹回来`）就是这个机制的直接后果。
  这也是我建议 §8.2 #3 必须实测的原因。
* **"加了 MoE 就更强"在本工程没有任何证据**（`docs/agents_design.md` 记录：
  TB 骨干至今没有棋力结论，`bench_moe` 的 A/B/C/D 等时对局**全是和棋**，
  连 A-vs-A 自对照也是）。把 conv+ResNet+MoE 一起上，等于**三个变量同时动**，
  即使棋力变了也归因不了。

## 9. 建议的推进顺序（每一步都可独立验证、都可单独回退）

```
第 0 步（先做，收益可能独立成立）
  给 conv2d.hpp 做 im2col + GEMM 优化, 并加一个 ns/MAC 的 bench 目标。
  这一步不碰任何 agent, 不影响任何既有数值, 而且它决定后面所有步骤是否可行。
  —— 注意: 现在 convdqn 的 rollout 也在吃这个朴素实现, 所以它有独立的收益。

第 1 步  (只验证 "conv 在棋上管不管用", 不带 MoE, 不带 ResNet)
  Conv(14+4→32,3) + Tanh → flatten ⊕ ctx → 头, 单层。
  目标不是变强, 是测出: 收敛轨迹、ns/MAC、以及"有没有明显崩"。
  对照臂: 同参数量的 MLP。

第 2 步  (加 ResNet 深度)
  叠到 4~5 个残差块, 消融坐标 ramp 平面。
  这一步回答"深度换感知野"这条论证是否落地。

第 3 步  (顺手把对齐表示 + 卷积策略头做进去, 单独 A/B)
  这是 §7 那条独立红利, 它和第 1/2 步的结论互不依赖, 可以并行。

第 4 步  (只在第 1~3 步跑通、且确实被容量卡住时)
  再考虑 MoE。而且按 §5.2 换成"局面阶段 / 棋盘区域"的硬路由,
  并且只对 1×1 逐点层分专家 (§5.3)。
  —— 如果第 1~3 步的结论是"conv 骨干已经够用、瓶颈在数据量",
      那么 MoE 就不应该做: 它加的是容量, 而缺的是样本效率。
```

最后一句总结：**"conv + ResNet" 是在修一个建模错误，值得做；
"MoE" 是在解决一个本工程当前并不缺的问题（容量），
而且它和你现在最缺的东西（样本效率、批大小、延迟预算）方向相反。
三个一起上，最大的风险不是效果差，是"变差之后归因不了"。**
