# dev-sacmoetb: TB 专家骨干的模型结构 / 收敛速度 / 棋力优化

分支 `dev-sacmoetb`（起点 `2e9c15e`）。这一轮只动 **SAC+AZ 的稀疏 MoE + TransformerBlock
专家** 那条路径（界面上的 `AGENT_SACAZ_MOE`），目标是用户口径里那三件事：**模型结构**、
**训练收敛速度**、**棋力效果**。

> **架构图单独一份**：[`dev_sacmoetb_architecture.md`](dev_sacmoetb_architecture.md) ——
> 8 张图（改动前/后的整网结构、MoE 与 TB 专家内部、头数降级的机制、一次叶子估值、
> 一个训练样本的梯度流、权重文件布局、一次决策的调用总览）。
> 下面这份文字是**为什么改**与**改完实测多少**，那份是**改成什么样**。

一句话结论：TB 专家这条路径上有**两个各自独立、都可实测的结构缺陷**，都在本轮修掉了；
合起来让 "同一台机器、同一个算法" 的**每样本训练代价降到 1/3.59、每次搜索模拟降到 1/5.0、
参数量降到 1/2.50**，而且 π / Q / V 的**数值逐位不变**（下面 §3.3 是逐位断言）。
棋力结论见 §6 —— **本轮没有做**棋力 A/B，理由写在那一节。

## 1. 缺陷一：TB 专家的头数被静默降级（请求 15 个头，实际只跑 3 个）

### 1.1 症状

`src/sacazagent.h` 里写着：

```cpp
static constexpr int MOE_TB_HEADS = 15;   /* d_model/15 = 84 维/头; 头越多越便宜 */
```

而 TB 专家真实的 `d_model` 是 `STATE_DIM`。**默认表示的 `STATE_DIM = 17 x 90 + 3 = 1263`**，
而

```
1263 = 3 x 421        (421 是素数)
```

`MultiHeadAttention` 老口径的构造规则是"从请求的头数**往下找第一个整除 d_model 的数**"：

```cpp
numHeads = NumHeads;                                        // 15
while (numHeads > 1 && (d_model % numHeads) != 0) --numHeads; // 15→14→…→3
```

在 1263 上找到的是 **3**。于是这个"15 个头的 TransformerBlock 专家"实际上是
**3 个头、`d_k = 421`** 的东西。

### 1.2 为什么没人发现

同一份代码、同一个类、同一个 `paramCount()`，**没有一个读数会变**：

| 检查项 | 降级时会不会报警 |
|---|---|
| 权重文件的结构指纹（层类型序列） | 不会（层类型没变） |
| `paramCount()` / 元素总数守卫 | 不会（它本来就只数**在用**的 head） |
| 权重文件写出的行数与内容 | 不会（写出的本来就是在用的那 3 个 head） |
| 参数量指纹 | 不会（见下表：差 0.158%） |
| 自检面板 | **原本一个字都没有** |

只有两个东西变了：**慢**，和**内存**。

`heads[NumHeads]` 是**定长数组**，15 个 `ScaledDotProduct` 对象全部被构造（每个都带
`wq/wk/wv`，`withGrad` 时还各带 `g/gv/gm` 三份副本），但只有 3 个参与前向 ——
**80% 的 qkv 张量是死的**。

这与 `docs/sac_regression_2026_09.md` 里那次 `TanhNorm<Sigmoid>` 回归是**同一类**失效：
同形状、同参数量的静默替换，面板上看不见。

### 1.3 实测（`.r1build/tbcost.cpp`，i5-10400F / MSVC 19.44 Release / AVX2）

| | 旧口径 `legacy` | 新口径 `honor` | 比值 |
|---|---|---|---|
| 请求头数 | 15 | 15 | |
| **实际参与前向的头数** | **3** | **15** | |
| `d_k` | 421 | 84 | |
| 注意力矩阵元素数 `Σ numHeads x d_k²` | 531,723 | 105,840 | **−80.1%** |
| 分配的 head 对象数 | 15（12 个是死的） | 15（0 个死） | |
| `paramCount()` | 7,182,996 | 7,171,629 | −0.158% |
| **单专家前向** | **19.06 ms** | **6.20 ms** | **3.07x** |
| **单专家前向 + 反向** | **71.86 ms** | **33.44 ms** | **2.15x** |
| 其中 MHA 单独 | 7.15 ms | 3.09 ms | 2.31x |
| 其中 FFN `1263→315→1263` | 0.11 ms | 0.11 ms | — |
| 其中尾部 `Tanh(1263→64) + Linear(64→128)` | 0.012 ms | 0.012 ms | — |

**代价基本全在注意力那 `d²/头数` 项上**：FFN 与尾部加起来占不到 2%，
而 `d_k = 421` 让 softmax 要算 531,723 个 `exp()`（实测每个约 23 ns）——
这就是 19 ms 里的 12 ms。

### 1.4 修法

`src/rl/attention.hpp` 给 `MultiHeadAttention` 加了第二个模板参数 `HonorHeads`：

* `HonorHeads = false`（默认）= **老口径**（找最大整除因子）。PPO / DQN+AB / `RL::SAC` /
  `SACAZLegacyAgent` 全部走这一支，**一位都没改**；
* `HonorHeads = true` = 按**请求的**头数切分：`d_k = d_model / NumHeads`（整除截断），
  允许 `numHeads * d_k < d_model`，尾部那几个坐标不进注意力拼接
  （它们在 `a` 里恒为 0，但仍然通过残差与 `Wo` 参与前向/反向）。

为什么不是"把 `d_model` 补到能整除"：`d_model` 由状态编码定死（1263），
`TransformerBlock` 是 `d_model -> d_model` 的层，不能改宽度；补宽还会改动 LayerNorm 的
统计量、并让状态编码与 PPO 的对齐口径一起漂。允许"头没铺满"是唯一不引入新层的修法。

另外把 `heads` 从**定长数组**改成 `std::vector`，只装**在用**的那些 —— 死内存归零。
这里有一条容易踩的坑：MHA 的构造函数里每个 `ScaledDotProduct` 都会从 `RL::Random`
抽 `wq/wk/wv` 的随机数，**少构造就等于把后面所有层的初始化随机数前移**，那会改掉每个
既有 agent 的初始权重。所以构造循环**仍然跑 `NumHeads` 次**（随机数消耗逐次相同），
没被用到的那些构造完就丢掉。

### 1.5 这条修法**没有**渗透到行为还原版

`SACAZLegacyAgent`（59e5233 行为还原版）**没有** `tbHonorHeads` 这个成员，它的
TB 专家仍然是旧口径（实测 `请求 15 / 实际 3 / 分配 3`，`test_sacaz` [17C] 钉住）。
它的逐手等价性因此一位都没变。唯一的例外是"死内存"那条**纯内存**修复对它也生效
（分配数 == 实际使用数），那一条不改任何数值。

## 2. 缺陷二：五张网各背一套骨干

### 2.1 症状

改动前 `SACAZAgent` 建 **5 张各自独立的网**：`actor` / `q1` / `q2` / `q1Target` /
`q2Target`，每张都背着一整套骨干。TB 专家骨干下这是 **28.8 M 参数/张，合计 144 M**。

代价有三块，都是"同一件事被算了三遍"：

* **搜索**：一次叶子估值 = `policySparse`（actor 骨干前向）+ `qValuesSparse`
  （q1 骨干 + q2 骨干前向）= **三次全网前向**，而三者的输入是同一个局面、差别只在
  最后那一层 `64 -> 128` 的线性头；
* **训练**：`learnBatch` 的每个样本要跑 **6 次全网前向**（`actor(s')`、两个目标网 `(s')`、
  `actor(s)`、`q1(s)`、`q2(s)`）+ **3 次全网反向**；
* **参数/数据比**：144 M 参数而自对弈数据以"千条"计。`docs/sac_regression_2026_09.md` 的
  结论（策略头参数量 63 倍就吃掉约 200 Elo）在这里被"五张网"放大了 5 倍。

### 2.2 修法：共享骨干 + 三个头（`TrunkMode::Shared`）

```
trunk        = [骨干层]                 (在线, 有梯度)
trunkTarget  = [骨干层]                 (目标, 无梯度)
actorHead / q1Head / q2Head             (三个只有输出层的头)
q1TargetHead / q2TargetHead
```

关键设计：**层对象只造一次，然后按 `shared_ptr` 组装成多张"视图"网**。
`actor` / `q1` / `q2` 在共享口径下仍然是**端到端可用的完整 `Net`**
（`actor.forward(state)` 就是"骨干 + 策略头"），所以 test / GUI / `selfCheckReport`
里所有 `agent.actor.xxx` 的用法一行都不用改；区别只在 agent 内部的**热路径**显式地
"骨干跑一次、三个头各跑一次"。

热路径上的三处要点（都在 `src/sacazagent.cpp` 里逐条注释了）：

1. **搜索**：新增 `sparseLeaf()` —— 一次骨干前向 + 三个头的合法列，语义与
   "`policySparse` + `qValuesSparse`"逐元素相同，但独立口径下那两次调用会把骨干跑三遍。
2. **训练**：目标侧 `π(s')` 取**在线**骨干（口径没变）、`V(s')` 取**目标**骨干
   （一份目标骨干被两个 Q 头共享 —— `softValueFrom` 用的就是 `min(Q1,Q2)`，完全等价）；
   反向时三个头各自的 `inputGrad`（`Net::backwardFrom` 把对输入的梯度存在那里）
   **相加**成 `dL/dh`，然后骨干**只反向一次**。
3. **优化器**：骨干只 `RMSProp` **一次**（`learningRateTrunk`）。照旧对
   `actor`/`q1`/`q2` 各调一次会把同一份骨干权重用同一个累积梯度更新三次 —— 等于学习率乘 3，
   一个完全静默、只让训练变坏的写法。同理 Polyak 也只同步一次。

### 2.3 实测（`.r1build/tbmatrix.cpp`，四个组合各一个独立进程，固定种子 20240913）

`d_model = 1263`，`batchSize=4`，16 条同分布经验，`learnFromSearch=false`：

| 结构 | 唯一参数量 | 构建 | `learnBatch(4)` | ms/样本 | `selectMove` ms/模拟 | 175 ms 预算的模拟数 |
|---|---|---|---|---|---|---|
| `separate + legacy`（**改动前**） | 144,131,280 | 4.4 s | 835.0 ms | 208.74 | 20.05 | ~8 |
| `separate + honor` | 143,903,940 | 1.8 s | 650.1 ms | 162.52 | 9.86 | ~17 |
| `shared + legacy` | 57,677,472 | 1.7 s | 302.1 ms | 75.54 | 7.81 | ~22 |
| **`shared + honor`（新默认）** | **57,586,536** | **0.6 s** | **232.7 ms** | **58.17** | **4.02** | **~43** |

两个因子各自贡献多少（相对改动前）：

| 因子 | `learnBatch` | `selectMove` | 参数量 |
|---|---|---|---|
| 只修头数口径（legacy→honor） | 1.28x | 2.03x | 1.00x |
| 只上共享骨干（separate→shared） | 2.76x | 2.57x | 2.50x |
| **两个一起（改动前 → 新默认）** | **3.59x** | **4.99x** | **2.50x** |

`learnBatch` 上头数口径只拿到 1.28x 而搜索侧拿到 2.03x，原因是**反向**：
`ScaledDotProduct::backward` 里有一项 `~6 x d_model²`（qkv 的权重梯度与对输入的梯度）
**与头数无关**，所以反向只从 71.86 降到 33.44 ms（2.15x），而前向是 3.07x。
一次 `learnBatch` 样本 = 6 前向 + 3 反向，所以它被那一项拖住。
**这也是下一轮最值得动的地方**（见 §7）。

### 2.4 等价性：共享**不改变算什么**，只改变**算几次**

`test_sacaz` [17B] 把独立口径的三份骨干与两份目标骨干**都设成同一份**
（这一步是实验设计的前提，不这么做比到的是"两份不同随机初始化"的差异），再把这份
"三个骨干相等"的独立网络逐层拷进共享口径，然后同权重同局面比对：

```
max|Δπ| = 0.000e+00      max|ΔQ1| = 0.000e+00     max|ΔQ2| = 0.000e+00
max|ΔQ1_target| = 0.000e+00
稀疏叶子路径: max|Δπ| = 0.000e+00, max|ΔQ1| = 0.000e+00, |ΔV_soft| = 0.000e+00
```

外加三条**只有共享口径才需要**的断言（少了它们，"共享"可能只是个不训练的摆设）：

| 断言 | 实测 |
|---|---|
| `actor`/`q1`/`q2` 三个视图确实与共享骨干**共享层对象**（不是陈旧副本） | 差 0.000e+00 |
| 共享骨干**真的收到了梯度**（一次 `learnBatch` 之后它的输出变了） | 最大变化 1.010 |
| 共享口径的**存/取往返**（4 文件格式：`_trunk` + 三个头） | 差 0.000e+00 |

## 2.5 三个问题：独立骨干为什么难训练 / 共享骨干为什么有效 / 共享的代价与副作用

这一节是**论证**，不是实测。为了防止把推理当成结论，每条都标了等级：

* **【实测】** 本机跑出来的数（命令都写在 §4）；
* **【本工程已记录的实测】** 之前几轮量过、有文档出处；
* **【推理】** 从上面两类事实推出来的判断，**本轮没有验证**；
* **【未测】** 明确的空白，§6 也列了一遍。

### (A) 独立骨干（5 张网各背一套）为什么难训练

**A1【实测】参数量与数据量的比例失控。** 5 张网 = **144,131,280** 参数，而回放池上限是
**4096 条**经验（`maxMemorySize`），自对弈数据以"千条"计。也就是**每条存下来的经验要
支撑约 35,000 个参数**。

这不是"参数多就一定差"，本工程有一条**同机制的实测**可以直接类推：
【本工程已记录的实测】`docs/sac_regression_2026_09.md` §4 —— 在**瓶颈宽度 h=64 不变**的
前提下把策略头从 128 槽换成 8100 路（头参数 8,192 → 518,400，63 倍），
对 MCTS 的得分率从 72.5% 掉到 45.0%（两个区间不重叠 ⇒ 净亏约 200 Elo），
而且逐项消融排除了奖励塑形、温度 α、抑制 critic、隐藏层不足四项。
结论是那句原话：**"参数/数据比失衡 —— 106 局自对弈的数据撑不起 8100 路输出的策略头"**。

共享骨干是这个论证在**骨干**上的同一份复制：把 3 份骨干压成 1 份，
参数从 143.9 M 降到 57.6 M（2.50x），而**没有删掉任何一个"本来在学东西"的参数**
（见 (C1)）。

**A2【实测 + 推理】5 张网里有 2 张（约 40% 的参数）几乎从不学习。**
`q1Target` / `q2Target` 是"只前向、无梯度"的网。它们由在线网 `copyTo` 初始化，
之后靠 Polyak 慢慢跟：

* 【本工程已记录的实测】`docs/sac_critic_diagnosis_2026_09.md` —— 一次 20 局的对弈
  （约 1300~2900 次 `learnBatch`）之后，**目标网的 |Q| 仍然是 0.072~0.097**，
  也就是随机初始化尺度（0.06~0.074）。原因是 `targetTau=1e-3` + 每 64 步同步一次，
  20 局只把目标网挪动 **2~4%**。
* 【推理】于是自举项 `V(s') = E_π[min_i Q_target_i] + αH` 里的**游戏信息接近于 0**，
  而它出现在**每一个** TD 目标里。独立口径下，这意味着 `q1Target`/`q2Target` 的
  **两份骨干**都是"随机初始化的、而且互不相同"的网 —— 训练里 40% 的参数量
  既不在学、又在参与目标计算。

  **必须说清楚：共享骨干并不能修好这一条。** 共享之后只剩 `trunkTarget` 一份，
  它的陈旧程度与改动前**完全一样**（还是 `tau=1e-3`/每 64 步）。
  共享只是把"两份互不相同的陈旧随机骨干"变成"一份"。这是**减少了一个混乱源**，
  不是**修好了目标网**。目标网那条缺陷有它自己的 A/B，而且实测"棋力差别不显著"
  （最好的一档 65.0% → 67.3%，Fisher **p = 0.43**），所以默认值没改。

**A3【推理】三份骨干各看 1/3 的梯度。** 独立口径下：

```
  actor 的骨干  ← 只吃策略损失的梯度
  q1 的骨干     ← 只吃 Q1 的 TD 梯度
  q2 的骨干     ← 只吃 Q2 的 TD 梯度
```

三份骨干的输入分布**完全相同**（同一个 `state`），却没有共享任何表示。
每一份都要**从零**学会"哪些格子上的什么子意味着什么"，而每一份拿到的更新次数
只有共享时的 1/3。**这不是"三倍容量"，是三份互相独立、各自欠拟合的表示。**

**A4【推理】双 critic 的去相关被"骨干不同"污染了。**
`min(Q1,Q2)` 想做的是"用一个下界估计压制过估计"，它成立的前提是两个 critic 的**误差**
可以互相抵消。而独立口径下 Q1 与 Q2 的差异**主要来自两份不同的随机骨干**，
不是来自"两次独立的估计"：谁的骨干恰好条件更好，谁就主导 `min`。
换句话说，**独立骨干让 `min` 变得更保守，但不见得更准**，而且这个保守程度
会随初始化的运气漂 —— 一个不可复现的语义。

**A5【本工程已记录的实测】独立骨干没有任何棋力证据。**
`docs/agents_design.md` / `issues_review.md` 写明：这个骨干**至今没有任何棋力结论**；
唯一一次直接对局（`bench_sacaz_vs_ab`，6 局，随机权重）是 **0 胜 6 负 0 和**，
而 n=6 支撑不了结论；`bench_moe` 的 A/B/C/D 等时对局**全是和棋**（连 A-vs-A 自对照也是）。
所以"独立骨干没效果"这句话的准确版本是：**没有证据表明它有效果，而它的代价是实测的**。

### (B) 共享骨干为什么有效

**B1【实测】搜索侧：一次叶子估值的骨干前向从 3 次降到 1 次。**
`20.05 → 4.02 ms/模拟`（4.99x）。同样 175 ms 的界面预算，模拟次数从 ~19 变成 ~43。

**B2【实测】训练侧：一个样本的骨干前向从 6 次降到 3 次、骨干反向从 3 次降到 1 次。**
`learnBatch(4)` 从 835.0 ms 降到 232.7 ms（3.59x，208.74 → 58.17 ms/样本）。

**B3【实测】参数量从 144,131,280 降到 57,586,536（2.50x），构建时间 4.4 s → 0.6 s。**

**B4【实测】它不改变"算什么"。** 把独立口径的三份骨干与两份目标骨干都设成同一份之后，
`max|Δπ| = max|ΔQ1| = max|ΔQ2| = max|ΔQ_target| = |ΔV_soft| = 0.000e+00`
（`test_sacaz` [17B]）。所以上面 B1~B3 的收益**不是**用精度换来的 ——
它只是把"同一件事被算了三遍"这件事去掉。

**B5【推理 + 一处重要的更正】"骨干收到 3 倍梯度信号"这句话在本工程里并不成立，
而正确的说法更有意思。**

直觉的说法是：共享之后骨干同时吃到策略 + Q1 + Q2 三份梯度，所以信号是 3 倍。
**但这在本工程不成立** —— `Net::RMSProp` 默认 `clipGrad=true`，而
`Optimize::RMSProp` 里的 `clipGrad` 做的是 `dw /= dw.norm2()`：**把每个权重张量的梯度
归一到单位长度**。于是：

* 梯度的**大小信息被抹掉**，每层的有效步长恒等于 `lr`（`sacazagent.cpp` 里那段
  注释与 `test_sacaz` [12a] 记的"冲过头再弹回来"都是这条的直接后果）；
* 把三份梯度**相加**再归一，与分别归一后各走一步，**步长一样、方向不同**。

所以共享真正改变的是**方向**：

```
  独立: 三份骨干各自沿"自己那条损失"的单位方向走        （3 次更新, 3 份表示）
  共享: 一份骨干沿"三条损失之和"的单位方向走 1 次         （1 次更新, 1 份表示）
```

【推理】这个方向有一个可辩护的好处与一个明确的风险：
* 好处：它天然是一个**多任务表示**，任何单条损失的批次噪声都被另外两条平均掉一部分，
  表示不会只服务于策略或只服务于价值；
* 风险：三条损失的方向可能**互相抵消或打架**（策略要的是"动作排序"，
  Q 要的是"局面绝对价值"），相加之后可能变成三者都不满意的折中 —— 见 (C1)。

**B6【推理】采样效率的实际来源是 B1/B2，不是"表示更好"。**
把话说到底：本轮**可复现、可测量**的收益全部来自"同样的时间能跑更多次模拟 / 更多次更新"。
"共享表示学得更好"这一条**本轮没有验证**，它是一个有待实验的假设（见 C7）。
这正是为什么 §6 单列了"共享骨干对学习质量的影响"作为未测项。

### (C) 共享骨干的缺点与副作用

按"会不会悄悄改变结果"排序。

**C1【未测】目标冲突（gradient interference）。** 这是共享结构最本质的代价。
策略损失要骨干输出"哪个动作好"，TD 损失要骨干输出"这个局面值多少"，
两者的最优表示不一定是同一个。独立口径下两份骨干各学各的、互不干扰；
共享之后只有一份表示，**任何一条损失变强都会挤占另外两条**。
本工程**没有任何实验能回答**这件事是好是坏，也**没有**做权重（例如给策略损失一个系数、
或给骨干一个更小的学习率）方面的探索。
可证伪的实验设计见 C7。

**C2【推理】双 critic 的去相关被削弱。** 共享之后 Q1 与 Q2 的差异**只剩最后一层
`64 → 128` 的线性头**（两个头仍然是独立初始化、独立梯度，所以它们确实不同，
但不再"独立地看世界"）。后果是 `min(Q1,Q2)` 作为下界估计的**偏差性质变了**：
从"两个独立估计取小"变成"同一个表示上两个线性读出取小"。这既可能**减少**
过估计（表示一致 → 两个头的误差更同向 → min 不那么保守但也更一致），
也可能**增加**过估计。方向未测。参考：SAC/TD3 的原始动机就是让两个 critic 尽量去相关。

**C3【实测口径改变】学习率不再是"每个目标一个"。**
改动前 `learningRateActor` 与 `learningRateCritic` 各自作用于自己那张网的骨干；
共享之后骨干只由 `learningRateTrunk` 控制（新增成员，默认取构造参数里的 `lr`，
与那两个相等）。今天两者本来就相等（都来自 `lr`），所以**数值上没变**；
但**"给策略骨干和 critic 骨干不同学习率"这个自由度没有了**。
三个头各自的学习率仍然独立。

**C4【实测：一个新的失败模式】视图与骨干共享层对象，这是一个**必须遵守的隐形契约**。**
共享口径下 `actor` / `q1` / `q2` 不再是"自己的网"，而是与 `trunk` / 各头
**指向同一批 `shared_ptr<iLayer>`** 的视图。由此产生两条新的纪律：

* **前向/反向的顺序**：骨干的缓存（`SparseMoE` 的 `gate`/`selected`/`expert_out`、
  `TransformerBlock` 的 `x_norm1/x_res1/x_norm2`、`Layer<Tanh>` 的 `o`）
  是**一份**。所以"用 `state` 前向一次，再用**另一个**局面反向"会静默用到错的缓存。
  `learnBatch` 里这一点是靠"反向之前最后一次在线骨干前向必须是同一个 `state`"保证的，
  已写进注释；
* **视图也能跑，只是慢**：`actor.forward(state)` 在共享口径下**仍然给出正确结果**
  （骨干 + 策略头），只是会把骨干重跑一遍。也就是说，**后人顺手写一句
  `agent.actor.forward(...)` 就能把 3 倍的收益悄悄吃掉，而没有任何报错**。
  这是与 `TanhNorm<Sigmoid>` 那次回归同一类的"静默"风险，所以 `test_sacaz` [17B]
  同时钉了两条：视图与 `trunk+head` 的输出**逐位相同**（证明共享是真的）、
  以及热路径走的是 `sparseLeaf`（`test_sacaz` [17B] 的代价断言会掉下来）。

**C5【实测：兼容性】权重文件从 3 个变成 4 个，前缀换名，旧权重载不进来。**
见 §3.2。副作用是 `AGENT_SACAZ_MOE` 这一支**要从头训练**
（`AGENT_SACAZ`、两支 59e5233 还原版不受影响）。

**C6【推理】路由统计的语义变了。** 负载均衡辅助损失 `L_aux = E·Σ f_i·P_i`
按"本批所有前向"统计门控。独立口径下有 **3 个独立的门控**（actor/q1/q2 各一个），
各自按自己被调用时看到的局面分布做均衡；共享之后只有 **1 个门控**，
它看到的是三条损失合起来的批。**理论上更一致**（同一个 `state` 的样本不再被算 3 次
而互相加权），但"均衡难度"和"专家特化能特化成什么"都变了。
`test_sacaz` [10]/[12c] 打的专家使用计数在改动前后都落在均衡区间
（`{51, 80, 72, 93}` / `{57, 84, 95, 60}`），但**没有做过 A/B**。

**C7【未测】共享之后棋力是升是降 —— 这是唯一真正要紧的未测项。**
`docs/agents_design.md:1837` 的口径是"20 局只能分辨大效应"。合理的实验设计是
**等时间配对**（这是唯一公平的比法，因为共享的全部收益就是"同样的时间能多跑"）：

```
  A 臂: --trunk=separate --tb-heads=legacy --budget=175   (约 2 次模拟/步)
  A'臂: --trunk=separate --tb-heads=honor  --budget=175   (约 2 次模拟/步)
  B 臂: --trunk=shared   --tb-heads=honor  --budget=175   (约 3 次模拟/步, 稳态 43 次)
```

三臂都从**同一颗种子 + 同一份起步权重**出发（`--warmup-games` 用同一参数），
跑 N 局互相对弈。判据：B 对 A 的胜率显著高于 50% ⇒ 共享的"更多模拟"压过了
C1/C2 的表示耦合代价；反之 ⇒ 表示耦合是真代价，那时应该改成
**"共享骨干 + 骨干单独一个更小的学习率"** 或 **"actor 单独一份骨干、双 critic 共享一份"**
（这是介于两者之间的第三个结构，本轮没有实现）。

**C8【推理】一个"看起来像缺点其实不是"的点：容量并没有真的丢 3 倍。**
3 份骨干从来不是一个 ensemble —— 它们在同一个数据流上、用同一套超参、为同一个目标训练，
而且其中两份（目标网）根本不训练。所以"参数量降 2.5 倍"损失的是
**冗余的、互相竞争同一批数据的**参数，不是"三个专家的容量"。
【推理】这也是为什么本轮的收益（3.59x / 4.99x）可以**不附带容量代价**地拿到。
但要讲清楚：**这条是论证，不是测量** —— §6 已把它列进"没有得出的结论"。

## 3. 界面上发生了什么

### 3.1 `AGENT_SACAZ_MOE` 改用共享骨干口径

`src/chessboard.cpp` 的 `createSACAZAgent` 只有一处构造点，这里显式传
`TrunkMode::Shared`。

### 3.2 权重前缀必须换（**旧权重载不进来**）

| | 文件 | 前缀 |
|---|---|---|
| 独立口径（`AGENT_SACAZ`、bench 的 `--trunk=separate`） | `_actor` / `_q1` / `_q2`（3 个） | `SACAZAgent::defaultWeightPrefix()` |
| **共享口径（`AGENT_SACAZ_MOE`）** | `_trunk` / `_actorhead` / `_q1head` / `_q2head`（4 个） | **`weights/sacaz_shared_agent`** |

两个口径的**文件个数与语义都不同**：独立口径的 `_q1` 里含着一整份骨干，共享口径的
`_q1head` 只是 `64 -> 128` 的一层。共用一个前缀的后果不是报错，而是"有人为了兼容补一条
回退"之后把独立口径的第一份骨干当成共享骨干、另外两份丢掉 —— **静默、不报错、训练继续**。

> **用户影响**：`weights/sacaz_moe_agent*` 那一组旧权重对 `AGENT_SACAZ_MOE` **失效**，
> 这一支要从头训练。`AGENT_SACAZ`（MLP 骨干）与两支 59e5233 还原版**不受影响**。

### 3.3 决策预算从 16 提到 40

`SACAZ_MOE_SIMS` 原来是 **16**，依据是"一次模拟 ~10.9 ms"。本轮之后稳态实测
**4.02 ms/模拟**，同样 175 ms 的预算从 ~19 次变成 ~43 次。取 **40**（约 161 ms/步），
留余量给"合法着法生成 / 棋盘试走回退"这些不随模拟数伸缩的开销。

为什么值得提：`16 < 分支数 (~39)` 意味着**一次深挖都没有**，π 目标退化成
"把自己先验前 16 名抹平"（`docs/issues_review.md` C16）。40 刚过分支数地板，
才开始有真正的深挖 —— 这是本轮的改动里**唯一一条直接指向棋力**的（见 §6）。

### 3.4 后台训练那一档也跟着调了

`BG_TRAIN_SACAZ_MOE_SIMS` 仍然是 64（训练要的是 π 目标质量，不是每步延迟），
但一轮 60 手的墙钟时间按上面的比例下降。

## 5. 兼容性与默认值

| 东西 | 默认 | 说明 |
|---|---|---|
| `tbHonorHeads` | **`true`** | 这是**修 bug**，不是开关：没有理由让"请求 15 个头却只跑 3 个"继续存在。传 `false` 只为 A/B 与复现历史读数 |
| `TrunkMode` | **`Separate`** | 构造函数默认值保持改动前的口径，所以所有既有调用点（test / bench / `AGENT_SACAZ`）**逐位不变**。只有 `AGENT_SACAZ_MOE` 与 `bench --trunk=shared` 显式开它 |

| `SACAZLegacyAgent` | 完全不动 | 没有 `tbHonorHeads`，也没有 `trunkMode`（`test_sacaz` [17C] 用 SFINAE 探针钉住） |

被**改掉**的两条旧断言（都在 `test_sacaz` [12]，理由与实测一起写在原处）：

1. `[12b]` 原来是"30 次 `learnBatch(4)` 之后 Q 比起点更靠近 0.5"。**这条一直是不稳定的**：
   `Net::RMSProp` 默认 `clipGrad=true` 把梯度张量归一到单位长度 ⇒ 每步位移恒等于 lr，
   目标又是常数 0.5 ⇒ 轨迹是"冲过头再弹回来"。隔离实验（旧口径 = 改动前的代码）实测轨迹
   `-0.057 → 2.880 → -2.706 → 1.411 → -0.556 → -0.745 → 0.376` ——
   终点落在哪基本是运气。现在改成：`(b)` 用 lr=3e-5 只断言"误差下降"（起点被 (a) 推到饱和区，
   定量没法做），新增 `(b2)` **在全新 agent 上**用同一协议做强阈值断言 ——
   实测 0.46028 → 0.01663（比值 0.036，阈值 0.35）；对齐表示 0.56483 → 0.00925（0.016）。
   **改后比改前更严**：旧版在 0.489 → 0.297 时也能通过。
2. `[12a]` 原来断言"改前表示下对照组（`azWeight=0` 且 `hasSearch=false`）的 π 轨迹均值
   > 均匀"。实测它**不稳**：同一份代码只换一组初始权重，比值就从 1.309 掉到 0.810
   （对照组只有"软 Q 项 + 熵项"，而软 Q 项的推力正比于 critic **当前**的 Q 间距，
   那个量在等步长更新下是振荡的）。改成**配对比较** `azMean > 3 x ctrlMean`
   （旧口径 7.0x、新口径 9.0x 都成立，且这正是本节标题想说的事），
   比值本身降级为**只打印不断言**的读数。

### 6.0.1 同一棵树上的回归对照（本轮真正想拿到的证据）

上面那棵 `2e9c15e` worktree 还有第二个用途：**证明本轮改动只动了 TB 骨干**。
同一条命令（`--games=2 --sims=16 --plies=30 --opening=4 --seed=20240901 --mcts-srand=12345`）
在两边各导一份走法序列，逐行 diff：

| 骨干 | `2e9c15e` vs 本轮 | 结论 |
|---|---|---|
| `mlp` | **61 行, 逐手相同** | 未受影响 |
| `moe-mlp`（稀疏 MoE + MLP 专家） | **61 行, 逐手相同** | 未受影响 |
| `tb`（稀疏 MoE + TB 专家） | 61 行, **不同**（有意） | 只动了这一个 |

`mlp` 与 `moe-mlp` 逐手相同这一条，是对本轮 `buildNet` 重构（拆成
`makeTrunkLayers` / `makeHeadLayer`）、`heads` 从定长数组改成 `vector`、
`ilayer.h` 加只读读数这三处改动的**回归保证**：它们没有改变任何既有骨干的初始化
随机数流、也没有改变任何数值。

### 6.1 棋力

* **棋力。** 本轮一次对局 A/B 都没跑。测到的只有"同一套算法、同样的时间预算下能跑多少次
  模拟"和"同样的模拟次数下算出的是不是同一件事"。`docs/agents_design.md` 与
  `issues_review.md` 已经写明：这个骨干**至今没有任何棋力结论**，此前唯一一次直接对局
  （`bench_sacaz_vs_ab`，6 局）是 0 胜 6 负 0 和，而 n=6 支撑不了任何结论。
  `docs/agents_design.md:1837` 的口径是"20 局只能分辨大效应"。
* **"更多模拟 ⇒ 更强"** 这条在本工程里只有间接证据（`docs/mcts_sims_scaling.md`），
  而且它自己也是概率性的。把 `SACAZ_MOE_SIMS` 从 16 提到 40 **是一个有依据的推断**，
  不是本轮测出来的事实。
* **共享骨干对学习质量的影响。** 共享之后骨干同时吃到策略与双 Q 三份梯度，
  这是 AlphaZero 的标准结构，但"三份梯度相加会不会互相干扰"在本工程里**没有测过**。
  本轮只证明了"同样的权重下前向逐位相同"，没证明"训练轨迹更好或更差"。
  §2.5 (C7) 给了可证伪的等时间配对实验设计。
* **头数口径对棋力的影响。** 15 个头（`d_k=84`）比 3 个头（`d_k=421`）**快 3 倍**，
  但"哪个容量/表达能力更好"没有测。`docs/agents_design.md` 里那条
  "头越多越便宜"只说了代价，没说效果。

---

## 7. 下一轮最值得做的

按"收益 ÷ 风险"排序：

1. **把反向里那一项 `~6 x d_model²` 降下来。** 现在一次样本 = 6 前向 + 3 反向，
   而后向的单价是前向的数倍且对头数不敏感（§2.3）。
   `ScaledDotProduct::backward` 里 `q/k/v` 三路的 `ikkj/kikj` 各走一遍，
   而且 `Tensor dz_hat(d_k,d_k)` / `Tensor dz(d_k,d_k)` / `dz.tr()` 每次都要分配 ——
   缓存它们、或把 `Wo` 与 qkv 的梯度合并成一次大 GEMM，都是明确的下一步。
2. **缓存 `LeafEval` 的中间量**（现在每次模拟还会重算一次 `getLegalActions` 与状态编码）。
3. **时间控制**：`docs/issues_review.md:2753` 记的"固定模拟次数，没有时间控制"这一条
   在共享骨干之后更突出 —— 稳态 4 ms/模拟 而冷启动那一步要几百 ms，
   固定次数在不同局面/不同缓存状态下能跑的次数差很多。
4. **收敛速度的对照组**：`replayEpochs` 默认 1、`targetTau=1e-3/每 64 步`这两个口径
   在 TB 骨干上从来没有做过配对实验（`docs/sac_critic_diagnosis_2026_09.md` 的全部结论
   都是非 TB 骨干上的）。现在每样本便宜了 3.6 倍，这类实验第一次变得可负担。
