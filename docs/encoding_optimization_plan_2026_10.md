## 0. 结论速览

### 0.1 19×90 作为序列 Transformer 的输入是否合理

| 判定项 | 结论 | 依据 |
|---|---|---|
| 形状：每格一个 token（T=90） | **合理**，且在"无 mask/padding"的实现约束下几乎是唯一解 | `docs/seq_transformer_design.md:462`（没有 mask）；变长的替子 token 方案见 §5.2 |
| 形状：token 的线性序 `t=9x+y` | **不是表达力问题**，只是先验问题 | `test_transformer [2a]` 关位置编码 ⇒ 置换等变（`\|dx\|=2.9e-6`） |
| 内容：14 个棋子平面 | **合理**，15 类（空 + 7×2）无 aliasing | `src/ppomcts_agent.h:93-103`、`src/ppomcts_agent.cpp:205-215` |
| 内容：第 15 维 `under_attack` | **纯冗余**：可由前 15 维推出 ⇒ 有效内容维 ≤ 18 | §C2 |
| 内容：第 16/17/18 维（全局标量铺满 90 格） | **有代价**：15.8% 的输入元素表达 3 个标量，且没有专属通路 | §C2 |
| **token 级内容** | **`~62/90` 个 token 是同一个"词"（只有 3 个全局常量）** | §C1 / §4.2 |
| 与全局编码布局的耦合 | **不合理（工程层面）**：`featDim = dIn/SeqLen`、平面顺序无自描述 | §C5 |
| 输出侧 | **语义不再对称**（输入的常量平面，输出非常量） | §C6 |
| 经验 | 同一份 19 平面，conv 排列棋力更好（60.0%，决胜局 17:5） | `docs/conv_resnet_agent_2026_10.md` §4.2 |

### 0.2 为什么 MLP 专家在棋力上占优（按证据强度排序）

| # | 原因 | 证据强度 |
|---|---|---|
| 1 | **容量/算力账被写反了**：MLP 的骨干参数是 seq 的 **4.85×**、每前向活跃参数 **4.90×**，而每模拟算力只有 1/10 | 【代码事实 + 算术】见 §1.5 |
| 2 | **等墙钟口径下 MLP 必然大胜**：模拟次数是本工程唯一测出过棋力的杠杆，而 seq 每模拟贵一个数量级 | 【实测·文档】§5.4 D1 |
| 3 | **权重状态可能完全不同**（seq 换 1d→2d 后旧权重被守卫拒绝；conv 是独立前缀） | 【代码事实】**可只读判定**，见 §5.4 D0 |
| 4 | **界面三支的 MoE 口径不同**（MLP 是 E8/t2，其余是 E4/t1）⇒ "骨干对比"混了两个变量 | 【代码事实】`src/rl/ppo.h:151-152, 209-210, 236-237` |
| 5 | 样本量不对称：慢的那两支在同一段会话里能下的局数少一个数量级 | 【推理】§5.4 D1 |
| 6 | 优化器口径对深链不利（`clipGrad` 被 RMSProp 的逐坐标归一抵消） | 【实测·文档】`docs/tb_expert_training_2026_10.md` |
| — | **⚠ 本仓库没有任何一条 MLP vs {seq, conv} 的棋力读数**；已有对局读数是 conv 61.0% decisive / seq 三支 53~57.5% inconclusive | 【文档事实】§C7 |

### 0.3 稀疏：三层量化，以及"该改哪一层"

| 层 | 量化 | 是否"太稀疏" | 该不该改 |
|---|---|---|---|
| 元素级 | 非广播的 1440 个 slot 里只有 **~55~75 个非零（4~5%）** | 是 | **不该**：乘零的算力只占 seq 的 1.1% / conv1 的 15%，绝对量 0.1~0.6 M MAC |
| **token 级** | **62/90 个 token = `[0×16, g,g,g]`** | **是（真病灶）** | **该**：见轴 A / 轴 B |
| 信息级 | 逐格词表只有 **30 种**（15 类 × 2 个被攻击位），且 1 维冗余 | 表达够、密度低 | **该**：提高"每格的信息密度"，不是减少通道 |

### 0.4 改进清单（优先级）

| 序 | 项 | 类别 | 作废权重范围 | 预期 |
|---|---|---|---|---|
| 1 | **C3 给 seq 补 4 个坐标/区域平面** | 专家内部（A 类） | 只 seq | 修"缺板面几何" |

| 4 | **轴 B 棋子 slot + 区域 token** 或 **C2 conv 干 + attention 尾** | 结构重构 | 那一支 | **同时解决稀疏与算力**（T 90→32 ⇒ 专家 MAC 0.31×） |

## 1. 事实基础（全部来自代码，逐条可复核）

### 1.1 19 个平面是什么

`src/ppomcts_agent.h:93-103` + `src/ppomcts_agent.cpp:205-253`：

| plane | 内容 | 逐格 / 全局 | 典型非零数 |
|---|---|---|---|
| 0..13 | 棋子 one-hot，`plane = type*2 + (是己方?0:1)`（7 类棋子 × 2 色） | 逐格 | 32（开局满子） |
| 14 | `PLANE_ATTACKED`：该格被**对方**攻击（含空格） | 逐格 | 数十 |
| 15 | `PLANE_UNDER_ATTACK`：该格上有**己方子**且被攻击 | 逐格 | 0~5 |
| 16 | `PLANE_HALFMOVE`：`halfMoveClock / 120` | **铺满 90 格** | 90（只有 1 个值） |
| 17 | `PLANE_REPEAT`：`min(重复次数,3)/3` | **铺满 90 格** | 90（只有 1 个值） |
| 18 | `PLANE_CHECK`：走子方是否被将军 | **铺满 90 格** | 90（只有 1 个值） |

### 1.2 数据流是纯转置；`featDim` 不是设计出来的

```
state[plane * 90 + cell]  (平面优先, cell = canonicalCell(x,y) = x*9 + y)
       │  gather:  Xs[t*featDim + f] = x[f*SeqLen + t]        (seq_transformer.hpp:1338-1345)
       ▼
T=90 个 token × featDim 维
featDim = dIn / SeqLen = 1710/90 = 19                        (seq_transformer.hpp:878)
       │  outProj 逐格: Linear(64 → 19)                       (seq_transformer.hpp:963)
       ▼
scatter:  o[f*SeqLen + t] = YS[t*featDim + f]                 (seq_transformer.hpp:1346-1353)
```

### 1.3 硬约束清单（改编码前必须知道）

| 约束 | 位置 | 不满足时 |
|---|---|---|
| `dIn % SeqLen == 0` | `seq_transformer.hpp:870-877` | **abort** |
| `POS_ROWS(10) × POS_COLS(9) == SeqLen` | `seq_transformer.hpp:856-863` | **abort**（⇒ `SeqLen` 不是自由序列长度，等价于"每格一个 token"写死） |
| `tokDim % Heads == 0` | `seq_transformer.hpp:879-884` | **abort** |
| `dff == 3 × tokDim` | `seq_transformer.hpp:886` | 硬编码 |
| 专家输入输出同维（MoE 契约） | `src/rl/sparse_moe.hpp` / `src/rl/expert.hpp` | 门控是 `d_model` 上的加权和 |
| **没有 mask / padding** | `docs/seq_transformer_design.md:462` | 变长序列不可用 |

### 1.4 谁在用这份编码（改一处牵动谁）

`ChessState` 是公共件（`src/chessstate.h:26-28`：各 agent 先选自己的平面布局，再调 `encodePiecePlanes` / `fillPlane`）：

| agent | 状态维数 | 规则/阶段平面数 |
|---|---|---|
| `PPOMCTSAgent`（4 支骨干共用） | **1710 = 19×90** | 3（halfmove / repeat / check） |
| `DQNABAgent` | 1710 = 19×90 | **5**（material / tempo / halfmove / repeat / check） |
| `SACAZAgent`（`ALIGNED_REPR`） | 1710 或 1263 = 17×90+3 | 3 |
| `EVABAgent` | 1530 = 17×90 | 3 |

⇒ **PPO 的 19 平面里没有 `material` / `tempo`，而 DQNAB 有**（`src/chessstate.h:51-56`；这 5 个标量的实现 `materialPhase` / `tempoPhase` 已经写在 `chessstate.h:89-109`）。

### 1.5 四支骨干的参数与算力对照（**结构性数字，与实现优化无关**）

| 支（界面口径） | 每专家 MAC/前向 | 每前向活跃参数 | actor 参数 | **骨干参数** | 每模拟墙钟（⚠ 见 §10） |
|---|---:|---:|---:|---:|---:|
| **MLP（E8/t2）** | 0.89 M | **449,628** | 2,448,204 | **1,812,200** | 0.14~0.24 ms |
| **seq（E4/t1）** | **9.67 M** | 91,731 | 1,009,772 | **373,768** | 3.71 ms（历史读数） |
| TB（E4/t1） | 13.3 M | — | 52,388,888 | — | 11.0 ms |
| conv（E4/t1） | 3.97 M | 44,275 | 819,948 | 183,944 | ≈2.5 ms（推算） |

算账过程（全部可手算复核）：

* `MlpExpert = 1710→64→64→1710` ⇒ 参数 `109,504 + 4,160 + 111,150 = 224,814`/专家；
  MAC `2·1710·64 + 2·64·64 + 2·64·1710 = 445,952`/专家；
  ×8 专家 + 门控 `8×1710+8 = 13,688` ⇒ 骨干 **1,812,200**；
  + 头 `Tanh 1710→64` = 109,504 与 `Softmax 64→8100` = 526,500，合计 636,004 ⇒ actor **2,448,204**
  （与 `docs/arena_sac_vs_ppo_report.md:169` 的读数逐位一致）。
* seq：`4 × 91,731 + 门控 6,844 = 373,768`；+ 636,004 ⇒ actor **1,009,772**
  （`docs/seq_transformer_design.md` §4.1）。
* conv：`6,656 + 4×9,248 + 627 = 44,275`/专家（`conv_resnet.hpp:59`）；
  `4×44,275 + 6,844 = 183,944`；+ 636,004 ⇒ actor **819,948**（`conv_resnet.hpp:61`）。

⇒ **结论（本文最重要的一条算术）**：
**MLP 的骨干参数是 seq 的 4.85×、每前向活跃参数是 4.90×，而每模拟算力只有 seq 的 1/10.8。**
seq 每参数摊 **105 个 MAC**，MLP 只摊 **2.0 个** —— "MLP 便宜所以是个小模型"这个直觉
在这两支之间**是反的**。
⚠ 这个错误方向甚至写进了注释：`src/chessboard.h:120-121` 写"MlpExpert…**容量小**
（2.15 M vs seq 的 1.0 M actor 参数）"，括号里的数字恰恰说明它更大；`ppo.h:348` 的
"容量小 ~21x"是拿 TB 的 38 M 比的。

### 1.6 搜索与编码的调用频率

`evaluateLeaf`（`src/ppomcts_agent.cpp:709-722`）：**每个模拟**先 `chess.getResult()`
（精确判和/判负，含三次重复与 60 回合），非终局才 `encodeState(...)` + `ppo.value(...)`。

⇒ **编码与"一趟 90 次 `isAttacked`"是每模拟一次的频率**，与一次网络前向同频 ——
这决定了 §5.1 里"多跑一趟攻击判定"的代价不能按"一次性开销"估。

## 2. 19×90 的合理之处（以及为什么它不是这个问题的答案）

### R1 每格一个 token 是"免 mask"约束下的唯一解
更自然的 token 化是"每个棋子一个 token"，但棋子数在 4~32 之间变长，需要 padding + mask，
而本工程**没有实现 mask**（`seq_transformer_design.md:462`）。定长 90 格不需要任何变长机制。
（这条在 §5.2 会被修正为"可以做到，但需要 key 侧加性偏置 + 重写 scatter"。）

### R2 特征完备、无 aliasing
14 个 one-hot 平面唯一确定"这一格是什么"（15 类），加 2 个 flag 补上攻防关系。
比旧 `TransformerBlock` 强得多：那支根本没有"格"的概念（`docs/conv_resnet_moe_analysis.md` §1.2）。

### R3 token 顺序不影响表达力，只影响先验
`test_transformer [2a]` 实测：关掉位置编码后对 token 置换等变（`|dx| = 2.9e-6`）。
所以 `t = 9x+y` 这个光栅序本身不限制模型能表示什么；它只对**依赖线性序的机制**有害
（RoPE / 1D 卷积 / 正弦编码）。`docs/seq_transformer_encoding_eval_2026_10.md` §9.3 已经把这件事
量化了：323 种盘内二维位移只折成 179 个 `Δt`、行尾回卷 9 处、`base=10000` 对 T=90 过长。
⇒ **形状没问题；"把 90 个 token 当一维序列配 1D 相对编码"才是问题**，而界面现役是 2d。

### R4 出口能自然回到 1710（MoE 契约）
逐格 `outProj 64→19` + `scatter` 保持"格 t 的输出是格 t 的函数"这个结构，
参数只有 1,235；替代方案 `Linear(5760→1710)` 要 **9.85 M**（在每专家 92 K 的预算下不该选）。

### R5 元素级稀疏本身不是缺陷
稠密浮点编码离散状态**天生过完备**（AlphaZero 的 119 平面同量级）。判断标准不能是
"零多不多"，只能是"零的代价 + 密度的后果"（见 §4）。

## 3. 19×90 的代价（逐条，标注证据强度）

### C1 【代码事实】token 级退化：62/90 个 token 只有全局常量
空且未被攻击的格：`[0×16, g,g,g]` —— **16 个零 + 3 个全局常量**，格特有的信息一个都没有。
开局 32 子 ⇒ **58 个这样的格**（中残局更多）。全部 90 个 token 共享同一个
`embed = Linear(19→64)`（`seq_transformer.hpp:889`）⇒ 这些 token 的表示方向相同，
只因位置嵌入相加而不同。

后果两条：
* **位置编码成为唯一的位置载体**。`docs/seq_transformer_encoding_eval_2026_10.md:531` 原话：
  "共享同一个 `Linear(19→64)` ⇒ 内容对'我在哪个格子'**完全盲**；**位置的唯一载体就是位置编码**"；
* **每行 softmax 在 ~60 个"同词不同位"的 key 上分摊质量**（`S = QKᵀ` 是 90×90，
  `seq_transformer.hpp:1558` 起的 `attnFwd`）。

### C2 【代码事实】3 个全局量铺满 90 格，且 1 维逐格冗余
* 平面 16/17/18 = **270/1710 = 15.8% 的输入元素**表达 3 个标量。经 `embed` 后它们对每个
  token 是**同一份加性向量**：在 Q/K 上是公共偏移（不产生选择性），只能经 V 与 FFN 起作用；
  经逐 token `SeqLayerNorm` 时表现为"逐 token 不同的缩放/平移"（**不会自动消失**）。
  仓库对 conv 支写过同一条：`docs/conv_resnet_moe_analysis.md:344-350`
  （"这 3 个标量和 14 个平面语义不同…全局信息要有入口"）。
* **平面 15 可由前 15 维推出**：它的写入条件是"该格有己方子 ∧ `attackedAbs[该格]`"
  （`src/ppomcts_agent.cpp:233-242`），而"该格有己方子"已由平面 0,2,…,12 的 one-hot 表达
  ⇒ `plane15 = plane14 ∧ (该格有己方子)`。**⇒ 19 维里 1 维纯冗余，有效内容维 ≤ 18。**

### C3 【推理】逐格可问的问题被人为限制在 2 个二值 flag 上
现在每格只表达"被对方攻击 / 我的子被攻击"，**没有攻击者身份、没有攻击/防御计数、没有"有根"**。
而"有根/无根""被几个子攻着"是象棋战术的核心。这条是 §5.1（轴 A）的全部动机。

### C4 【代码事实】seq 支完全没有板面几何平面
conv 支内部自己补了 4 个零参数通道（行 ramp / 列 ramp / 河界 / 九宫，
`conv_resnet.hpp:96-114`、`221`、`397-403`，且 `conv_resnet.hpp:27-29` 写明"不加是确定的性能损失"）；
seq 支只有 2D 位置嵌入，河界/九宫要靠 FFN 从 `(row+col)` 的非线性里自己合成
（同一类论证见 `seq_transformer_design.md` §9.4 的"中心交点要靠 FFN 非线性合成"）。

### C5 【代码事实】形状与全局编码布局耦合
* `featDim = dIn / SeqLen` ⇒ "19" 是**平面数的副产物**，不是设计出来的特征维。
  任何"加一个逐格通道"都要改共用编码口径，而它同时服务 5 支骨干 + 8 个 agent；
  SAC/DQN 的 `1263 = 17×90+3` 在 seq/conv 支上**直接 abort**（`src/rl/ppo.h:201-205`）。
* **平面顺序进入模型语义，但没有任何自描述**：权重文件只自描述位置编码模式
  （`POS2D` / `POSROPE`）。把棋子平面从 `type*2+isMine` 改成 `isMine*7+type`
  ⇒ `PLANES` 仍是 19、`STATE_DIM` 仍是 1710、参数量逐位相同 ⇒ **参数量守卫放行、
  权重被静默错位读入**。`docs/seq_transformer_design.md` §10.2 把"改编码布局会静默错位"
  列为不变量，但**没有守卫**（对比：位置编码模式有 `test_transformer [6g]` 的子进程退出码）。
* `POS_ROWS × POS_COLS == SeqLen` 是**无条件**断言（`seq_transformer.hpp:856`），
  于是"每平面一个 token（T=19）"这种 tokenization A/B 会被当场挡住。

### C6 【代码事实】输出侧语义不再对称
输入的平面 16/17/18 在各格严格相等，**输出的同样三个分量不再相等**（逐格 `outProj`）。
今天无害（只有 actor/critic 头读它），但若将来把专家输出当"状态"复用（残差、堆叠、回喂编码器），
这是一个静默的语义漂移点。
另外账要看清：内部残差流承载 `90×64 = 5760` 个数，出口只有 1710，头再压到 64
⇒ **两次有损投影连着走**。要提容量，瓶颈在"MoE `d→d` 契约 + 头结构"，不在"19"这个数。

### C7 【实测·文档】同一份 19 平面，conv 排列的棋力更好
`docs/conv_resnet_agent_2026_10.md` §4.1/§4.2（100 局 / 50 配对开局 / 等模拟预算 64 /
同一训练预算）：

| 臂 | 对 MCTS 得分率 | 判定 |
|---|---:|---|
| `conv`（19+4 通道） | **61.0%** | **decisive**（Wilson [51.2, 70.0]） |
| `seq` + 1d / 2d / rope | 57.5 / 57.0 / 53.0% | 全 inconclusive |
| （直接对局）`conv` vs `seq`+2d | **60.0%**（决胜局 **17:5**） | — |

⚠ 混杂因素：conv 多了 4 个几何通道、ResNet、参数与每模拟代价都不同；100 局、小训练预算。
**这不是干净的 tokenization A/B。**
⚠ 更重要的是：**仓库从来没有一条 MLP vs {seq, conv} 的棋力读数**
（`docs/tb_expert_training_2026_10.md:280` 原话："本轮一次对局都没跑…等模拟下 TB 与 MLP 谁强"）。

## 4. 稀疏的三层量化（回答"是否太稀疏"）

### 4.1 元素级：确实稀疏，但**几乎不花钱**
非广播平面共 `16 × 90 = 1440` 个 slot，实测非零 **~55~75（4~5%）**；
3 个广播平面另有 270 个"非零但重复"的值。信息量：逐格 15 类 ≈ 3.9 bit + 2 个 flag
⇒ 90 格 ≈ **~400 bit**，而输入是 `1710 float = 54,720 bit` ⇒ **过完备约 120×**。

与"乘零"相关的算力账：

| 支 | 与稀疏相关的项 | MAC | 占该支前向 | 其中"乘以零"的绝对量 |
|---|---|---:|---:|---:|
| seq | `embed` 19→64（`:889`） | 109,440 | **1.1%** | ~0.10 M |
| conv | `conv1` 23→32, 3×3（`conv_resnet.hpp:317`） | 596,160 | **15.0%** | **~0.57 M** |
| MLP | 第一层 1710→64 | 109,440/专家 | 24.5%/专家 | ~0.10 M |

对照非稀疏开销：seq 的注意力 **2.07 M**、FFN **4.42 M**；conv 的 4 个残差块 **3.32 M**。

⇒ **"压缩输入省算力"这条动机不成立**：把 19 平面压成 1 个 index（15 类查表）最多省掉
seq 的 1.1%。要省算力该动的是 T² 的注意力与 `dff = 192` 的 FFN。

### 4.2 token 级：**这才是真病灶**
`62/90` 个 token 的内容是 `[0×16, g,g,g]`（空 + 未被攻击）。它们**不是没用**
（位置 + 注意力仍能表达"这是关键格"），但它们**彼此之间只靠位置编码区分**，
于是：整个模型的位置知识压在位置编码上（C1），而界面选的 2d 位置向量落在
**秩 ≤ 18 的仿射子空间**里（`seq_transformer_encoding_eval_2026_10.md` §9.4）
⇒ 位置方向从 90 个自由向量压到 19 个。

### 4.3 信息级：词表 30 种，且有 1 维冗余
逐格"词"= 15 种棋子状态 × 2 个被攻击位 = **30 种**；第 15 维可由前 15 维推出（C2）。

### 4.4 结论
**"元素级稀疏要不要压缩"这个问题应该被放弃；要问的是"怎么让每个 token 携带更多信息"
（轴 A）、"要不要换 token 单位"（轴 B）、"能不能在进入注意力之前就稠密化"（轴 C）。**

### 5.1 轴 A：让空格 token 有内容（**不改 T、不改输出契约**）★ 清单第 1 优先

| # | 加什么 | 引擎 API（现成） | 新增代价 | 信息增量 |
|---|---|---|---|---|
| **A1** | `attacked_by_<type>`（7 平面） | `Chess::sample(them, steps)` 一趟伪合法走法，按终点聚合 | 一趟走法生成（**每模拟一次**，§1.6） | 从"被攻击"升级到"**被谁的炮/车指着**"——炮架/马腿的**后果**天然表达 |
| **A2** | `attack_count` / `defend_count`（各 1 平面，非二值） | 同上，累加计数 | ~0 | **每格信息密度翻倍**（1 bit → log2(N)） |
| **A3** | `defended`（1 平面） | `Chess::isAttacked(p, me)`（`src/chess.h:119`） | **+90 次 `isAttacked`**（现有攻击那一趟翻倍） | "有根/无根"是战术核心，现在**完全缺失** |
| **A4** | `reach_from` / `reach_to`（2 平面） | `getLegalActions` 已经算好的走法集合（**不是新算**） | 一趟聚合 | "哪些格能被走到"（AlphaZero 的 move-count 平面同源） |
| **A5** | 邻域池化平面（1~2 个，零参数） | 对 `attacked` 平面做一次 3×3 池化 | ~0 | 给 seq 支补**局部先验**（现在只有 conv 有 3×3） |

* **统一代价**：改 `PLANES/STATE_DIM` ⇒ **四支骨干权重全部作废**（§5.0 B 类）。
  ⇒ **要加就一次加全（B 类里 `A1+A2+A3+A4` 一起，19 → ~29 平面），只付一次重训。**
* **预期（诚实）**：仓库实测过"补全 Markov 状态修的是**建模错误**、不是棋力"
  （规则平面消融：0 胜 8 负 vs 0 胜 8 负，`docs/agent_dqnab_design.md:388-398`）。
  所以预期是**修一个有据可查的表示缺陷**，涨 Elo 要看读数。
* **最先要量的一步**：`encodeStateFor` 单独计时（对照 §1.5 的网络前向）。
  **没有这个数就不该动轴 A**（A1/A2/A3 都要多跑一趟 90 次判定或一趟走法生成）。

### 5.2 轴 B：换 token 单位（棋子 slot + 区域 token）—— **唯一同时解决稀疏与算力**

**关键发现**：降低 T 省的不只是"空 token"，而是**整条序列的算力**。
按 `seq_transformer_design.md` §5.1 的 MAC 分解，与 T 成正比的部分
（embed / QKV / Wo / FFN / outProj）= **7.59 M**，与 T² 成正比的部分（`S=QKᵀ`、`PV`）= **2.07 M**：

| T | T-正比项 | T²-项 | 专家 MAC 合计 | 相对现在 |
|---|---:|---:|---:|---:|
| 90（现在） | 7.59 M | 2.07 M | **9.67 M** | 1× |
| **32**（32 个棋子槽） | 2.70 M | 0.26 M | **2.96 M** | **0.31×（≈3.3× 更省）** |
| 41（32 子 + 9 区域） | 3.46 M | 0.43 M | 3.89 M | 0.40× |

引擎**恰好有 32 个棋子槽**（`for (int i = 0; i < 32; i++) { Stone *s = chess.stones[i];
if (s == nullptr || s->alive == false) continue; … }`，`src/ppomcts_agent.cpp:206-215`）
⇒ **T 可以固定为 32，不需要 padding**；被吃的子是"死槽"，用 **key 侧加性偏置**（softmax 之前
加 `-inf`）当软 mask 即可 —— **不需要实现完整的变长 mask**。

* **每 token 特征**（稠密）：类型 one-hot/索引（0..14）+ `alive` + `x/y` ramp + `attacked`
  + `defended` + 3 个全局 ≈ 20 维，**每一维都有内容**。
* **必须补回的信息**：**空格上的 `attacked`**（现在"被攻击的空格"是真实战术信息）。
  补法：加 K 个**区域 token**（9 个 3×3 块，或 10 行 + 9 列 = 19 个）汇总空格区域。T = 32 + K。
* **必须重做的**：
  1. **输出 scatter**：现在 `X[t][f] → o[f*90+t]` 假设"token t = 格 t"（`seq_transformer.hpp:1346-1353`）。
     棋子 token 要改成"该子的输出写回它所在的格"，区域 token 写回它的块 —— **本方向最大的工程量**
     （MoE 契约要求输出仍是 1710）。
  2. **断言**：`POS_ROWS × POS_COLS == SeqLen`（`:856`）要放宽。
  3. **位置信息**：token 不再绑定格子 ⇒ `x/y` 必须进特征。
* **反方（诚实）**：**稀疏从"空格"换成"死槽"** —— 残局 32 槽里可能只剩 4 个活子，
  算力按固定 T=32 付而信息按活子数收。但绝对代价（T=32 的常数）已经比 T=90 小 3.3 倍。
* **判据**：`test_transformer` 的三条不变量（`[2a]` 置换等变 / `[2b]` 常量 token / `[6]` 位置编码）
  **语义会变**，要重新设计断言，不是放宽容差。

### 5.3 轴 C：结构稠密化（**期望最稳**）

元素级稀疏只存在于最外层；过了第一层（embed / conv1）表示就是稠密的。
所以根治"稀疏"的正确姿势是"**第一层要能从稀疏模式学出稠密语义，且这个映射能被共享**"：

| # | 做法 | 状态 | 依据 |
|---|---|---|---|
| **C1** | **conv 支**（已有 3×3 + 权重共享） | 已实现 | 同一份 19 平面，conv 对 MCTS **61.0% decisive**（§C7）；参数账：`Wo` 1.59 M vs `Conv2d(14→32,k=3)` 4,032（`conv_resnet_moe_analysis.md` §2.1） |
| **C2** | **conv 干 + attention 尾（hybrid）** | 未接线 | 先用 1~2 层 3×3 把稀疏 one-hot 变成稠密特征图（**此时 token 已不稀疏**），再让 transformer 做全局关系（车/炮长程线、牵制）。这是"稀疏在进入注意力之前就被消掉"的唯一干净做法 |
| **C3** | **seq 支补 4 个坐标/区域平面**（行/列 ramp、河界、九宫） | **未做**（conv 内部已有） | 只作废 seq 一支、一天量级、**有成功先例**；修 C4 |

**C3 的具体落点**（专家内部，A 类）：
`seq_transformer.hpp:878`（`featDim` 扩到 `featDim + K`）· `:889`（`embed` 输入宽）·
`allocBuffers()`（`Xs/dXs` 是 `SeqLen × featDim`，要改）· `forward/backward` 的 `gather/scatter`
与 `dX` 的维度（**最容易静默错位的地方**）。

### 5.5 接口耦合的修法（不涨棋力，但减少静默事故）

| # | 修什么 | 落点 | 收益 |
|---|---|---|---|
| E1 | **平面顺序自描述**：权重文件写一行平面布局标记（如 `PLANES:piece14,att,und,hm,rep,chk` 的哈希），`read` 与当前布局不一致就 abort | `SeqPosEnc` 的模式标记行是现成范式（`seq_transformer_design.md` §9.4），照抄到 `Net` 级 | 挡掉"重排平面 ⇒ 参数量相同 ⇒ 静默错位" |
| E2 | **tokenizer 显式接口**：把"哪些平面属于逐格、哪些属于全局"写成显式契约，而不是 `featDim = dIn/SeqLen` 硬推 | `seq_transformer.hpp` / `conv_resnet.hpp` / 编码器 | 加/减全局平面不再打断"整平面"契约 |
| E3 | **全局量的专属通路**（轴 A 的配套项）：把 3 个广播平面从"铺满 90 格"换成 1 个 **global token**（T=90+1，只参与 attention/FFN、**不参与 `outProj`**）或头前拼接 | `seq_transformer.hpp:856`（断言放宽）、`:963`（`outProj` 只对 90 个格 token）、`:1346`（`scatter` 只读前 90 个） | 消掉 15.8% 的低密度输入；注意力 +2.2%（8100→8281）。transformers 在这件事上比 conv 便宜，本支偏偏没用上 |

### 5.6 明确不建议 / 性价比为负

| 方法 | 为什么不做 |
|---|---|
| **压缩输入**（19 平面 → 1 个 index） | 只省 seq 的 1.1%；表达力不变（one-hot × 共享线性 ≡ 查表 + bias）。唯一真收益是**统计效率**（空格能拿到不与其他类共享的向量）⇒ 属"顺手做"，不是优化项 |
| **稀疏 GEMV / 只在非零列上算** | 同上；且会破坏 `MM::` 内核的规整形状（仓库的 MM 契约不允许） |
| **删掉冗余的 `plane15`**（19→18） | 收益≈0，只在重构时顺手（但**减少一处隐式契约面**本身有价值） |
| **马腿/炮架专用平面** | 引擎没有现成 helper（只有 `isAttackedOne(target, stone)`）⇒ 要**新写一遍几何枚举** = 第二份规则实现，与引擎漂移是静默缺陷高发区；而其**后果**已被 `attacked` + A1 表达 |
| **历史棋局序列** | §6 |
| **多分辨率塔**（九宫特写 / 车炮切片） | 九宫/河界用 C3 的 2 个平面零参数就能表达；多塔直接乘算力 |

## 6. 与"历史棋局序列"的关系（为什么它不在清单里）

| 层 | 判定 | 依据 |
|---|---|---|
| **信息论** | 本工程**没有长将/长捉判负**（`src/chess.h:26`），和棋只有两条：三次重复（`Chess::isRepetition`，`src/chess.cpp:1029-1049`）+ 60 回合无吃子（`:1067`）。这两条的充分统计量分别是"当前局面的出现次数"与 `halfMoveClock`，**都已在编码里**（平面 17 / 16） | 【代码事实】 |
| **搜索** | 历史已被**精确**使用：每个模拟 `chess.getResult()`（`ppomcts_agent.cpp:711`），搜索的 `Chess` 对象带真实历史（`moveForward` 写 `history`）⇒ 树内重复检测精确 | 【代码事实】 |
| **三个真缺口** | ① 窗口内**其它**局面的出现次数（"走到 q 就判和"）② **手数上限**（界面 300 手判和，`src/chessboard.h:584`；而 PPO 的 19 平面里**没有 tempo**，DQNAB 有）③ **对手身份**（混合对手池每局抽签，最优动作依赖对手；仓库自己写过"要给网络对手特征…否则价值目标不可辨识"，`docs/mixed_opponent_training_2026_10.md:41`） | 【代码事实 + 推理】 |
| **代价** | T=90H 的注意力 ×H²（H=4 ⇒ 16×、H=8 ⇒ 64×）；每帧一个摘要 token（T=90+H）只 +18.6% @H=8 但每帧压成 64 维 | 【算术】 |
| **学习** | 同一局面对应 H 种输入 ⇒ 网络必须学"对历史不变"；而历史分布**随策略漂移**（位置分布近似平稳）⇒ 给一个应当是不动点的价值函数加了一个非平稳输入维度 | 【推理】 |
| **正确解法** | 三个真缺口都是 **O(1) 个标量**（重复压力、tempo、对手 one-hot），**不是 H×90 的 token** | — |
| **已有实测** | 规则平面消融：0 胜 8 负 vs 0 胜 8 负（`agent_dqnab_design.md:388-398`）⇒ "补全 Markov 状态修的是建模错误，不是棋力" | 【实测·文档】 |

**若真要做**，形态排序（代价/收益）：① O(1) 标量 → ② 上一步 `(from,to)` 两平面 →
③ 每帧一个摘要 token → ④ 帧内/帧间分解注意力 → ⑤ 全序列拼接（不可行）→ ⑥ GRU 递归。
⚠ 另有一条几何细节：规范视角按**该帧自己的走子方**镜像（`ChessState::canonicalCell`），
相邻两帧的坐标帧**互为镜像**，喂历史必须显式处理（统一到同一帧，或加"帧"这一根位置轴）。

| "当前可微调到 21~25 通道" | 19→23 就把 `conv1.W` 从 (32,171) 变 (32,207)，`conv_resnet.hpp:27-29` 原话"**两种口径的权重互不兼容**"；`docs/agents_design.md:3137` 同样记着"改状态编码"作废 `weights/` 那一批 | 加平面 = **一次全量重训**，不能"微调" |
| "19×90 是为 CNN 量身定做，**未来想上 Transformer** 就成了包袱" | 两支**都在**：界面默认已是 seq（`src/chessboard.cpp:481` `PPOMCTS_BACKBONE = SeqExperts`），conv 是第五支 | 不是规划问题，是现状问题 |

## 8. 推进顺序（每步可独立验证、可单独回退）

| 步 | 做什么 | 为什么这个顺序 |
|---|---|---|
| **0** | **只读**：查 `weights/` 四个前缀的存在/mtime/大小（D0）；顺带量一次 `encodeStateFor` 的耗时 | 第一刀决定"棋力差异归因"，第二步决定轴 A 的代价上限。**都不改代码** |
| **1** | **C3**：seq 补 4 个坐标/区域平面（A 类，只作废 seq） | 有 conv 先例、一天量级、可 A/B |
| **2** | **轴 A 一次做全**（A1+A2+A3+A4，19→~29 平面）+ E3（global token，若同一轮做） | 反正要全量重训一次，凑齐再训 |
| **3** | **D3 + D4**（E/topk 对齐 + 一次超参搜索） | 让"骨干对比"变成单一变量，补上"从未做超参搜索"的空缺 |
| **4** | **轴 B（棋子 slot + 区域 token）或 C2（conv 干 + attention 尾）** | "3× 级算力 + 稀疏"双收益，工作量最大，放在有前面读数之后 |
| 全程 | **E1/E2**（平面顺序自描述、tokenizer 显式接口） | 不涨棋力，但挡静默事故；可与任一步同轮做 |

## 11. 诚实边界

* **本文是分析与方案：本轮没有改任何 `src/` 代码，也没有跑任何实验。**
  所有"实测"数字都标了出处（文档名 + 章节/行），其余为算术或推理。
* **结构事实**（读代码可逐项复核）：§1 全部、§3 的 C1/C2/C4/C5/C6、§4 的三层量化、
  §5.2 的 T→32 算力表、§5.5 的耦合清单、§7 的 6 条修正。
* **推理/判断**（需要读数才能定论）：§0.2 的归因排序（尤其"权重状态"与"样本量"各占多少）、
  轴 A 的**收益大小**、轴 B 的**输出 scatter 设计**与 wall-clock 收益、C2 的工程可行性、
  §5.4 D1 的"等墙钟必然大胜"。
* **本文没有断言"19×90 导致了棋力损失"**。反方向的证据是：同一份 19 平面（conv 排列）
  已经拿到 61.0% decisive；"补全 Markov 状态"的消融给出 0 胜 8 负 vs 0 胜 8 负。
  所以轴上 A/B/C 的诚实预期是：**A 修表示缺陷、B 买算力（这条最实在）、C 买归纳偏置**；
  想涨棋力，第 0 步（判定权重状态）与 D 类（预算/口径）的收益概率更高。
* **本文没有写"哪一支应该替换哪一支"**：四支骨干是同一套算法/搜索/训练的不同骨干
  （`src/chessboard.h:116-129`），换骨干作废该支权重，属于一次独立的重训决策。
