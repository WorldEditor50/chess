## 0. 结论速览

### 0.1 Transformer 专家理论上会比 MLP 专家更好吗

| 层面 | 答案 |
|---|---|
| **通用理论** | **取决于专家的输入是不是序列**。单向量输入下，注意力没有"位置"可交互，Transformer 退化为"线性 + FFN + 多余开销"；序列输入下它才拿到 MLP 给不了的东西（两两关系、跨位置共享） |
| **本仓库的实际口径** | **两支都是 `d → d`（1710 → 1710）的专家，但 seq 支的输入本来就不是单向量**：它按格子切成 **T=90 个 token × 19 维**（`seq_transformer.hpp:1338-1345`）。所以"Transformer 退化成 MLP"这个常见论证**在这里不成立** —— 它是一支**真的序列模型** |
| **理论上界的来源** | ① 跨位置**权重共享**（同一套 QKV/FFN 用在 90 个格上）；② 一步到位的**全局感受野**（车/炮的长程线）；③ 相对/绝对位置的显式建模（`SeqPosEnc` 三模式）。MLP 三样都没有 |
| **理论上界的代价** | 算力 **9.67 M MAC**/专家（MLP 0.89 M，**10.8×**），而**每前向活跃参数只有 91,731**（MLP 449,628，**1/4.9**）⇒ **seq 每参数摊 105 个 MAC，MLP 只摊 2.0** |
| **结论** | **理论上"更好"只在"任务真的需要跨位置关系"且"算力/数据不吃紧"时成立。**本工程两条都紧张：模拟次数是唯一测出过棋力的杠杆、参数/数据比是头号瓶颈 ⇒ **当前口径下 MLP 的期望价值更高，但这不等于 seq 结构差**（见 §2.4 的三个可证伪条件） |

### 0.2 AlphaZero（围棋）的结构：本仓库已经有的 / 缺的

| AlphaZero 组件 | 本仓库对应 | 状态 |
|---|---|---|
| 17 平面输入（**8 帧历史 ×2** + 行棋方） | 19 平面（14 棋子 + 2 攻防 + 3 规则标量铺满），**无历史帧**；"轮到谁"由**规范视角镜像**表达 | ✅ 等价物齐备（**规则不同**，见 §3.2） |
| 首层 3×3 Conv 256 通道 + BN + ReLU | `ConvResNetExpert`：`Conv2d(23→32,3×3)+Tanh`，**刻意不用 BN**（理由见 `src/rl/conv_resnet.hpp:37-43` 与 `docs/conv_resnet_moe_analysis.md` §4） | ✅ 已有，规模小一档 |
| N 个残差块（围棋 19/39） | **4 块**（`PPO_CONV_BLOCKS = 4`，`src/rl/ppo.h:235`） | ✅ 可调大（90 格棋盘不需要 19~39） |
| **共享干 + policy / value 双头** | **PPO：两个独立骨干**（`src/rl/ppo.h:248-250、269-270`）；SAC 那两支已共享干 + 三头 | ⚠ **PPO 未搬**（§3.3） |
| policy 头：1×1 conv → 73 / 362 平面 | `Tanh(1710→64)` + `Softmax(64→8100)` = **526,500 参数** | ⚠ **空间化策略头未做**（§3.4） |
| value 头：1×1 conv → 256 FC → tanh | `Tanh(1710→64)` → `Linear(1)` | ✅ 同构 |
| MCTS 800 sims + PUCT + **visit 分布蒸馏** | `PPO_SIMS = 1600` + PUCT + visit 分布监督 | ✅ |
| Dirichlet 噪声 / 温度 | `pickUntriedByPrior` 的加噪 U 项（默认**关**，生产路径必须关） | ✅ |
| **不用 rollout**，叶子用一个网络前向出 (p, v) | `evaluateLeaf`：终局走 `getResult`，非终局走 `ppo.value` | ✅ 但**每次模拟 2 次骨干前向**（§5 ★Z1） |
| 置换表跨手复用子树 | `m_tt` + `treeReuse`（B-5，`src/ppomcts_agent.cpp:2049-2059`） | ✅ |
| **网络只被每个节点求一次** | ❌ **父节点策略每次展开都重算**（`src/ppomcts_agent.cpp:2024-2027` ⇒ 每次模拟 2 次骨干前向） | ⚠ **最大的一条可省算力**（§5 ★Z1，约 **1.4~1.6×**） |

### 0.3 rollout：本仓库的现状与判定

| 问题 | 判定 | 依据 |
|---|---|---|
| 本仓库有没有 rollout？ | **两套搜索各一套口径**：`AGENT_MCTS`（`MCTSAgent`）**用纯随机 rollout**（`simulateRandomPlay`，`maxPlies=200`，均匀随机合法着法）；`AGENT_PPOMCTS`（AlphaZero 式）**完全不用** | `src/mcts.cpp:218-260、287-339`；`src/ppomcts_agent.h:27-28` |
| 给 PPO+MCTS 加随机 rollout 值不值？ | **不值**（仓库自己的读数：随机 rollout 的叶子信号"同一个局面跑两次很可能得到相反的符号"，`src/mcts.cpp:427-428`；且本工程"模拟次数"是唯一杠杆，rollout 直接吃模拟预算） | 【实测·文档】 |
| 引导式 rollout（应将/吃子优先 + 有限深度）有没有用？ | **理论上是补丁，不是主路**；本仓库还有一条**反证据**：叶子没训准时"深搜是负收益"（256→1024 节点反而从 12.5% 掉到 0%，`docs/agent_dqnab_design.md` §7.4 第 1 条）——而 rollout 等价于加深搜索 | 【实测·文档】 |
| 该不该改现有的 `AGENT_MCTS`？ | **不该**：它同时是"混合对手池的 50%"与历史读数的**固定标尺**（`docs/mixed_opponent_training_2026_10.md`）⇒ 要就**新加一档** | 仓库既有纪律 |

## 1. 事实基础（读代码；本节的每一条都能复核）

### 1.1 本仓库的专家是 `d → d`，不是"CNN 瓶颈向量 → 头"
`RL::SparseMoE` 的门控是 `d_model` 上的加权和（`src/rl/expert.hpp` / `sparse_moe.hpp`），
所以**每个专家必须输入输出同维**：PPO 口径下是 **1710 → 1710**。
四支骨干的差别是"这 1710 维怎么被加工"，而不是"谁是骨干谁是头"：

```
PPO actorP : state(1710,1) -> SparseMoE(E, top-k, 专家) -> Tanh(1710->64) -> Softmax(64->8100)
PPO critic : state(1710,1) -> SparseMoE(E, top-k, 专家) -> Tanh(1710->64) -> Linear(64->1)
                             └── 两个网络各背一套完整专家 (ppo.h:248-250, 269-270)
```

### 1.2 "序列"到底在哪一支里

| 支 | 专家内部形态 | 有没有 token 轴 | 位置信息 |
|---|---|---|---|
| `MlpExpert` | `1710→64→64→1710`（3 层 FC） | ❌ 无 | 无 |
| `TbExperts`（`TransformerBlock`） | 单向量 `(d×1)` 上的"伪注意力"：`q·kᵀ` 是 `d_k×d_k` **外积**，`softmax` 还是**全局**归一 ⇒ 实测初始化时只占块输出方差 **5.6e-07**（`docs/tb_expert_training_2026_10.md` §9） | ❌ 无 | 无 |
| `SeqExperts` | **标准 Pre-LN 编码器**：T=90 token（每格一个）× featDim=19，逐行 softmax，可学位置编码 | ✅ | ✅ 位置编码（1d/2d/rope） |
| `ConvExperts` | `(19,10,9)` 图像 + 4 个坐标通道 → 3×3 卷积栈 + 残差 → 1×1 回 1710 | ❌（但有空间轴） | ✅ 结构自带（平移等变 + 4 个绝对坐标通道） |

⇒ **本工程的"Transformer 专家"不是一个套在向量上的 Transformer，而是一支真正的序列编码器。**
任何"向量输入下 Transformer 退化为 MLP"的论证**不适用于这一支**
（它适用于旧 `TransformerBlock`，而那正是 `docs/tb_expert_training_2026_10.md` §9 的结论，
也是 `SeqExperts` 被新写出来的原因）。

### 1.3 每次模拟的前向次数（这是 §5 ★Z1 的依据）

`src/ppomcts_agent.h:77-79` 记录的口径："现在每个模拟是 **1 次 actor（父节点策略） + 1 次 critic（叶子价值）**"。
代码路径（`src/ppomcts_agent.cpp`，`selectMove` 的每模拟循环）：

```
SELECT   : 从根按 PUCT 下到 nodeID
EXPANSION: encodeState(parentState)                    (:2024)
           pickUntriedByPrior(nodeID, parentState, …)  (:2025)
             └─ ppo.actionMasked(parentState, …)       (:464)   ← 一次完整骨干前向
           按先验挑 1 个未展开着法 → 创建子节点        (:2025-2047)
EVALUATE : evaluateLeaf(…)                             (:709-722)
             ├─ chess.getResult()  (终局: 将/困毙/三次重复/60 回合)
             └─ encodeState + ppo.value(...)                    ← 第二次完整骨干前向
```

**关键事实**：`pickUntriedByPrior` 每次都从 `parentState` **重算整个策略**
（`:464` 的 `ppo.actionMasked` 是"整骨干前向 + 只算合法列的头"，R1 优化省的是**头**的 8100 列，
不是骨干）。而一个节点有 ~40 个合法着法、被展开 ~40 次
⇒ **同一个父局面的骨干前向被重复算 ~40 次**（每次都只为挑一个孩子）。

### 1.4 PPO 与 SAC 的结构差异（同仓库内的先例）

| | PPO（`AGENT_PPOMCTS` 系） | SAC+AZ（`AGENT_SACAZ` 系） |
|---|---|---|
| 骨干 | **actor 与 critic 各背一套完整专家**（`ppo.h:269-270`） | **共享骨干 + 三头** |
| 实测 | — | 每样本训练代价 **1/3.59**、每模拟搜索代价 **1/5.0**、参数量 **1/2.50**，且 **π/Q/V 数值逐位不变**（`README.md:267`） |

## 2. Transformer 专家理论上会比 MLP 专家更好吗

### 2.1 通用判据（与具体项目无关）

Transformer 相对 MLP 的**结构性**优势只有三条，每条都要求特定条件：

| 优势 | 触发条件 | 单向量输入时是否成立 |
|---|---|---|
| 两两关系建模（注意力） | 输入是**长度 > 1 的序列** | ❌ 退化为"自我注意力 = 线性变换" |
| 跨位置**权重共享** | 序列元素同质（同一套权重适用所有位置） | ❌ 无位置 |
| 一步到位的**全局感受野** | 元素之间存在需要全局传播的依赖 | ❌ 无 |

反过来，MLP 作为**通用逼近器**对"固定维向量 → 输出"的映射没有表达力上限上的劣势；
它的劣势只在"缺归纳偏置 ⇒ 需要更多数据学同一件事"。
⇒ **所以问题从来不是"Transformer 与 MLP 谁更强"，而是"这份输入的语义是不是序列、
以及这个任务的数据/算力是否付得起归纳偏置的账"。**

### 2.2 本仓库的实际答案（与常见说法的**三处不同**）

| 常见说法 | 本仓库的实际情况 |
|---|---|
| "CNN 出瓶颈向量，专家吃单向量 ⇒ Transformer 退化为 MLP" | **seq 支的输入不是单向量**：T=90 × 19（§1.2）。它是真序列模型，退化论证不适用于它；那个论证适用于**旧 `TransformerBlock`**，而那份审计（§9）正是新支路的动机 |
| "Transformer 专家只是比 MLP 重，表达力更强 ⇒ 数据够了就更好" | **算力与容量的方向是反的**：seq 每专家 **9.67 M MAC / 91,731 参数**（每参数 **105 MAC**），MLP 每前向 **0.89 M MAC / 449,628 活跃参数**（每参数 **2.0**）。seq 花 **10.8×** 的算力，买到的是 **1/4.9** 的前向容量。在本工程"容量买得到、棋力买不到；模拟次数才是杠杆"的实测下（`docs/xiangqi_capacity.md`、`src/rl/ppo.h:272-273`），这个交换方向本身就是亏的 |
| "上 Transformer 会更慢所以更差"（把慢当成定论） | 慢是**实现与规模问题**，不是结构问题：P5（批量 FC）+ P6（注意力矩阵化）落地后，真专家 **forward 2.99 → 1.87 ms（1.60×）**、**fwd+bwd 8.81~9.12 → 5.51~5.61 ms（1.57~1.66×）**（`docs/tensor_optimization_plan.md` 的 P5/P6 行）。结构没变，代价掉了一半 |

### 2.3 已有读数的定位（它是什么、不是什么）

| 读数 | 值 | 能说明什么 |
|---|---|---|
| BC 四臂同协议（1000 局面 / 8 epoch） | 留出 CE：廉价专家 2.5460 / seq 2.6510 / TB 2.6600 / **MLP 2.6917**；留出 top-1：32.5 / 31.5 / 31.5 / **30.0%** | seq 的**表示质量**不差于 MLP（甚至略好） |
| 棋力对局 | conv 对 MCTS **61.0% decisive**；seq 三支 53~57.5% **inconclusive**；**没有 MLP 臂** | "哪个专家更强"**没有干净答案**；仓库自己写明"等模拟下 TB 与 MLP 谁强…本轮一次对局都没跑"（`docs/tb_expert_training_2026_10.md:280`） |
| 参数账 | §2.2 的表 | 差距的大头在**算力/容量交换**，不在表达力 |

### 2.4 理论上界：什么条件下 seq 应该赢（可证伪）

| 条件 | 为什么 | 本工程现状 |
|---|---|---|
| **任务真的依赖跨位置关系** | 注意力的全部价值在这里（车/炮的长程线、牵制、炮架/马腿的间接关系） | ⚠ **部分被手工特征替代**：`PLANE_ATTACKED` / `PLANE_UNDER_ATTACK` 已经把"攻击关系"喂进去了（2 个二值平面），注意力要做的是"被**谁**攻击"这一层 |
| **格与格的权重共享能真的被复用** | 否则 seq 只是"贵一点的 MLP" | ✅ 成立（同 `embed` 用在 90 格） |
| **算力不吃紧**（每模拟贵 10× 不伤棋力） | 模拟次数是唯一杠杆 | ❌ 不成立（3.71 ms vs 0.14~0.24 ms 的历史读数；⚠ 口径待重测） |
| **数据够**（序列模型要多得多的样本） | 归纳偏置的账要用数据付 | ❌ 不成立（BC 2000 局面 / 自对弈 40 局的小预算读数） |
| **位置信息真的能进模型** | seq 支的逐格内容对位置完全盲（共享 `Linear(19→64)`），位置编码是**唯一载体** | ⚠ 2d 位置向量落在秩 ≤ 18 的仿射子空间里（`docs/seq_transformer_encoding_eval_2026_10.md` §9.4） |

⇒ **预测（可证伪）**：把 `tokDim` 从 64 抬到 128/256、`Blocks` 2→3~4、BC 数据 ×5、
并且把"被谁攻击"的关系特征补上之后，seq 相对 MLP 的**表示质量优势会扩大**（BC 留出 CE / top-1
的差距变大）。**如果扩大不了，说明本工程的瓶颈确实不在表达力**（那才是"R5 型"的负面结论，
和"容量买不到棋力"一致）。
⚠ 反面提醒：抬容量在**随机初始化 + 小数据**下常常表现为"更差"（`agent_dqnab_design.md` §7.4
第 1 条：256→1024 节点反而 12.5%→0%）⇒ 这条预测必须**同时抬数据**，否则读数会被欠训练掩盖。

## 3. 从 AlphaZero（围棋）能搬什么

### 3.1 结论：本仓库已经是 AlphaZero 形状的，缺口只有三处

见 §0.2 的对照表。三处缺口按收益排序是：**① 每次模拟 2 次前向（§5 ★Z1）**、
**② actor/critic 两个独立骨干（§3.3）**、**③ 稠密策略头（§3.4）**。
其余组件（PUCT + visit 蒸馏 + 无 rollout + 置换表复用 + Dirichlet 噪声）**结构上已经对齐**。

### 3.2 **关键区别：AlphaZero 的历史帧是为"劫"服务的，本工程不需要**

* AlphaGo Zero 的 17 平面里，**8+8 帧历史**是为了让网络能表达**劫（ko）**这类
  **依赖历史的规则**（打劫禁止回到上一个局面；严格说 8 帧只是近似，真正的 superko
  要更长的历史或哈希集合）——**搜索侧用完整历史精确判定，网络侧给一个近似**。
* 本工程的规则集**不需要帧**：`src/chess.h:26` 明确"**本工程没有长将/长捉判负**"，
  和棋只有两条（三次重复 + 60 回合无吃子，`src/chess.cpp:1051-1074`），
  它们的**充分统计量是 2 个标量**（当前局面的出现次数 / `halfMoveClock`），
  而这两个标量**已经在 19 个平面里**（plane 16/17）；搜索侧还在每个模拟用
  `chess.getResult()` **精确**判定（`src/ppomcts_agent.cpp:710-711`）。
* ⇒ **"本工程没有历史帧"不是偷工减料，而是规则不同。** 反过来说：
  **哪一天要实现"长将/长捉判负"（它是序列规则："连续将军"由谁发起），
  历史就立刻变成必需** —— 要么加帧（AlphaZero 式），要么加一个"将军链"统计量。
  这件事必须与规则实现同一轮决定，否则 V(s) 会重新变成非 Markov。

### 3.3 可搬项 A：**共享干 + 双头**（有同仓库先例与实测）

* 现状：PPO 的 actor 与 critic **各背一套完整专家**（`src/rl/ppo.h:269-270`）。
* 先例：SAC+AZ 改成"共享骨干 + 三头"后实测 **每样本训练 1/3.59、每模拟搜索 1/5.0、参数 1/2.50**，
  且 **π/Q/V 数值逐位不变**（`README.md:267`）。
* **对 PPO 的诚实预期（与 SAC 不同）**：搜索里 actor 前向在**父节点**、critic 前向在**叶子**，
  是**两个不同局面** ⇒ **共享干不能把每次模拟的 2 次前向降到 1 次**（那是 §5 ★Z1 的活）。
  收益在：**参数量 ~1/2、峰值内存 ~1/2、每样本训练代价下降**（一次骨干反向替两次）。
* 代价：结构变更 ⇒ 该支权重作废；且 policy/value 的梯度会互相影响（需要一次 A/B，
  指标口径照 `docs/dev_sacmoetb_2026_09.md` 的三头拆分）。

### 3.4 可搬项 B：**空间化策略头**（`docs/conv_resnet_moe_analysis.md` §7 的假设）

AlphaZero 的策略头并不用"稠密大矩阵"，而是用卷积把动作**结构化**地输出。
本仓库现在是 `Tanh(1710→64)` + `Softmax(64→8100)` = **526,500 参数**，
而 `Conv2d(C→90, 1×1)`（每个出发格输出 90 个目标格的 logits）只要 **C×90 + 90**：

| 口径 | 参数 | 说明 |
|---|---:|---|
| 稠密 | `64×8100 + 8100 = 526,500` | 现状（`src/rl/ppo.h` 的头接线） |
| 卷积 | `32×90 + 90 = 2,970`（C=32） | **177× 更少**，且表达的是"从任意格出发的走法分布空间同构"这个**更强**的先验 |

* **为什么这条在本工程格外值得做**：`docs/sac_regression_2026_09.md` 实测"对齐表示（1710/8100）
  比改前表示净亏约 200 Elo"，**归因是"8100 路输出的稠密策略头参数涨 63 倍"**，不是 1710 维状态本身。
  也就是说：**策略头的参数/数据比就是本工程的头号瓶颈**，而空间化策略头正对着它。
* 工程落点：新增一个"空间化头"层类型 + 在 `RL::PPO` 里按骨干选择；需要骨干输出**空间结构**
  （conv 支天然有；seq 支的输出是平面优先的 1710，可按 `(19,10,9)` 重排）。
* 代价：**作废该支全部 PPO 权重**；且 8100 路动作索引是 `from*90 + to` 的双射
  （`src/chessstate.h:74-81`），1×1 conv 的输出恰好就是 `[from][to]` ⇒ **索引口径天然吻合**，
  这是这条方案能落地的前提。

### 3.5 可搬项 C：残差规模（AlphaZero 的缩放轴）
围棋用 19/39 个残差块 + 256 通道；本仓库 conv 支是 **32 通道 / 4 块**
（`PPO_CONV_CHANNELS=32`、`PPO_CONV_BLOCKS=4`，`src/rl/ppo.h:234-235`）。
棋盘只有 90 格（`docs/conv_resnet_moe_analysis.md` §2.2 论证"需要的是深度不是宽度"），
所以合理的下一档是 **通道 32→64、块 4→8**（只作废 conv 一支，属超参级改动）。

### 3.6 不能搬的
| AlphaZero 的做法 | 为什么不能搬 |
|---|---|
| **BatchNorm** | 本工程是"一条样本一次更新"，且 **MCTS 推理前向与训练前向共用同一批层对象** ⇒ running statistics 会被推理污染（`src/rl/conv_resnet.hpp:37-43`）；`LayerNorm` 同理（对整张量求标量均值/方差会把空间抹平） |
| 围棋式动作编码（19×19+1 / 国象 73 平面射线编码） | 本工程用 `from*90 + to` **双射 8100**（`src/chessstate.h:22-24` 记了哈希编码碰撞的旧事故）；改动作编码会同时作废策略头与全部权重，且与 `bench`/界面口径耦合 |
| 历史帧（见 §3.2） | 规则不同：本工程的两条判和规则由 2 个标量充分表达 |

## 4. rollout：本工程该怎么用

### 4.1 代码事实：两套搜索，两套叶子口径

| | `AGENT_MCTS`（`MCTSAgent`） | `AGENT_PPOMCTS`（`PPOMCTSAgent`） |
|---|---|---|
| 叶子 | **纯随机 rollout**：`simulateRandomPlay`（均匀随机合法着法，`maxPlies = 200`，`src/mcts.cpp:218-260`） | **网络价值**：`evaluateLeaf` → `ppo.value`（`src/ppomcts_agent.cpp:709-722`） |
| 本仓库对它的评价 | "它的叶子信号是 `simulateRandomPlay()` 的终局结果（±1/0）—— **方差极高：同一个局面跑两次随机对局很可能得到相反的符号**"（`src/mcts.cpp:427-428`） | "Instead of random rollouts, evaluation uses the PPO value head"（`src/ppomcts_agent.h:27-28`） |
| 用途 | **混合对手池的 50%**（`docs/mixed_opponent_training_2026_10.md`）+ arena 的标尺对手 | 界面现役（1600 模拟） |

### 4.2 为什么不该给 PPO+MCTS 加随机 rollout

1. **有直接的负面读数**：`src/mcts.cpp:427-428` 的"同局面两次 rollout 符号相反"——
   这是仓库自己量的。
2. **它吃的是唯一有效的杠杆**：每次模拟本来只花 1~2 次网络前向；插入一条长度 200 步的
   rollout（每步 `sample()` 生成合法着法 + 规则判定）**比一次网络前向贵一个数量级**。
   而"模拟次数是本工程唯一测出过棋力的杠杆"（`src/rl/ppo.h:272-273`）。
3. **规则复杂度**：炮架/马腿/将帅对脸/九宫 + 60 回合 + 三次重复；随机走法会大量进入
   循环与和棋，把 V 的目标压平（`src/rl/diag.h:792` 已经有"重复占比高 = 裁判问题"的读数）。
4. **AlphaZero 已经给出结论**：网络 P/V 取代随机 rollout 是这套方法的**核心**，不是可选项。

### 4.3 什么时候引导式 rollout 可能有正面作用（以及一条反证据）

| 场景 | 可能的收益 | 反证据 / 风险 |
|---|---|---|
| **冷启动**（V 还没训好） | 用"规则优先（应将 > 吃子 > 子力）走 1~3 步"的短 rollout 当叶子的补充信号，随训练衰减到 0 | 本仓库实测"**叶子没训准时加深搜索是负收益**"（256→1024 节点：12.5%→0%，`docs/agent_dqnab_design.md` §7.4 第 1 条）⇒ **rollout 只有在"规则比 V 更准"时才该用**，而这恰好只在极早期成立 |
| **残局/战术课程** | 杀棋深度（马炮/车兵杀法）是多步因果，短 rollout 或小深度穷举能给目标 | 与主训练解耦（单独生成课程数据），不要塞进主搜索 |
| **标尺/基线** | 传统 MCTS 作为"完全不随训练漂移"的对手是必要的 | **不要改现有 `AGENT_MCTS`**：它是混合池的 50% 与历史读数的固定点；要就**新增一档** `AGENT_MCTS_GUIDED` |
| **主搜索** | ❌ | 见 §4.2 |

### 4.4 如果真要做，接法与纪律（照仓库惯例）

1. **唯一入口**：任何叶子补强都必须走 `evaluateLeaf`（`src/ppomcts_agent.cpp:709-722`），
   并保留"**终局先 `getResult`**"这条（它修过"一步杀命中率 0/20"的真缺陷，见该处注释）。
2. **混合口径要显式**：`V_leaf = (1−w)·V_net + w·V_rollout`，`w` 按训练量衰减到 0，
   并且**要把 `w` 印进日志/自检面板**（"设了却没生效"是本工程记过多次的事故类型）。
3. **裁判口径与搜索一致**：rollout 里的终局判定必须用 `chess.getResult()`（不能自写判定），
   否则等于让 rollout 学另一个游戏。
4. **新档位而不是改旧档位**（`AGENT_MCTS` 不动），并用 `test_mixed_opponents` 的直方图断言
   钉住"池子里抽到的还是原来那一档"。

### 5.1 ★Z1 的细节（值得单独写清，因为它是"免费"的一条）

> **[2026-10-14 已实现]** 落地形态与实测读数如下（本节其余部分是当初的推导，保留作口径依据）。
>
> **代码**
> * `AZNode` 新增 `priorActionIndices` / `priorValues` / `priorCached`
>   （`src/ppomcts_agent.h`）—— 存的是该节点**完整合法集**上的稀疏策略前向结果；
> * `pickUntriedByPrior`（`src/ppomcts_agent.cpp`）改成"未命中才算一次、命中就按
>   **动作下标**查表"；命中时 `legalIdx` 的顺序与 untried 不再对齐，所以选择逻辑从
>   "按下标取"改成"按动作下标查"（对两条路径给出同一批数值）；
> * 开关 `azPriorCache`（默认 **true**）+ `setAzPriorCache()` + 命中/未命中计数器
>   + `resetAzPriorCacheStats()`；自检面板新增一行读数与判读；
> * CLI：`train_ppo --no-az-cache`（`test/train_ppo_main.cpp`）。
>
> **为什么可以缓存（等价性论证）**
> 1. 节点的局面与它的合法着法集在**创建时**就固定了；
> 2. 先验是"局面 + 完整合法集"的确定性函数 —— 稀疏 softmax 的归一化分母**正是这个集合**；
> 3. 集合不变式：`untried ∪ 已展开孩子的 parentAction` **恒等于**完整合法集
>    （三处调用点都是"挑走一个 → erase → 建孩子"的成对写法，已逐点核对）
>    ⇒ 首次算出的那一份与后续每次重算**逐位相同**。
>
> **实测（`train_ppo --backbone=mlp --games=3 --sims=16 --moves=30 --seed=20240901`，
> 缓存开/关两臂，同一二进制）**
>
> | 读数 | 缓存关（改动前口径） | 缓存开 | 结论 |
> |---|---:|---:|---|
> | 每局结果 / 手数 / 吃子 / 开局种类（3 局全部） | 和 30 ply / 截断 / 红1 黑0 … | **逐行相同** | ✅ **不改决策** |
> | 推理侧前向次数 | **6306** | **3612** | **1.75×**（当初预测 1.4~1.6×、上界 2×） |
> | MoE 路由直方图（MaxVio/最小份额/有效专家） | 1.389 / 0.6% / 6/8 | 1.361 / 0.2% / 6/8 | ⚠ **不是行为差异**：重复前向被省掉后，累计直方图的**样本数**变了（同一次前向重复计账被去掉），逻辑必然 |
>
> **第二组（`--games=2 --sims=64 --moves=40`，同一 seed）**
>
> | 读数 | 缓存关 | 缓存开 | 比值 |
> |---|---:|---:|---:|
> | 推理侧前向次数 | **20924** | **12750** | **1.64× 更少** |
> | 墙钟（总） | 1.2 s | **0.9 s** | **1.33× 更快** |
> | 决策相关行（每局结果/手数/吃子/开局种类/和棋分桶） | — | — | **完全相同** ✅ |
>
> ⇒ 前向省 1.64~1.75×，端到端墙钟省 1.33×（差额是编码/树操作/反向等与前后向无关的部分）。
> ⚠ 这两组是**廉价骨干（MLP）+ 小配置**的读数，用来验证"等价性 + 前向数"最合适；
> 生产口径（seq 骨干、1600 模拟）的墙钟应另量一次。
>
> **未做**：critic 价值（V）的节点级缓存 —— 读代码后确认**它本来就不重复**
> （每个模拟只新建一个孩子，孩子的 V 只在那一次算），所以"缓存 (p,v)"里的 v 那一半
> 没有可省的量。本项只缓存**策略先验**。

* **省下来的到底是哪一次前向**（推导）：
  * 现状：每次模拟 **1 次 actor（选中的那个节点） + 1 次 critic（新建的孩子）**，
    N 次模拟（N = `PPO_SIMS` = 1600）⇒ **2N = 3200 次骨干前向**。
  * critic 那一次**不可省**：每个模拟都会新建一个孩子，它的价值只算这一次。
  * actor 那一次**可以省**：被展开的节点数是 **D**（搜索树里"被展开过"的节点数），
    而现在 actor 前向被算了 **N** 次 —— 差额 `N − D` 全部是**同一个局面上的重复计算**
    （一个节点有几个孩子就被重算几次；根节点在 1600 模拟里被展开 ~40 次，
    见 `src/ppomcts_agent.cpp:2016-2018` 对"~40 个合法着法"的说明）。
  * ⇒ 缓存后总前向 **2N → N + D**；`D` 由搜索树形状决定（1600 模拟的树里
    被展开的内部节点大约几百个）⇒ **约 1.4~1.6× 的吞吐提升，上界是 2×**（当 D→N 时）。
    ⚠ `D` 是**可实测的**（代码里已有 `m_nodesCreated`，加一个"被展开过的节点数"计数即可）
    —— 建议在动手前把它印出来，免得收益靠猜。
* **为什么数值可以逐位不变**：先验来自"同一个网络 + 同一个局面"的确定性前向
  （`encodeState` + `ppo.actionMasked`），叶子价值同理（`encodeState` + `ppo.value`）。
  缓存只是把同一结果存下来 ⇒ **搜索树与决策应逐位相同**。
* **唯一的数值风险点：RNG 消耗顺序**。根节点的 Dirichlet 噪声（`pickUntriedByPrior`
  里那条加噪 U 项，`:372`）必须在**缓存的那一份先验**上加，且**每次决策只抽一次**
  （现状是每次展开抽一次？⇒ 实现时要对齐 RNG 调用次数，否则 `test_ppomcts` 的确定性断言会红）。
* **与置换表复用的关系**：`AZNode` 已有 `prior` 字段（`:213/230`），说明"把先验挂在节点上"
  本来就是设计的一部分；`m_tt` 复用子树时（`:2049-2059`）缓存的 `(p,v)` 应**一起继承**。
* **注意与既有注释的关系**：`:2090-2092` 的注释说"叶子自己的策略先验会在它被展开的那次模拟里用到，
  所以不必现在再算一遍"—— 那一条讲的是"**同一个模拟内部**不要把一个局面算两遍"（它修的是旧代码
  的重复），**不是**"节点级的缓存"；本文这条补的是**跨模拟**的重复，两者不冲突。
* **验收**：两棵源码树 + 两个二进制（同工具链），同 seed 同局面
  ⇒ ① 决策/访问分布**逐位相同**；② `probe`/`bench` 的每模拟墙钟显著下降；
  ③ `test_ppomcts` / `test_mcts` / `bench_anchor` 全过。

## 20. 2026-10-16 更新：SAC+AZ-MoE 的**动作输出**改成与 PPO 对齐（用户口径）

用户口径：**"sac agent 对齐 ppo agent 输出"**。

§8.4 第 2 条记的是"掉约 200 Elo 的锅在**稠密策略头**、不在状态维数"，据此上一轮把
SAC 的动作口径钉在 **128 槽哈希**上。本轮把它改成 **8100 双射**，理由是：

* 上一轮对齐的是**输入**（19×90 = 1710，`SACAZ_ALIGNED_REPR`），输出仍然是 128 槽哈希
  ⇒ 两个 agent 的**动作空间不同构**（同局面平均挤掉 5.16 个着法），"算法对照"这一层
  在原理上就不成立（`docs/agents_design.md` §11 / §20.4）；
* **这一改不加任何参数**：`ACTION_DIM` 是编译期常量，序列专家构建下头张量本来就是
  8100 宽 —— 改的只是"可达槽位"，不是参数/数据比（§8.4 关心的正是后者）；
* 因此 §8.4 那条 -200 Elo 的账**不能**直接搬到这一档上：它量的是"对齐表示 + 稠密头"
  整档，而本轮的 8100 双射**没有实测棋力**（只有结构、CE 与既有对齐口径测试的证据）。
  **要下棋力结论必须重训**（盘上没有 seq 口径的 SAC 权重，所以这一改没有作废旧模型）。

落地与配套修正：

| 位置 | 改动 |
|---|---|
| `src/chessboard.cpp` `createSACAZMoETbAgent` | 不再 `a->legacyHashAction = true`（走 `canonicalCell(from)*90 + canonicalCell(to)`，与 `PPOMCTSAgent` 逐字同一个公式） |
| `src/sacazmoetbagent.h/.cpp` | `Transition::curMask/nextMask` 与 `m_pendingMask` 从 `std::uint64_t[2]`（`i & 63` 折叠，只在 128 槽下忠实）换成 `std::bitset<ACTION_DIM>` ⇒ 8100 位掩码**逐位忠实**；`maskToBits/bitsToMask` 签名随之改 |
| `test/gui_seq_wiring_main.cpp` | 新增 [3b] 两条断言：自检报告必须印 "对齐双射 8100"、`ACTION_DIM == 8100` |
| `AGENT_SACAZ_OLD_MOE`(还原版) | **不动**（用户口径: "SAC legacy 不修改"）—— 两支**刻意不同口径**，不是漏改 |

⚠ 边界：`SACAZMoEMlpAgent` / `SACAZAgent` / `SACAZLegacyAgent` 的掩码容器仍是
`std::uint64_t[2]`。它们**没有**走双射（GUI 上对应条目要么不选双射、要么已移出下拉框），
所以当前无害；但谁要把其中任一支切到 8100 双射，**必须先做同一处修正**，否则训练侧
的合法集会被放大（损失照常下降，读数上看不出来）。

### 20.1 双射 vs 128 槽哈希的**留出保真度** A/B（2026-10-16，已实测）

"这一改的棋力未实测" 那一条现在有了第一批读数。工具：`train_bc --hash-action=1` 退回
128 槽哈希（默认 0 = 双射），其余**逐字相同**：`--agent=sac-moe --shared=1 --depth=4
--soft=1 --soft-depths=4 --epochs=8 --batch=64 --lr=0.002 --holdout=5`，同 teacher / 同数据 /
同 seed。判据用报告里那个**唯一可比**的列 `KL = CE − H(t)`（软目标下 CE 的下界是 H(t)）。

| 数据量 / seed | 双射 留出 KL | 哈希 留出 KL | 双射 train/留出 CE 差 | 哈希 train/留出 CE 差 |
|---|---:|---:|---:|---:|
| 300 局面 seed=20240901 | 2.6047 | **2.4830** | 1.20 | 0.51 |
| 300 局面 seed=20240902 | **2.3557** | 2.4506 | 0.93 | 0.34 |
| 1000 局面 seed=20240901 | **2.1705** | 2.2825 | 0.62 | 0.10 |

读法（三条，缺一条就会把噪声当结论）：

1. **300 局面这一档两个 seed 符号相反**（第 1 行哈希赢 0.12、第 2 行双射赢 0.09）
   ⇒ 240 条训练样本下两支**分不出来**。那时候唯一稳定的差别是**双射的过拟合差大得多**
   （0.93~1.20 vs 0.34~0.51）。
2. **加到 1000 局面（800 训练）双射赢 0.11 nats，且过拟合差从 1.20 收到 0.62** ——
   与本文档 §8.4 那条"掉 200 Elo 的锅在**参数/数据比**"的解释**一致**：双射不是更差，
   是更**吃数据**。这也意味着 §8.4 当年那个负结论是在小数据下量的。
3. **棋力仍然没有读数**：BC 的留出 KL 只说明"更像老师"，不说明下得好
   （工具自己也印这条边界）。要棋力必须 `bench_agent_arena --sac-legacy-hash`
   两臂配对开局对局 —— 那需要先训出两臂权重。

⚠ 口径边界：两臂的 CE 分属**不同的动作支撑集**（128 槽有碰撞、8100 是双射），
所以直接比 CE 会被"有效类别数"污染；表里的 KL 列同样不是完美对齐（H(t) 在两臂也
略有差别：0.5504/0.5484 与 0.5471/0.5391）。把它当**方向性读数**用，不要当成
"差 0.11 nats" 的精确度量。

### 20.2 双射 vs 哈希的**棋力对局**（2026-10-17，已跑；本轮**触底**、未分胜负）

新增构建目标 `bench_agent_arena_seq`（`SACAZ_ALIGNED_REPR=1 SACAZ_MOE_EXPERT_SEQ=1`，
与 `test_sacaz_aligned_seq` / 界面同一套结构）—— 原因：默认 arena 构建是 128 槽表示，
`legacyHashAction` 被 `!ALIGNED_REPR` 短路，**双射与哈希在那个二进制里根本无法区分**。

协议：两臂各用 `train_bc_sacaz_seq --agent=sac-moe --shared=0 --positions=400 --depth=4
--soft=1 --epochs=8 --seed=20240901` 克隆同一个老师（AB 深度 4），只差 `--hash-action`；
对局 `bench_agent_arena_seq --mode=match --a=sac --b=ab --backbone-sac=tb --games=12
--opening=6 --paired-openings`（先手交换 12 局）。

| 臂 | 比分 (胜/负/和) | 得分率 | 终局材料差 (A−B) |
|---|---|---:|---:|
| 双射 8100 | 0 / 12 / 0 | 0.0% [0, 24.2] | **−2.2** |
| 128 槽哈希 | 0 / 12 / 0 | 0.0% [0, 24.2] | −2.6 |

**结论：这一轮问不出答案，而"问不出"本身是有信息量的**：

1. **两臂都在地板上**（0-12，Wilson 上界 24.2%）—— 400 局面的 BC 策略离 AB-4 太远，
   得分率这个量已经饱和，两臂的区间完全相同 ⇒ **不可区分**。
2. 唯一没触底的量是**终局材料差**（arena 就是为这种情况才印它）：双射 −2.2 vs 哈希 −2.6，
   差 0.4 个子力值，**方向偏向双射**，但只有 12 局单样本，且两臂的初始权重不同（随机初始化
   随 `--hash-action` 改变 RNG 消耗）⇒ 只能记为"弱线索，与 §20.1 的 CE 方向一致"。
3. **下一步该怎么测才对**（这一条比读数更重要）：不要拿 `vs AB-4` 当尺子（地板效应会吃掉
   全部信号），而应该 **双射 vs 哈希 直接对局**（等强的两臂互下，Elo 尺度不依赖第三方强弱）
   —— 那需要 arena 把 `--sac-legacy-hash` 做成**按侧**的开关（现在它是全局的）；
   或者先把这个策略练到"能和 AB-4 打出非零分"再用材料差/得分率比较。

⚠ 权重格式注意：BC 训练器的 `--shared=1` 写出 `_trunk/_actorhead/_q1head/_q2head`，
而 arena 的 SAC 默认是 `Separate`（读 `_actor/_q1/_q2`）—— 两处口径不同, 载入会**响亮失败**
（本轮先踩过一次：`A 权重载入失败`）。要么训 `--shared=0`，要么给 arena 加 `--sac-shared`。

## 7. 诚实边界

* **本文是方案：本轮没有改任何 `src/` 代码，也没有跑任何实验。**
* **代码事实**（可逐项复核）：§1 全部；§3.1/§3.2 的规则与搜索判定点；§4.1 的两套搜索口径；
  §5.1 的缓存可行性（数值不变性 + RNG 风险点）。
* **算术**（可手算）：§2.2 / §0.1 的 MAC 与参数比；§3.4 的策略头参数 526,500 → 2,970。
* **推理/判断**（需要读数才能定论）：§0.1 的"当前口径下 MLP 期望价值更高"、
  §2.4 的五条可证伪条件与预测、§3.3 的共享干对 PPO 的收益幅度、
  §3.4 的空间化策略头在**骨干不是 conv** 时的收益、§4.3 的冷启动补丁。
* **我**没有**断言"seq 结构差"或"conv 一定赢"**：仓库已有的唯一干净对局读数是
  conv 对 MCTS 61.0% decisive（同一份 19 平面、不同排列），而 MLP 从未进过那个对局表。
* **★Z1 的收益是本次分析里最确定的一条**（不动结构、不作废权重、数值可逐位不变，
  前向数从 `2N` 降到 `N + D`），但它**仍未实测**，而且它的量级**取决于 `D`
  （搜索树里被展开过的节点数）**：D 越大收益越小，D→N 时才是 2×。上表里
  "约 1.4~1.6×"是**推理**，只有把 `D` 印出来、再把两棵树的每模拟墙钟与决策一致性量出来才算数。

## 8. 实现记：SAC 的 MoE-TB 骨干换成序列专家（2026-10-14）

> 用户口径（本轮）：**"sac agent 的 TB 专家使用 seq transformer"**。
> 这与上一轮 PPO 那句口径（"PPO agent 的 TB 专家默认使用 seq transformer"）是同一件事，
> 差别在于**SAC 这边有一个硬前提**：它的默认状态表示喂不进序列专家。

### 8.1 硬前提：SAC 的默认表示 1263 不能按格子切 token

序列专家按**格子**切 token，要求 `dIn % SeqLen == 0` 且 `SeqLen == POS_ROWS*POS_COLS == 90`
（`src/rl/seq_transformer.hpp` 的构造断言，不满足**响亮失败**）。
而 SAC 的默认表示 `STATE_DIM = 17*90 + 3 = 1263`（那 3 个规则标量是**追加的尾巴**，
不是第 18 个平面）**不满足整除** —— `src/rl/ppo.h:201-205` 早就把这条记下来了。

⇒ 只有**对齐表示**（`-DSACAZ_ALIGNED_REPR=1`，`STATE_DIM = 19*90 = 1710`）才行。
两条路都不通：把 1263 硬切会得到 `SeqLen=3/421` 这种没有棋盘语义的序列；
而对齐表示的切换是**另一个变量**（实测对 SAC 掉约 200 Elo，归因是"8100 路稠密策略头"
而不是状态维数本身 —— 见 `docs/sac_regression_2026_09.md` 与 `conv_resnet_moe_analysis.md` §7）。

### 8.2 落地形态：编译期开关 + 编译期守卫（默认一位不动）

| 落点 | 改了什么 |
|---|---|
| `src/sacazmoetbagent.h` | 文件顶部加 `#error` 守卫：`SACAZ_MOE_EXPERT_SEQ=1` 必须与 `SACAZ_ALIGNED_REPR=1` 同时出现；类里加 `MOE_EXPERT_SEQ` / `MOE_SEQ_HEADS=4` / `MOE_SEQ_BLOCKS=2` / `moeSeqPosMode()="2d"` 与整段口径说明 |
| `src/sacazmoetbagent.cpp` | `makeTbExpertMoe()` 在开关下改用 `SeqTransformerExpert<90,4,2>`（宽度取 `expertHidden`，默认 64），并**显式设置位置编码** `setPosModeByKey("2d")` —— 设不上就 `abort`（不能静默退回 1d）；`sharedWeightPrefix()` 换成 `weights/sacaz_moe_seq_shared_agent`；`backboneName()` 改成"稀疏MoE(序列Transformer专家)"；自检面板新增"专家类型"读数；只有这一支才 `#include "rl/seq_transformer.hpp"` |
| `test/sacaz_variants.h` | `variantName()` 跟着开关改字（与 `backboneName()` **逐字一致** —— 报告里两处不能各说一套） |

**为什么用编译期开关而不是运行时**：专家是 `SparseMoE` 的**模板参数**（`SparseMoE<Expert,E,K>`），
且 `STATE_DIM` 本身是编译期常量 ⇒ 只能另开二进制；这与既有的 `SACAZ_ALIGNED_REPR` 是同一套做法。

### 8.3 实测

| 读数 | 默认构建（对齐表示 + TB 专家） | 新构建（对齐表示 + 序列专家） |
|---|---:|---:|
| `bench_sac_mcts_min --backbone=tb` 自报的骨干名 | `稀疏MoE(TB专家)` | **`稀疏MoE(序列Transformer专家)`** |
| **actor 参数量** | **51,773,108** | **991,596**（≈ **1/52**；与文档里 seq-2d 的 991,596 逐位吻合） |

### 8.4 没做的事，以及为什么（诚实边界）

1. **没有把界面的 `AGENT_SACAZ_MOE` 默认换成序列专家**。原因不是"不想做"，而是
   **做不到而不附带另一个变量**：界面用的是默认构建（1263 / 128 槽），而序列专家在
   1263 下**构造就 abort**。要改界面默认，必须先决定"把 SAC 的状态表示也换成对齐表示"——
   而那是一条**已被实测为掉约 200 Elo** 的改动（归因在策略头），属于独立的一轮 A/B，
   不该混在这条口径里静默发生。
2. **没有做"对齐状态 + 保留 128 槽哈希动作"那个组合**。代码里其实已经有这条路
   （`legacyHashAction` 开关，`sacazmoetbagent.cpp` 里的 `if (!ALIGNED_REPR || legacyHashAction)`），
   而按 `conv_resnet_moe_analysis.md` §7 的归因，"掉 200 Elo"的锅在**稠密策略头**、
   不在状态维数 —— 所以**"对齐状态 + 哈希动作头 + 序列专家"很可能是这一支的正确配置**，
   值得单独设一轮 A/B（不在本轮口径内）。
3. **没有跑棋力读数**。`bench_sac_mcts_min_aligned_seq` 只做了 2 局冒烟；
   要回答"值不值"，按仓库纪律得 100 局 / 50 配对开局 + 锚点 Elo，且两臂都要先各自训练。
   本轮交付的是**开关可用、结构正确、断言全过**，不是棋力结论。
4. **序列专家自己的旋钮只接了一半**：位置编码模式接了（`moeSeqPosMode()`），
   但 `tokDim` 走的是构造签名里的 `expertHidden`（默认 64），没有单独暴露；
   dropout / `Blocks` 也没做成运行时旋钮。这些在 PPO 支有更完整的 CLI（`train_bc --pos/--dropout`），
   如果这一支要长时间用，应当把它们补齐。

## 10. 实现记：四支 TB 专家骨干全部换成序列 Transformer（2026-10-15）

> 用户口径：**"把所有 agent 里的 TB 专家换成 seq transformer，输入都使用 19x90 特征，与
> ppo agent 对齐"**。
> 上一轮（§8，2026-10-14）只把 **PPO** 那一支换成了 seq（`chessboard.cpp` 的

### 10.1 范围、开关与落点

| `AGENT_DQNMCTS_MOE` | `DQNMCTSMOETbAgent` | TB / 1263 | seq / **1710** | `DQNMCTS_MOE_EXPERT_SEQ` | `weights/dqnmcts_moe_seq_agent` |

**做法：不改源码默认值，只给 `chess`（界面）这个 target 加四个编译宏**

* `test_*` / `bench_*` / `train_*` 不带宏 ⇒ 仍旧跑 TB 那一套，**既有断言、读数与权重文件一位
  不动**，"改前"始终可以对照（这也是本仓库对"换骨干"的一贯要求）。

### 10.2 "19×90 与 PPO 对齐"的**准确**含义（重要）

对齐的是**形状与契约**，不是平面语义：

* 形状：`dIn = 19 平面 × 90 格 = 1710`，平面优先（`state[plane*90 + cell]`）⇒ 每格一个 token
  (`T = 90`)，token 宽 = 平面数；这正是序列专家"按格子切 token"的**硬前提**
  (`dIn % SeqLen == 0`，`SeqLen = POS_ROWS*POS_COLS = 90`)；
* 专家：四支都用**同一份实现** `RL::SeqTransformerExpert<90,4,2>`（Pre-LN、可学 2D 位置
  编码、逐行 softmax），与 PPO 支的 `PPOSeqExpert` 逐字同一个模板；
* ⚠ **平面语义各支不同，这是既有的、各有测量依据的口径，本轮不动**：
  * `PPOMCTSAgent`：14 棋子 + **被攻击 / 己方子被攻击** + 无吃子 / 重复 / 被将 = 19
    （`src/ppomcts_agent.h:96-101`）；
  * `DQNABAgent` / SAC 对齐表示 / `DQNMCTSMOETbAgent`（本轮新）：14 棋子 + **子力 / 总手数 /
    无吃子 / 重复 / 被将** = 19（`src/chessstate.h` 的 `CTX_*` 顺序）。
  两者都是 1710，都能喂进序列专家，但**不是同一组特征**。若产品口径要的是"连平面语义也统一
  （DQN/SAC 线改用 PPO 那两个威胁平面）"，那会改动 DQN 线那 5 个规则平面与 SAC 的上下文定义，
  属于**独立的一轮**（要重训、要重新量），本次没有擅自做。

### 10.3 逐条记账与边界（诚实项）

1. **SAC 两支的动作口径**（用户口径：保留 128 槽哈希动作头）：这条口径**只在界面生效**
   —— `chessboard.cpp` 的构造点 `#if SACAZ_MOE_EXPERT_SEQ` → `a->legacyHashAction = true`
   （`SACAZLegacyAgent` 同理），**类的默认值保持 `false`**（对齐表示 ⇒ 8100 双射）。
   ⚠ 但 `ACTION_DIM` 是**编译期常量**（`ALIGNED_REPR ? 8100 : 128`），所以无论这条开关
   怎么设，**头张量都仍是 8100 宽**，只有可达槽位被哈希到 128 个 —— 它隔离的是"动作编码"
   这一个变量，**不是**参数/数据比。
   **本轮新拿到的、与 §8.4 第 2 条猜测相反的证据**：`test_sacaz_aligned_seq`
   （对齐 + 序列专家）在**哈希**口径下有 **4 条学习动力学断言不成立**
   （"训练把 π(目标) 推离均匀"、"轨迹峰值 > 0.3"、"带监督项的轨迹均值 ≥ 对照组的 3 倍"、
   "Q 朝目标方向移动"），在**双射**口径下 **472 条断言 0 失败**。所以"对齐状态 + 哈希动作头
   + 序列专家很可能是正确配置"这句话**至少在这套单元级判据上不成立**；界面口径仍按用户选择
   保留哈希，但把它从"类的默认档"挪到"界面口径"，这样两种配置各有一个二进制盯着
   （类默认档由 `test_sacaz_aligned_seq` 盯，界面口径由界面自己盯）。
   要不要继续用哈希，建议按 100 局配对 + 锚点 Elo 再判一次（本轮没做棋力读数）。
2. **模拟/节点预算没有跟着调**：`SACAZ_MOE_SIMS=16`、`DQNMCTS_MOE_SIMS=40`、`DQNAB_NODES=256`
   都是按 **TB 专家的单次前向成本**（~5–6 ms / ~0.8 s 每步）定的。换成 seq 之后单次前向便宜一个
   量级 ⇒ 同样的墙钟预算能搜更多次，但"该给多少"**必须实测**（本仓库唯一测出过棋力的杠杆），
   顺手改会把"换专家"和"换预算"两个变量混在一轮里。**留作下一轮**。
3. **没有棋力读数**：本轮交付的是"结构正确 + 断言全过 + 界面构建通过"，**不是"更强"**。
   要回答值不值，得按仓库纪律跑 100 局 / 50 配对开局 + 锚点 Elo，且两臂各自先训练。
4. **存量权重按设计载不进来**：每支的前缀都换了（见 10.1），旧 TB 权重文件仍留在盘上给不带宏的
   `test_*` / `bench_*` 用；`Net::load` 的参数量守卫与各 agent 的前缀守卫都会**明确拒绝**，
   不会静默错读。
5. **D8 的 cwd 纪律**：`test_dqnmcts_moe*` 里的权重往返用例假设"运行目录里有 `weights/`"
   （即 **build 目录**）。在仓库根目录直接跑会得到 3 条 `saveModel 失败` —— 那是 cwd 造成的
   假报警，不是回归（两种配置**同样**失败）。跑法：`cd build/<...> && .\test_xxx.exe`，
   或直接 `ctest`。
