# 把 MCTS 模拟次数提到 800+ 能不能提高胜率？（实测回答）

**问题**：把 MCTS 类 agent 的模拟次数提到 800 以上，胜率会不会提高？

**一句话回答**：在当前工程里**不能可靠地提高胜率**。三条独立读数都指向同一处：
多出来的预算确实改变了搜索（80 → 800 有约 1/4 的局面换手、根访问份额 15% → 47%），
但**没有转化成胜率**，而成本是**线性 10 倍**；纯 MCTS 那条更极端 —— 800 次的选点本身
在两次同预算运行之间都**不重现**。

本文全部数字都标明来源：【实测·本轮】= 本次用新工具当场跑出来的；【实测·仓库】=
`docs/` 里已有的实测（注明出处）；【代码】= 读代码得到的机制。

---

## 0. 先分清是哪条 "MCTS"（预算差 10 倍）

| agent | 每步预算（`src/chessboard.cpp:84-86`） | 叶子评估 | 每次迭代成本 |
|---|---|---|---|
| 纯 `MCTS` | **800** 次随机回放 | 随机走到终局 | ~1.5 ms（成本全在回放） |
| `PPO+MCTS` | **80** 次 | PPO 的价值头（38 M 参数稀疏 MoE） | **6–9 ms**（成本全在访存） |
| `DQN+MCTS` | **200** 次 | DQN 的 Q 头 | 本文未实测 |
| `SAC+AZ` / `SAC+AZ-MoE` | 256 / 16 次 | 最大熵 critic | 小 MLP 0.05 ms / TB 骨干更贵 |

GUI 里那个写着 "MCTS 800 次模拟" 的是**纯 MCTS**（`chessboard.cpp:1083-1084` 直接
`MCTS mctsAI(env, 1.414f)`），不是 PPO+MCTS。所以"提到 800 以上"这句话，对纯 MCTS 是
"从 800 往上加"，对 PPO+MCTS 是"从 80 加 10 倍" —— 两者要分开回答。

## 1. 成本：先看值不值（【实测·本轮】）

同一台机器（i7-12650H 笔记本，16 GB，单进程串行，Windows）：

| agent | ms / 模拟（或迭代） | 80 次/步 | 400 次/步 | 800 次/步 | 数据来源 |
|---|---|---|---|---|---|
| PPO+MCTS（当前工作区，TB 专家） | **6.06–9.09** | 0.49–0.73 s | 2.4–3.6 s | **4.9–7.3 s** | `bench_ppo_sims --probe-positions=100`（9.0 ms）、`=20`（6.1 ms）、`bench_ppo_vs_ab --sims=80`（698 ms/步） |
| PPO+MCTS（已提交状态，MlpExpert） | ~0.14 | 0.011 s | 0.06 s | 0.11 s | 【实测·仓库】`README.md:196-202`（80 次模拟 = 11.0 ms/步） |
| 纯 MCTS | **1.5 ms / 迭代** | 0.12 s | 0.6 s | **1.2 s** | 【实测·本轮】`bench_mcts_sims`；与 `test_mcts` 的 100/500/1000/2000 = 130/650/1300/2627 ms 一致 |
| 参考：ABAgent 深度 4 | — | — | — | 0.11–0.22 s/步 | 【实测·本轮】`bench_ppo_vs_ab` 打印的 AB 每步耗时 |

两个直接后果：

1. **PPO+MCTS 的 800 次 = 每步 5–7 秒**，是对手（AB 深度 4）每步时间的 **20–60 倍**；
   换成**等时间**（AB 0.22 s/步）只够跑 **~24 次模拟** —— 比现在的默认 80 次还少。
   也就是说在当前骨干下，"800 次"不是"多一点预算"，而是"换一种比法"。
2. 这个 6–9 ms/模拟 是**未提交的工作区改动**造成的：`src/rl/ppo.h` 的 MoE 专家从
   MlpExpert 换成 `TransformerBlock<16,360>`（E=4, top-1），参数量 **2.15 M → 38.0 M**、
   单次前向 **0.139 → 3.59 ms**（该注释自带实测表）。README/`docs/` 里"每模拟
   0.14–0.22 ms"是**换专家之前**的数字，现在还没同步 —— 这一点本身值得单独修文档。

## 2. 决策：多搜索确实改变决策，但没有变"对"（【实测·本轮】）

新工具 `bench_ppo_sims --probe-positions=N`：**同一份权重**、同一批局面，只改模拟次数，
比较根节点的访问分布与最终选点（100 个局面，随机开局 6 手，AB 不参与）：

| 读数 | 80 次 | 800 次 |
|---|---|---|
| 根孩子数（分支数） | 38.4 | — |
|「深挖余量」= sims − 分支数 | 41.6 | 761.6 |
| 第一名孩子的访问份额 | **14.6%** | **46.4%** |
| 前二名 Q 差 | +0.0179 | +0.0278 |
| **选中的着法相同** | **76.0%**（即 24% 的局面换手，SE ≈ 4.3%） | |
| 每步耗时 | 719 ms | 7276 ms |

结论：**10 倍预算换来 1/4 的局面换手 + 明显更集中的访问分布** —— 搜索确实"更自信"。
但"换手"不等于"变强"，仓库里两个独立的代理读数都是平的：

* 对 AB 深度 4 的选点一致率：【实测·仓库】`issues_review.md:1566-1571`（bc8k_d4，60 局面，
  SE ±6%）：400 次 = 33.3 / 31.7 / 33.3%，1200 次 = 26.7 / 25.0 / 30.0%（c_puct =
  0.5 / 1.414 / 3.0），而 80 次是 30.0% —— **没有单调提升，1200 次那组还偏低**。
* B-5 复用探针（`issues_review.md:1454-1461`）：80 / 400 / 1200 次下对 AB 一致率
  = 20.0% / 20.0% / 22.5%（bc8k_d4）、12.2% / 15.0% / 15.0%（bc20k）。
* 另一个已知的极端对照：**未训练**权重把模拟从 80 提到 200，探针数字一动不动
  （`training_optimization.md:285-286`）—— 先验是噪声时多搜索完全无效。

**为什么"变了"却"没变好"**（机制，三条都有实测支撑）：

1. `getPUCT` 对未访问孩子返回 `+∞`（`src/ppomcts_agent.cpp:367-382`）⇒ 前 ~38 次模拟
   先把孩子铺满，深挖余量只有 `sims − 分支数`（`issues_review.md:1470-1476` 同一结论）。
2. 选点是**访问数 argmax**（`ppomcts_agent.cpp:1159-1205`，温度 0），所以"更集中"只体现为
   更自信，不体现为更正确。
3. 最关键：**叶子评估的误差比要分辨的差距大一个量级**。本轮训练出的 PPO 先验/价值头
   （`bench_ppo_distill --actor=1`，8000 局面，AB 深度 3 当老师）：价值头留出 MSE
   0.0169 → 0.0161，即 **RMSE ≈ 0.13**（±1 量程）；而根上前二名的 Q 差只有 **0.017–0.037**。
   多模拟是在**平均一个偏差远大于信号的估计器** —— 采样数再多也修不掉偏差。

## 3. 胜率：同权重头对头（【实测·本轮】，本文唯一直接量"胜率"的实验）

新工具 `bench_ppo_sims`：两个 PPO+MCTS 分身**载入同一份权重**、温度 0、开局由局号决定，
唯一差别是 `--sims-a` / `--sims-b`；因为选点在温度 0 下是确定性的，同预算的两次运行会
**逐位相同**，所以任何结果差异都能归因到预算。

| 实验 | 结果 |
|---|---|
| 空对照 80 vs 80（12 局） | 12 和（镜像确定性对手，只用来证明夹具无颜色/实现偏置） |
| **80 vs 800（8 局，60 手上限，`--material=1`）** | **A(80) 0 胜 / B(800) 1 胜（18 手被将死）/ 7 和**；得分率 43.8% ± 8.8% |
| 同上，终局评估代理（只对和棋，A 视角，阈值 ±0.2） | B 占优 5 局 / 均势 2 局 / **A 占优 0 局**；均值 **−0.390 ± 0.129**（n=7） |
| 成本 | B 是 A 的 **9.8×** 每步时间 |

老实读法（两条都写出来，别只挑一条）：

* **胜率上分辨不出**：0 胜 vs 1 胜、7 和，噪声带 ±8.8%，这个规模回答不了 ≤10% 的效应；
* **有一个方向一致的小幅优势**：代理读数说 800 次那侧终局平均领先约 0.4（约一个兵强，
  不到半个马），5 局占优、0 局落后。n=7、且代理指标本身是同一个弱评估器的意见，
  **只能当"有一点证据表明多搜索下得稍好"，不能当结论**；
* 这与第 2 节不矛盾：多搜索带来的边际提升**小于**该工程与 AB 深度 4 之间的差距，
  所以拿它对 AB 打，分数率仍然钉在 0–5%。

仓库里既有的胜率读数（全部与"多模拟"无关或方向相反）：

| 配置 | 对 AB 深度 4 的得分率 |
|---|---|
| 未训练，80 次模拟 | 5.0%（0 胜 18 负 2 和）【实测·仓库】`training_optimization.md:370` |
| 未训练，**等时间 ≈ 477 次** | **0%**（0 胜 6 负；三组配置各 6 局，20 局那组 0 胜 20 负）`agents_design.md:751-754` |
| BC20k（训练过），**等时间 565 次** | **2.5%**（0 胜 19 负 1 和）`training_optimization.md:366-370` |
| bc8k_d4（训练过，老师 d4），等时间 20 局 | 5.0%（0 胜）`training_optimization.md:425` |

**从 80 次（未训练）提到 565 次（BC 训练过）——模拟次数 ×7、先验质量大幅提升，
得分率从 5.0% 变成 2.5%，仍全在 ±5% 噪声带内、且没有一局赢。** 这是"加模拟次数"
在整个工程里最直接的一次检验，答案是负面的。

## 4. 纯 MCTS 那条：800 往上加更没意义（【实测·本轮】）

`bench_mcts_sims`（12 局面，随机开局 6 手，回放上限 200 手，与 `MCTS::simulateRandomPlay` 同口径）：

| 读数 | 值 |
|---|---|
| 每次回放耗时 / 平均手数 | 1.48 ms / **189.6 手（上限 200）** |
| **回放走到手数上限（按和棋返回 0.0）** | **85.3%** |
| 分胜负 | 14.7%（我方胜 7.5% / 我方负 7.2%，**基本对称 = 噪声**） |
| 单次回放标准差 | 0.384 → 800 次模拟的均值标准误 = **0.0136** |
| 800 次选点 vs **800 次重跑**（同预算） | **0/12 相同** |
| 800 次选点 vs 1600 次 | **0/12 相同** |

读法：

1. 纯 MCTS 每次迭代 1.5 ms 里绝大部分是"随机走满 200 手"，而 **85% 的回放以和棋收尾、
   返回 0.0** —— 也就是**没有信息**；剩下 15% 的胜负还是对称噪声。多模拟只是把每个孩子的
   均值**往 0 收敛**，方差降了、信号没涨（SE ∝ 1/√N：要把决策噪声降 3 倍要 9 倍预算，
   即 7200 次 ≈ 11 秒/步，而 AB 深度 4 是 0.1–0.2 秒/步）。
2. **同一个局面、同一个预算（800），两次独立运行选出的着法 12/12 不同** —— 800 次下的
   "策略"本身不是局面的稳定函数，这种情况下谈"提高胜率"没有意义。
3. 交叉印证：【实测·仓库】`test_mcts` 的 MCTS(1000 次) vs AB(深度 3) = **0 胜 4 负**；
   `agent_evab_design.md:212-216` 的 EVAB（限长回放 + 静态搜索）对 MCTS(600) = **6 胜 0 负**，
   与 AB 深度 5 等时间打平。**同一时间预算下，换估计器（回放改静态评估）比加迭代次数
   便宜两个数量级。**

## 5. 什么条件下"加模拟次数"才会值钱

把它们写成前提，就能看出现在缺哪一条：

1. **叶子评估的差分误差 << 兄弟局面的真实差**（现在是 0.13 vs 0.02–0.04，差 3–6 倍）；
2. **每次模拟便宜到能跑几千次**（现在 6–9 ms/模拟，等时间只有 ~24 次；MlpExpert 时代是
   0.14 ms/模拟，那条前提反而成立 —— 而那时的实测结论同样是"没有胜率收益"）；
3. **选点规则能把"多出来的预算"变成决策质量**（现在是未访问 +∞ + 访问 argmax，
   预算与分支数同量级时额外预算只买到"更自信"）。

三条同时成立时（AlphaZero 那种"训练好的网络 + 每步 800–1600 次模拟"），加模拟次数当然
有用；本工程现在一条都不满足，所以实测出来是"变了但没变强"。

## 6. 建议的杠杆（按性价比）

1. **先降每模拟成本**（等于白送模拟次数）：批量叶子前向（一次前向服务 8–16 个叶子）
   直接打在 R1 留下的访存墙上（`agents_design.md` §17.6、README「R1」段）。
2. **改选点，而不是加预算**：去掉未访问孩子的 `+∞`（或改成 Gumbel/基于 Q 的选点）——
   文档已把 Gumbel AlphaZero 标为"低模拟数下的算法正解"（`training_optimization.md:823`）。
3. **换叶子评估的验收指标**：现在只验过 MSE（蒸馏 MSE 降 4.2 倍而选点没动，
   `training_optimization.md:269-278`）。应该量**兄弟局面的排序一致性**（critic 值排序 vs
   AB 根分值排序的秩相关）—— 那才是 MCTS 真正消费的东西。
4. **纯 MCTS 那条**：把回放限到 20–40 手 + 用静态评估收尾（EVAB 路线），
   而不是把 800 提到 8000。
5. **棋力评估协议**：20 局等时间对局的噪声带是 ±5%，回答不了 ≤5% 的效应
   （`issues_review.md:1631`）。先用配对探针筛（`bench_policy_agreement` /
   `bench_ppo_sims --probe-positions`），再用几千局或与棋力相关的代理指标定论。

## 7. 复现

```bat
:: 本轮新增的两个工具
cmake --build <build> --target bench_ppo_sims bench_mcts_sims

:: 同权重、只改模拟次数：根访问诊断 + 选点换手率 + 每模拟成本（快，分钟级）
<build>\bench_ppo_sims.exe --probe-positions=100 --sims-a=80 --sims-b=800 ^
    --opening=6 --load=weights/sweep_prior

:: 同权重、只改模拟次数：头对头对局（慢；800 次一侧约 5–7 秒/步）
<build>\bench_ppo_sims.exe --games=8 --plies=60 --sims-a=80 --sims-b=800 ^
    --material=1 --opening=4 --load=weights/sweep_prior --seed=20250101

:: 纯 MCTS：回放结果分布 + 同预算重跑的重现性 + 选点换手率
<build>\bench_mcts_sims.exe --positions=12 --sims-a=800 --sims-b=1600 --verbose

:: 本轮用的先验/价值权重（旧权重在换专家后已无法载入，见下）
<build>\bench_ppo_distill.exe --positions=8000 --depth=3 --opening=8 --actor=1 ^
    --epochs=6 --actor-epochs=8 --save=weights/sweep_prior

:: 纯 MCTS 的时代对照（既有工具）
<build>\test_mcts.exe
```

**两个必须知道的坑（本轮踩到）**：

1. **`weights/` 下所有旧权重在换专家后都载入失败**（stderr: "张量数量不足 (文件被截断?)"，
   而 stdout 仍打印"载入成功"）：`bc8k_d4` / `r2_sp` / `verify_on` / `distill` 都是
   MlpExpert 时代的文件。要复现 `docs/` 里的任何棋力对照，得先重训一份 ——
   本轮用 `weights/sweep_prior_{actor,critic}` 顶上（8000 局面 BC，留出 top-1 5.5%、
   CE 8.99 → 5.41；注意它比 `docs/` 里的 bc8k_d4 弱得多，一致率不在一个量级）。
   **建议给 `loadModel` 的"张量数量不足"改成硬失败**，别让 stdout 说成功。
2. **两个 `bench_ppo_sims` 进程不能同时跑**：每个进程持有两个 TB 专家网络（各 ~1.2 GB），
   与本机常驻的 VM + VS Code + node 一起会把 16 GB 撑爆 —— 实测同一份代码从
   **6–9 ms/模拟**掉到 **170–180 ms/模拟**（换页抖动，慢 20 倍）。本轮所有对局数据因此
   是串行跑的；只有**耗时**列会被抖动污染，**决策与胜负不受影响**（温度 0，确定性搜索）。

## 8. 本文没验证的

* `DQN+MCTS`（200 次迭代）的同类标度实验 —— 未做，结论只能类推（它的叶子是自训练的 Q 头）。
* 800+ 次模拟下**头对头**的样本只有 8 局、60 手上限、代理指标为终局评估。要把
  "小幅优势"升级成结论，需要几百局量级（或换成与棋力相关的代理指标）。
* 批量叶子前向、Gumbel 选点这两条建议**只给了机制与出处，没有实测**它们的收益。
