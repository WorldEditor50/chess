# 混合对手训练：MCTS 50% + AB-L1..L4 各 12.5%（均匀分布采样）（2026-10 第四轮）

> 用户口径（原文）：**"实现 mcts, abagent-1,2,3,4 混合对局, mcts 对局数量占 50%,
> 其余 abagent 平分, 按照均匀分布采样选择 agent 对弈训练"**；随后的追加口径：
> **"增加 B 方混合 agent"**（= 把同一个池子接到**对局**那一侧，见 §9）。
>
> 一句话：给 PPO 的**自对弈训练**加一个**对手池** —— 每局开头按均匀分布抽一个对手
> （MCTS 50%，AB 深度 1/2/3/4 各 12.5%），对手的手**只推进局面、不进学习方的样本**，
> 并且**每局换先手**。默认关（纯自对弈，与改动前逐位相同）；界面后台训练已打开它。
>
> 代码：`src/rl/mixed_opponents.hpp`（权重 / 采样 / 深度→档位映射，**训练侧与对局侧共用**）、
> `src/ppomcts_agent.h/.cpp`（池子 + 训练循环里的对手分支）、
> `src/ppo_train_opponents.cpp`（池子的**构造**，单独一个 TU，理由见 §4）、
> `src/chessboard.cpp`（界面后台训练打开池子 + **对局侧的 `AGENT_MIXED_POOL`**，§9）、
> `src/mainwindow.cpp`（勾选框 + 下拉框那一项）、
> `test/test_mixed_opponents_main.cpp`（**44 条断言**，秒级进 ctest）、
> `test/repro_concurrency_main.cpp`（对局路径的真对局读数）、
> `test/train_ppo_main.cpp`（`--opponents=mixed` 等四个参数 + 直方图读数）。

## 1. 语义（三条，缺一条就不是这句话的意思）

| 口径 | 实现 | 为什么必须这样 |
|---|---|---|
| **"对局数量占 50%"** | 采样发生在**每局开头**，一局一个对手 | "数量"说的是**局**的比例；按手采样会变成"每手都可能换对手"，那不是"混合对局" |
| **"均匀分布采样"** | 一次 `U(0,1)` 落在**权重累积区间**的那一段：MCTS `[0,0.5)`、AB-L1 `[0.5,0.625)`、…、AB-L4 `[0.875,1)` | 权重与区间一一对应，且用 `RL::Random`（与 `setSeed` 同一颗引擎）⇒ **同一 seed 下对手序列可复现** —— 本工程所有随机性的统一口径 |
| **"其余 abagent 平分"** | `abWeight = (1 - mctsShare) / abMaxDepth`，默认 `0.5/4 = 0.125` | 参数化：`--mcts-share` / `--ab-max-depth` 想换成 3 档 AB 或 70/30 都只是参数 |

## 2. 两条边界（决定了这个功能的适用范围，不写清就会被误用）

### 2.1 对手的手**不进学习方的样本**（只推进局面）

自对弈里"对手那一半"是学习方自己按策略采样出来的，所以把它记成学习方的动作转移是
**on-policy** 的；换成真对手之后，同一份记录会变成 **"off-policy 却打着 on-policy 的标签"**
—— 对 PPO 这类需要行为策略的算法是实打实的偏差（那些动作从来没有以那个概率被采样过）。

所以对手的手只做一件事：**推进局面**。学习方自己的转移因此落在"被真对手应手之后的局面"上，
回报里带着对手的影响 —— 这正是"从对手身上学"的内容。
（与 `aiagent.h` 的 `OpponentPolicy` 逐字相同的纪律；那里还写了"把对手着法当样本收进来"
为什么需要另一套处理：要给网络对手特征、或按 off-policy 方法，否则价值目标不可辨识。）

### 2.2 每局换先手

奇数局对手执红（`trainSelfPlay` 的起手方是黑）。不换的话红黑两侧的样本量不对称，
而象棋的先手优势很大 —— 判据与 `bench_agent_arena` 的"交换先后手"同源。

## 3. 验证（`test_mixed_opponents`，**44 条断言 / 0 失败**，秒级进 ctest）

| 段 | 断言 | 实测读数 |
|---|---|---|
| [1] | 池子构成：MCTS 0.5 + AB-L1..L4 各 0.125、名字与深度对得上、权重之和 == 1 | `MCTS(800)=0.500  AB-L1..L4=0.125` |
| [2] | **采样直方图**：200 局，每个对手的局数落在**二项分布 ±5σ** 内（n=200 时 MCTS 的 σ≈7.07、AB 各 ≈4.68） | MCTS **100**（期望 100）、AB-L1..L4 = 17 / 28 / 29 / 26（期望各 25，全在区间内） |
| [3] | 每局换先手（第 0 局黑、第 1 局红、第 2 局又黑） | 三条都过 |
| [4] | **对手的手不进样本**：`maxMoves=1` 时，纯自对弈"学习方进轨迹 20 手 / 20 局"；混合对局"对手 10 手 + 学习方 10 手"，两者之和 == 总手数 | 20 / (10+10) ✓ |
| [5] | 默认关：池子空、`mixedOpponentGames()==0`、20 局全是学习方自己的手 | ✓ |
| [6] | 参数越界被**纠正**而不是静默换分布：`mctsShare=2` ⇒ 1.0（池里只剩 MCTS，**权重 0 的档位不建**）；`mctsShare=-1` ⇒ 0.0（只剩 AB，各 0.25）；`abMaxDepth=0` ⇒ 只剩 MCTS | ✓ |
| [7] | **对局侧与训练侧共用的采样件**（`RL::MixedPool`）：池子构成、**200000 次**采样的 5σ 直方图（比 [2] 紧约 30 倍）、空池返回 -1（调用方据此回退）、以及**深度 → 界面档位表**（§9.3 那处真实事故的回归） | MCTS 99747（期望 100000）、AB 各 ≈25000；映射 1/2/3→1/2/3、4→0、5→-1 ✓ |

> 这套测试跑的是**廉价骨干**（MLP 专家，每局 1 手 1 模拟），所以几百局只要几秒 ——
> 它量的是**采样分布**，不是棋力。放进 ctest 的理由：采样比例错一位（少一档 AB、
> 或 MCTS 抽成 100%）**不报错、损失曲线也看不出来**，而它正是用户口径的核心。

## 4. 一个实现上的决定：池子的构造单独一个 TU

构造对手池需要 `MCTS` 与 `ABAgent` 两个类（构造函数与 `findBestMove` 定义在
mcts.cpp / abagent.cpp）。把这段写进 `ppomcts_agent.cpp`，会让**15 个**已经链接它的目标
（`train_ppo` / `bench_ppo_*` / `test_diag` / `bench_ppo_sparse` / …）突然都需要再加两个
`.cpp` —— 而其中大多数根本不用这个功能。

所以：**池子的构造放在 `src/ppo_train_opponents.cpp`**，只有真正用到它的目标加那三个文件
（`CHESS_CORE`、`train_ppo`、`test_mixed_opponents`、`repro_concurrency`）。
配套还有一处实现细节：`trainSelfPlay` 里**只走虚函数** `AgentBase::getBestMove` 驱动对手，
MCTS 的模拟预算由 `BudgetMcts`（MCTS 的薄壳，把 `getBestMove` 覆写成
`findBestMove(color, budget)`）实现 —— 否则 `ppomcts_agent.cpp` 又会引用 `MCTS::findBestMove`
这个符号，把 15 个目标的链接问题带回来。

> ⚠ **CMake 上的一个坑（这个仓库自己记过、本轮又踩了一次）**：新增一个 `.cpp` 必须加到
> **每一个直接列源文件的目标**上，不能只加 `CHESS_CORE` —— 只在 `--target chess` 下构建
> 是查不出来的。本轮漏的是 `repro_concurrency`（它直接列源文件），表现是
> `LNK2019 指向 enableMixedOpponentTraining`。见 `CMakeLists.txt` 那一处的注释。
> 另一条同源的坑：**只 build `chess` 不会重链 `repro_concurrency.exe`** —— 用旧二进制跑
> 新功能会得到"看起来通过"的假读数（本轮实测：旧 harness 完全跑不出池子）。

## 5. 代价与读数（实测）

| 项 | 读数 |
|---|---|
| MCTS 对手（800 次迭代，与界面 MCTS agent 同预算） | ≈ **1.0 s/手**（实测 1.24 ms/迭代）；一局 60 手上限里它大约走一半 ⇒ **每轮多 ~30 s** |
| AB-L1..L4 | 0 / 3 / 34 / 90 ms 量级 ⇒ 可忽略 |
| 端到端（`train_ppo --backbone=conv --opponents=mixed --games=12 --sims=16 --moves=20 --opponent-mcts-sims=48`） | 12 局：MCTS 4 / AB-L1..L4 = 3 / 1 / 1 / 3；对手共走 **112 手**，学习方进轨迹 **112 手**（各占一半，符合"换先手"）；`unmatched = 0`（对手着法全部合法）；value MSE 0.618（训练在动） |
| 界面路径 | `repro_concurrency 1 4 4`（`ChessBoard` + 后台训练 + 自动保存）⇒ `全部跑完, 没有崩溃`；后台训练 clone 已带池子（`BG_TRAIN_MIXED_OPPONENTS = true`） |

**界面这一支的开销**（写进 `chessboard.cpp` 的常量注释）：MCTS 800 次迭代 ≈ 1.0 s/手，
一轮 60 手多 ~30 s；关掉它只需把 `BG_TRAIN_MIXED_OPPONENTS` 改成 `false`，立刻回到
纯自对弈（与改动前逐位相同）。

不只是"后台训练默认打开"，而是**界面上一等的开关 + 可见读数**：

| 项 | 位置 / 内容 |
|---|---|

| **每轮读数** | 每轮训练结束打一行：`[train] 混合对手: 共 N 局 \| MCTS(800)(0.500) x局/y手 AB-L1(0.125) … \| 学习方进轨迹 M 手`。**为什么要它**：采样比例错了（少一档 AB / 全抽 MCTS）在损失曲线上**完全看不出来**，这一行是界面路径上唯一能看见它的地方（工具侧的对应读数是 `train_ppo` 报告末尾的直方图）。走 Qt 的 `qInfo`，与仓库其它诊断（`[P1] 对手入训 = …`、`[weights] …`）同一条通道，在 Qt Creator 的 Application Output 里看 |

**验证（实测）**：

| 项 | 读数 |
|---|---|

## 8. 诚实边界

1. **本轮没有量棋力**：这份交付是"训练分布"的实现与验证（采样比例、两条边界、
   端到端能跑通）。"混合对手训练出来的权重比纯自对弈强多少"需要按
   `docs/conv_resnet_agent_2026_10.md` §4 的协议（100 局 / 50 个配对开局 / 等模拟预算）
   跑一轮 A/B —— **没做**。
2. **对手是"脚本型"的**（MCTS + AB 的固定等级），不是"冻结的历史权重"；
   本工程另有一条冻结快照的机制（`frozenOpponentOverrideFor`），本轮没接进这个池子。
3. **AB 的深度口径是"ABAgent 的搜索深度"**（1..4），与界面上的 `AGENT_AB_L1/L2/L3` +
   `AGENT_ALPHABETA`(深度 4) 同源；MCTS 的预算显式给 800（= 界面 MCTS agent），
   可用 `--opponent-mcts-sims` 改小来换墙钟。
   **⚠ 这句话在 §9 之前只是"文档里的口径"**：对局侧的映射曾经写成
   `AGENT_AB_L1 + (深度 - 1)`，于是"AB-L4"落到枚举值 16 = `AGENT_SACAZ_MOE_MLP` —— 详见 §9.3，
   现在由 `RL::MixedPool::matchAbLevelOfDepth()` 显式列出并进了断言。
4. **界面默认开、库默认关**：库侧 `trainSelfPlay` 在不打开池子时一行额外代码都不执行
   （不画随机数、不建实例），所以既有的自对弈读数与改动前**逐位可比**；界面侧默认勾上（`BG_TRAIN_MIXED_OPPONENTS = true`），不想用就取消勾选。
5. **§9 的对局侧池子同样没有量棋力**：那一节证明的是"每局真的换了一个对手、读数按对手分得清"，
   不是"混合对手池这支 agent 有多强"（池子当 A 方时的比分会因抽签而逐场不同，
   要下结论必须看逐对手那一行，报告里也这么写着）。
6. **`AGENT_MIXED_POOL` 不是真 agent**：它没有权重、没有常驻实例、没有自检项；
   它是"这一方每局抽一个真对手"的开关。所以：`saveCurrentAgentModel(19)` 返回 false
   （没有可存的东西）、后台训练那一支把它归进"预期没有后台训练"（不会每轮刷假警告）、
   评估模式下的"冻结口径"那一段专门说明它不需要快照（抽出的 MCTS/AB 都没有可训练权重）。

## 9. 对局侧：B 方混合 agent（用户口径："增加 B 方混合 agent"）

### 9.1 语义（五条）

| # | 口径 | 实现位置 |
|---|---|---|
| 1 | 界面 A/B 下拉框里多一项 **"混合对手池 (MCTS+AB1-4)"**（`AGENT_MIXED_POOL`，枚举值 19，**追加在末尾**） | `chessboard.h` / `mainwindow.cpp` |
| 2 | 选中它的那一方**每局**抽一个真 agent，抽中谁就由谁**下完这一局**（整局固定 —— 每手换对手不是"混合对局"，那样连"这一局输给谁"都说不清） | `matchAgents` 每局循环开头 |
| 3 | 抽签走 `RL::MixedPool::sampleIndex` + `defaultPool` —— 与**训练侧陪练池同一个函数**（唯一定义在 `rl/mixed_opponents.hpp`），所以"训练时的对手分布"与"对局时的对手分布"不会漂开 | `rl/mixed_opponents.hpp` |
| 4 | 胜负**按抽中的对手分组**记（`MatchStats::poolStats` / `poolGames`），报告里单列一段 | `MatchStats::detail()` |
| 5 | 自检面板报**它是什么**（构成 / 抽签口径 / 深度→档位映射），不是空串；"全部模型自检"的名单（`kAll`）里也有它一格 | `ChessBoard::getAgentSelfCheck(AGENT_MIXED_POOL)`、`mainwindow.cpp` |

抽中之后的落点会**写回 `redType/blackType`**，于是对局其余机制（决策路径、开场快照、
奖励口径、模式闸门、BC 采样）一行都不用改 —— 它们看到的是一支正常的 agent。

**两边都选池子**是允许的，但必须**各自独立抽一次**：只抽一次而只替换 A 方的话，B 方会带着
`AGENT_MIXED_POOL` 走进决策 switch，而那里没有这一档（它不是真 agent）⇒ 退化成"每手走第一个
合法走法"的**假对局**（报告看上去正常）。两边都抽时，逐对手那一栏的名字带 `A 方:` / `B 方:`
前缀，否则同名对手会把两方（互为对手）的胜负混进同一行。

### 9.2 池子是**每场对弈重算**的（不是 `static` 缓存）

第一版写的是函数内 `static`：只在第一次进入时初始化。后果是配置改过之后（界面上是那个勾选框，
占比 / 深度 / 对手 MCTS 预算走 `ChessBoard::setMixedOpponentConfig` 或 `chessboard.cpp` 里的出厂
常量 —— **训练侧与对局侧共用同一份设置**，只有一处决定"出厂口径"）再开一局，用的**还是老权重**
—— 读数看着正常、却与当前设置不一致（本工程最怕的那一类错）。现在改为在每场对弈的循环**之前**
建一次：既不是每局重算（白归一化），也不会跨场沿用旧配置。验证方式是让相邻两场用不同配置
（`repro_concurrency` 里奇数轮把占比压到 0）：

```
第 1 轮: 池子设置 MCTS 占比 = 0.50   -> 抽到 AB-L1（0.5 那一档里 AB 各 12.5%）
第 2 轮: 池子设置 MCTS 占比 = 0.00   -> 抽到 AB-L2（此时池子里**没有** MCTS）
第 3 轮: 池子设置 MCTS 占比 = 0.50   -> 抽到 AB-L2
第 4 轮: 池子设置 MCTS 占比 = 0.00   -> 抽到 AB-L1
```

### 9.3 ⚠ 本轮抓到的一处真实事故：深度 4 映射到了另一个 agent

对局侧第一版写的是：

```cpp
const AgentType sampled = (e.abDepth <= 0) ? AGENT_MCTS
                                           : (AgentType)((int)AGENT_AB_L1 + (e.abDepth - 1));
```

而界面枚举里 **AB 只有 L1/L2/L3**（深度 1/2/3），**深度 4 就是下拉框里那一档
`AGENT_ALPHABETA`**（`AB_DEPTH = 4`）。于是：

| 池子里的档位 | 表达式算出的枚举值 | 实际是谁 |
|---|---|---|
| AB-L1 / L2 / L3 | 13 / 14 / 15 | ✅ `AGENT_AB_L1/L2/L3` |
| **AB-L4** | `13 + 3 = 16` | ❌ **`AGENT_SACAZ_MOE_MLP`**（SAC+AZ 稀疏 MoE，一个完全不同的网络） |

**它为什么差点蒙过去**：报告里那一行仍然写着"AB-L4"，比分照常记；唯一的异常是那一局的奖励
口径 - SAC 那一支有"学习口径"，于是明细里出现 `奖励 A=-0.00[学习口径]` —— 而 AB 应该永远是
`[引擎口径]`（`agentHasLearningRewardTable` 里没有 AB）。是这一行**对不上口径**才把它揪出来：

```
修复前: 第 1 局: 红=混合对手池 黑=Alpha-Beta -> 和棋  ... 奖励 A=-0.00[学习口径] B=0.10[引擎口径]
修复后: 第 1 局: 红=混合对手池 黑=Alpha-Beta -> 和棋  ... 奖励 A=0.00[引擎口径] B=0.30[引擎口径]
```

**修法**：把"深度 → 界面档位"做成共享头文件里的**显式表**，不再用算术：

```cpp
inline int matchAbLevelOfDepth(int abDepth);   // 1..3 -> 1..3; 4 -> 0 (= 主 Alpha-Beta 档); >=5 -> -1
```

`-1` 表示界面上**没有**这一档，调用方必须报警（用主 AB 档兜底 + `qWarning`），不许静默取近似。
断言进了 `test_mixed_opponents [7]`：三档映射 + 深度 4 → 0 + 深度 5 → -1 + **默认池里每一档
都必须是界面上真有的一档**（最后这条正是能在修复前把 16 抓出来的那条）。

> 教训（与 §4 的 CMake 坑同一类）：**"两边都写得看起来对"不等于一致** —— 训练侧用深度建
> `ABAgent`，对局侧要换成枚举档位，两个数字体系不同源。凡是这种"跨体系映射"，
> 都要显式列出来 + 进断言，而不是靠算术巧合。

### 9.5 代价

* 抽签本身是常数时间（一次 `U(0,1)` + 线性扫描 5 项），每局一次；
* **真正的代价来自对手本身**：抽到 `MCTS(800)` 时那一方每手 ≈ 1.0 s（与界面 MCTS 同预算），
  一局 120 手上限最多多花约 1 分钟；抽到 AB 各档最快（深度 1 几乎瞬时，深度 4 = 主 AB 档的代价）；
* 所以"池子当某一方"的**一场比分**的墙钟取决于抽签结果 —— 这也是"逐对手分组"必须存在的
  另一个理由（同一场里各局的代价与强度都不同）。

> **⚠ 界面二进制要重链**（与 §4 那条 CMake/构建坑同一类）：这一轮改了 `mainwindow.cpp`
> （下拉框那一项的位置 + "全部模型自检"名单），所以**必须重新链接 `chess.exe`**；
> 而 `chess.exe` 正被一个**正在运行的界面实例**占用时，链接会以
> `LNK1104: 无法打开文件"chess.exe"` 失败 —— 那是"文件被锁"，不是编译错误（同一份
> `mainwindow.cpp` 在 `probe_hvai_flow` 里链接成功并 `失败项: 0`）。关掉那个实例再
> `build.ps1 chess` 即可。**旧的 `chess.exe` 不会自己更新**：它跑起来仍然看不到这次
> 的改动（下拉框位置/自检名单），而"看着能跑"最容易被当成本轮已经生效。
