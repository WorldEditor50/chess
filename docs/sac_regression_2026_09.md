## 0. 当前状态（先说结论，再说没查清的）

### 0.000 【最终形态】当前 SAC 与 59e5233 **逐手等价**（不止统计等价）

用户要求"把 agent 还原回 `59e5233` 的 SAC"。做法不是再存一份代码，而是把等价性
**证明并钉住** —— 当前代码相对 59e5233 的改动全是"等价重写"，判据就是
**同一输入必须给出同一走法**。

判定方法（`tools/verify_sac_equiv_59e5233.ps1`）：同一份 `bench_sac_mcts_min` 源码
编到两棵树上，给两版**同一个 `--mcts-srand`**（固定对手随机流），各导出走法序列逐行 diff。

| 用例 | 行数 | 结果 |
|---|---|---|
| moe-mlp, 2 局 x 40 手 | 81 | **逐手完全相同** |
| moe-mlp, 4 局 x 80 手（seed 20240901） | 258 | **逐手完全相同** |
| moe-mlp, 4 局 x 80 手（seed 777） | 300 | **逐手完全相同** |
| tb, 2 局 x 30 手（两个种子） | 61 x2 | **逐手完全相同** |

另有**不依赖基线树**的回归护栏（`tools/verify_sac_golden.ps1` + `test/golden/`）：
把首次等价验证得到的走法序列固化成基准，以后任何改动动了 SAC 的行为就当场变红，
并打印**第一处**差异（只报"第 N 行不同"没有诊断价值，一处不同会让整局岔开）。

等价性只在**已测量的用例**上成立（上表两个骨干、两种手数上限、两个种子、观察 40~80 手）；
不能说"对所有设置、任意深度都等价"。当前构造出等价行为所依赖的默认值见 §6。

**补充（同日，用户要求"用不同的 C++ 类把新旧 SAC 区分开"之后）**：

* "还原回 59e5233"在代码上的落点不是"再写一份实现"，而是一个**派生类**
  `SACAZLegacyAgent`（`src/sacazlegacyagent.h`），对应界面类型
  `ChessBoard::AGENT_SACAZ_OLD`（下拉框"…(59e5233 行为还原版)"）。
  它复用 `SACAZAgent` 的全部算法，只钉住 4 个口径值（目标熵 0.98 / alpha lr 1e-3 /
  critic 不钳位+纯 MSE / 叶子全量估值），加一个独立权重前缀
  `weights/sacaz_old_agent`（后台训练临时前缀 `weights/_temp_train_sacaz_old`）。
* 网络结构上它与 59e5233 **逐行相同**：`buildNet` 的层构建行与
  `git show 59e5233:src/sacazagent.cpp` 逐行 diff 过（17 行全同）。
* **⚠ 本文档早先版本里的一个错误已修正**：曾经说"用 `TanhNorm<Linear>` 且 `r = 1`
  可以逐位复现 59e5233 的那层激活（与 `Layer<Tanh>` 逐项相同）"。**这是错的**——
  `TanhNorm::forward` 把偏置加在 tanh **外面**（`o = Fn(tanh(r·W·x) + b)`），
  而 `Layer<Tanh>::forward` 是 `tanh(W·x + b)`，两者只在 b ≡ 0 时相同。
  实测（`test_sacaz` [14]，同权重同局面，稀疏 MLP 专家骨干）：
  max|Δπ| = **1.8e-07**、max|ΔQ| = **8.9e-06**。
  那个 `legacyNet` 开关**已删除**；`buildNet` 里所有分支就是 `Layer<RL::Tanh>`。
* 这条错误当时**测不出来**，原因值得记：开关是普通成员，赋值发生在构造函数
  `buildNet()` **之后** ⇒ **静默空操作**，"两个变体是否等价"的检查永远通过。
  现在 `SACAZAgent::hiddenActivationName()` 报的是 actor 第 2 层的**真实类型**
  （读网络，不回显开关），并印在自检面板第一段。

### 0.0 【已定位并修复】根因：隐层激活被换成了 `TanhNorm`

**一句话**：`buildNet` 的 `SparseMoeMlp` 分支里，隐层激活在**先前就存在的一处未提交改动**中
从 `RL::Layer<RL::Tanh>` 被换成了 `RL::TanhNorm<RL::Sigmoid>`（`SparseMoeTb` 分支同样）。
把它改回 `Layer<RL::Tanh>` 之后：

| 指标 | TanhNorm（坏） | 改回 Tanh（好） | 改前原树 59e5233 |
|---|---|---|---|
| 前向: 先验加权和 | 77.066641 | **75.721268** | **75.721268**（逐位相同） |
| 前向: Q1 加权和 | 36.640323 | **16.613757** | **16.613757**（逐位相同） |
| 60 局对 MCTS | 44.2% [32.3, 56.7] | **75.8%** [63.7, 84.9] | 70.0% [57.5, 80.1] |

**为什么这个改动难查**（值得记下来）：
* `TanhNorm<Fn>::_(STATE_DIM, h, ...)` 与 `Layer<Tanh>::_(STATE_DIM, h, ...)` 都是
  "输入 STATE_DIM、输出 h" 的**同形状**层 ⇒ **参数量完全相同**（1436536），
  于是权重文件的参数量守卫、`paramCount()` 对比、甚至"前 4 个权重原值"都**看不出差别**；
* 它不在这一轮我改过的任何文件里（`git diff HEAD` 显示这一处改动**先于本轮**存在），
  所以"我改了什么"的思路会一直漏掉它；
* 症状是"随机权重下棋力掉 26 个点"，看起来像算法/表示问题，实际是一行激活函数。

**定位手法（下次直接照做）**：
1. `--dump-forward`：同种子下打印**状态指纹 + 先验加权和 + Q 加权和**。
   状态指纹相同而网络输出不同 ⇒ 问题在"权重或前向"，与训练/搜索无关。
2. `--dump-forward` 里再打各网络的**前 4 个权重原值**（浮点加权求和当指纹会饱和，
   实测同一个和对应两套不同权重）。
3. 权重也逐位相同 ⇒ 只剩"前向路径"，此时 `git diff <基线commit> -- <agent>.cpp`
   一眼就能看到层类型的差异。

### 0.0.2 【最终判定】配对复测：当前代码 **不低**于 59e5233

用户反馈"回退后胜率仍不如 59e5233"。上一节的判定有一个**方法学缺陷**：MCTS 对手的
随机流每次运行都不同（见 §7 第 0 条），所以两次运行的"基线 vs 当前"并不是同一副牌。
给两版**同一个 `--mcts-srand`**（对手行为逐局一致）后重测。

**复现命令**（两版必须用**同一个** `--mcts-srand`，否则又是在比"对手的随机流"）：

```bat
:: 基线: 在 worktree 里单独编译同一份工具
git worktree add --detach E:\home\code\chess_base_59e5233 59e5233
::   (把 test/bench_sac_mcts_min_main.cpp 拷进去 + 在它的 CMakeLists 加同类目标)
cmake --build E:\home\code\chess_base_59e5233\build-min --target bench_sac_mcts_min

:: 两版各跑同一组参数
set SEEDS=20240901 777 31337
for %s in (%SEEDS%) do (
  build\...\bench_sac_mcts_min.exe            --games=100 --sims=160 --plies=120 ^
      --opening=4 --seed=%s --mcts-srand=12345 --backbone=moe-mlp
  E:\home\code\chess_base_59e5233\build-min\bench_sac_mcts_min.exe --games=100 ... ^
      --seed=%s --mcts-srand=12345 --backbone=moe-mlp
)
:: 自检: 同一命令跑两次必须**逐局相同** (否则 --mcts-srand 没生效)
```

|---|---|---|---|
| 59e5233（基线） | 600 | 304 / 34 / 262 | **72.50%** |

**结论**：
1. **当前代码不低**：两组配对分别 +1.33 与 +0.33 个百分点，600 局合计 +0.83 点，
   所有区间大幅重叠 ⇒ 统计上**不可区分**（甚至略偏高）；
2. 而**修复前**（`TanhNorm`）在同口径下是 44~46% ⇒ 修复确实拿回了那 26~30 个点；
3. 用户观察到的"比不上"最可能来自三处：
   * **用户那边的二进制还没包含 `TanhNorm` 修复** —— 那一行在 `git diff HEAD` 里，
     属于**未提交**的工作区改动；别人从提交点拉一份工作区就会带上坏的版本；
   * 拿的是**修好之前**的训练权重；
   * 或者一次**没有固定对手随机流**的读数（见 §7 第 0 条：同一命令两次能差 20 个点）。
   建议复跑时加 `--mcts-srand=<两版同一个数>`。

**顺带一个方法论副产品**：固定对手随机流之后，**SAC 自己的种子对结果影响很小**
（基线 70.0/71.5/73.5/73.5/72.0/74.5；当前 71.0/78.0/74.0/73.0/69.5/74.5），
而**对手的随机流影响极大**（同一命令两次 62.5% vs 82.5%）。也就是说：这类"对 MCTS"的
评测里，**方差主要来自评测器（对手的随机流），不是来自被测 agent** —— 这正是本仓库
`docs/mcts_sims_scaling.md` §3 那条"分辨力不足"的具体形态，也是之前那些
"决定性"结论屡次翻转的原因。

## 3. 容量实验：隐藏层假设不成立（方向相反）

`--sac-hidden` 扫 64/128/256（随机权重，对 MCTS 40 局）：

| 隐藏层 h | 8100 双射动作 | 128 槽哈希动作 |
|---|---|---|
| **64（默认）** | **58.8%** [43.4, 72.6] | **50.0%** [35.2, 64.8] |
| 128 | 46.2% [31.8, 61.3] | 45.0% [30.7, 60.2] |
| 256 | 55.0% [39.8, 69.3] | 41.2% [27.4, 56.6] |

**加宽隐藏层在两种动作空间下都更差。** 所以"隐藏层不足导致采样能力弱"不成立。
真实的结构失衡是**反向的**：策略头参数从 8,192 涨到 518,400（63 倍）而 h 不动
（`1263→MoE→Tanh(64)→Linear(128)` vs `1710→MoE→Tanh(64)→Linear(8100)`），
即**参数/数据比**失衡，而不是"瓶颈太小"。

## 4. 高维动作空间的稀疏性：只解释一部分

### 4.1 单元级读数（新增，这是用户第三次提问的直接答案）

`test_sacaz` 的 `[12a]` 节量的是"**只关掉 AZ 监督项、只留软 Q 项**时, 能不能把某一个动作
的概率推起来"。这个比值 = **对照组 π(目标) / 均匀**：

| 表示 | 动作头宽度 | 对照组/均匀 |
|---|---|---|
| 改前（128 槽哈希） | 128 | **13.83** |
| 对齐（8100 双射） | 8100 | **0.43** |

也就是说：**同样的软 Q 项、同样的批数与学习率，在 128 路输出下能把单个动作的概率推到
均匀的 13.8 倍；在 8100 路输出下连均匀都推不到。** 这正是"高维动作空间数据太稀疏"的
直接体现 —— 不是比喻, 是一个可复现的单元级读数。

原因是双向的：
1. **输出侧**：策略头 63 倍宽（8100 vs 128），而瓶颈 h=64 不动 ⇒ 每个动作能分到的
   "表达能力"被摊薄（梯度也被摊薄：一次更新只碰 44/8100 = 0.5% 的列，
   而 128 槽下是 44/128 = 34%）；
2. **数据侧**：106 局自对弈里每个动作槽位只被访问极少数次，稀疏程度进一步提高。

### 4.2 表示级读数（多种子合池）

| 配置 | 局数 | 比分 | 得分率 | 95% Wilson |
|---|---|---|---|---|
| 改前 `59e5233`（1263/128） | 200 | 101/14/85 | **71.8%** | [65.1, 77.5] |
| 对齐（1710/8100） | 200 | 55/36/109 | **54.8%** | [47.8, 61.5] |

区间不重叠 ⇒ 表示本身值约 **17 个百分点**（约 120 Elo），与 §4.1 的机制一致。

> **注意**：这两组 200 局是在**修好 TanhNorm 之前**跑的，所以两组都被那个隐层缺陷
> 压低了绝对值；但"对齐 < 改前"这个**相对结论**仍然成立（两组受同一个缺陷影响）。

## 7. 方法学教训（比结论更值钱）

0. **【本轮最重要】评测器本身不可复现 —— 所有"对 MCTS"的跨版本比较都被污染了。**
   MCTS 的展开与随机走子用 `std::rand()`, 而 `std::srand` 播的是
   `std::time(nullptr)`（`src/mcts.cpp` 的构造函数）。于是**每次运行的对局随机性都不同**：

   | 同一命令 (当前二进制, 20 局) | 得分率 |
   |---|---|
   | 第 1 次 | 62.5% |
   | 第 2 次 | **82.5%** |

   两次相差 **20 个百分点**。"换一次 MCTS 的随机流"就等于换一副牌, 于是
   "A 版本 70% vs B 版本 68%"这类结论**在统计上毫无意义** —— 它测到的可能只是
   对手换了牌。修复办法已加进工具：`bench_sac_mcts_min --mcts-srand=<N>`
   （两版都用同一个 N, 对手行为逐局一致；固定后同一命令两次跑出**完全相同**的比分）。
   **本文档 §1~§6 里所有"对 MCTS 的比分"都受这个缺陷影响, 请按"单次抽样"读。**

1. **单种子/几十局的读数不能下"决定性"结论。** 本文档第一版就是拿 80 局、单种子
   得出"72.5% vs 45.0%，区间不重叠 ⇒ 决定性"，随后同一配置在别的运行里量到
   43.8% / 46.0% / 44.0%。**判据必须是多种子合池 + 可复现的对手**（本仓库
   `docs/mcts_sims_scaling.md` §3 早就写过这条，我违背了它）。
2. **"数学上等价"不等于"行为上等价"。** `1.0f * x` 是恒等，但在与参考实现对比的场合
   应写成显式分支；否则排查者会先怀疑它，白花时间。
3. **指纹（初始权重哈希）是分层的廉价工具**：它一次就把"随机流差异"和"代码差异"分开，
   否则会在 RNG 上浪费大量排查时间。
4. **"逐位一致"的断言只能证明单点等价**，不能证明整条搜索路径等价；要证明后者，
   必须在**同一局面**上对比根的访问分布，而不是只比一次前向。
