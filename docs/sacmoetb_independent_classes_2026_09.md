# 把 SAC+AZ+MCTS 的稀疏 MoE 两支拆成**独立类**（2026-09）

用户口径：

> 使用独立类实现 sac + mcts + alphazero + moe + tb专家 与
> sac + mcts + alphazero + moe + mlp专家，并按照建议验证问题。
>
> 后续：新的奖励方法也应用到 sac + mcts + alphazero + moe + mlp 专家；
> 测试验证对弈使用 mcts agent 或者 ab agent level=1。

这一份记录**做了什么、怎么验证的、代价是什么**，以及顺带回答的另一个问题
（"mlp 专家用独立骨干会不会更好" —— 实测答案见 §6）。

---

## 1. 拆分后的四个类（互不继承、互不包含）

| 类 | 骨干 | 界面 agent 类型 | 文件 |
|---|---|---|---|
| `SACAZAgent` | 纯 MLP（两个 Tanh 隐层） | `AGENT_SACAZ` | `src/sacazagent.{h,cpp}` |
| **`SACAZMoEMlpAgent`** | 稀疏 MoE(E=8, top-2) + **MLP 专家** | `AGENT_SACAZ_MOE_MLP` | `src/sacazmoemlpagent.{h,cpp}` |
| **`SACAZMoETbAgent`** | 稀疏 MoE(E=4, top-1) + **TB 专家** | `AGENT_SACAZ_MOE` | `src/sacazmoetbagent.{h,cpp}` |
| `SACAZLegacyAgent` | 59e5233 行为还原版（自带两支骨干） | `AGENT_SACAZ_OLD*` | `src/sacazlegacyagent.{h,cpp}` |

拆分前是**一个类** `SACAZAgent` + `enum class Backbone {Mlp, SparseMoeMlp, SparseMoeTb,
DenseMoeTb}` + 运行时 `switch` 选层。现在**骨干 = 类型**：

* **隔离是结构性的**：改 `sacazmoetbagent.cpp` 碰不到 MLP 专家那一支（不同的文件、不同的类）
  —— 不再是"靠 git diff 自证这一次没改到"。
* **一个类 = 一个骨干**：不再有"同一个类背着两个界面 agent 类型"的坑。
* **全部实验旋钮保留**：`trunkMode` / `rewardShape=3` 的动态奖励分配 / 目标网 / 熵项 / α …
  两个新类都是 `SACAZAgent` 的**逐字副本**（见 §4.1 的生成方式），所以 A/B 能力一位没丢。
* **哪些东西按骨干分了家**（正是"一个骨干一支"的收益）：
  `tbHonorHeads` + 五个 TB 头数读数只在 `SACAZMoETbAgent`；
  `expertHidden` / `auxLossCoef`（MoE 负载均衡）只在两个 MoE 类；
  纯 MLP 类**连 MoE 路由读数都没有**（以前它恒返回 0/-1）。

## 2. 生成方式（为什么可以确保"只是搬家"）

两个新类是**脚本复制 + 改名**生成的，然后用**归一化比较**证明"除类名/守卫/include
之外逐字符相同"（PowerShell 侧把类名替换成占位符后 `-ceq` 比较 → 四个文件全部 True）。
之后只手工改了这些**按骨干分岔的地方**：

| 手工改动 | 说明 |
|---|---|
| `makeTrunkLayers()` | 四支 switch → 每类一支（**层构造顺序逐字保留**：MoE 层在前、Tanh 层在后 —— 顺序决定 `RL::Random` 的消耗，是"同种子权重逐位相同"的前提） |
| `backboneName()` | 静态枚举表 → 每类一个实例方法（稠密对照组由 `moeDense` 决定） |
| `guiAgentLabel()` / `defaultWeightPrefix()` | 每类一个：`weights/sacaz_agent` / `sacaz_moe_tb` / `sacaz_moe_mlp`（**四支四前缀**：共用会让后训练的那一支静默覆盖另一支） |
| 删掉不属于自己的东西 | MLP 类删 TB 头读数与 MoE 读数；MoE-MLP 类删 TB 头读数与 `tbHonorHeads`；TB 类删 MLP 专家的 `expertHidden` 用法 |

### 3.1 接线时抓到的第二个真 bug：三个类**共用同一个共享口径权重前缀**

逐字副本把 `sharedWeightPrefix()` 一起带过来了 —— 三个类**都返回**
`"weights/sacaz_shared_agent"`。拆分前这没问题（一个类一个值），拆分后它意味着
**两个骨干互相覆盖权重**：TB 那一支、MoE-MLP 那一支、纯 MLP 那一支写的是同一批文件，
而文件里是不同骨干的权重（结构指纹能挡住"层数不同"，挡不住"同构但口径不同"）。

修法（每个类一个值，且**不动界面存量模型**）：

| 类 | `sharedWeightPrefix()` | 说明 |
|---|---|---|
| `SACAZAgent`（纯 MLP） | `weights/sacaz_mlp_shared_agent` | 新值（它本来不该用 TB 那个值） |
| `SACAZMoETbAgent` | `weights/sacaz_shared_agent` | **保留历史值** = 界面 `AGENT_SACAZ_MOE` 的存量模型照旧能载入 |
| `SACAZMoEMlpAgent` | `weights/sacaz_moe_mlp_shared_agent` | 新值 |

临时文件前缀同理（`TMP_WEIGHTS_SACAZ_MOE_MLP`）—— 共用会让**后台训练互相覆盖**。

## 4. 验证（三条硬证据）

### 4.1 四个骨干的指纹与拆分前**逐行相同**（AB level=1 锚点）

方法：拆分**之前**先把四个骨干的指纹存下来，拆分之后用同一条命令再跑一遍，逐行 diff
（抹掉墙钟读数）—— 用 `bench_sacaz_vs_ab --depth=1`（= 界面上的 `AGENT_AB_L1`）：

```bat
bench_sacaz_vs_ab --games=2 --sims=16 --plies=60 --opening=4 --depth=1 ^
                  --seed=20240901 --backbone=<mlp|moe-mlp|tb|dense-tb>
```

| 骨干 | 拆分前 vs 拆分后 |
|---|---|
| `mlp` | **逐行相同** |
| `moe-mlp` | **逐行相同** |
| `tb` | **逐行相同** |
| `dense-tb` | 第一次**不同** → 查出根因（见 4.2）→ 修好后**逐行相同** |

> 比较口径：抹掉**墙钟读数**（`ms/步` / `构建耗时` / `总耗时`）与**空白**之后逐行比。
> 后者是必须的 —— `%6.1f` 这种列宽格式化在数字位数变化时会多/少一个空格，
> 不归一会把"耗时不同"误报成"顺序不同"（本轮就误报过一次 `tb`，
> 归一之后差异是 **0 行**）。

指纹里含：每局胜负/手数/材料、`唯一参数量`、`|Q|max`、`Σπ 偏差`、**专家路由直方图**
（最敏感的一项：稠密对照是 4 个专家各 3451 次，稀疏是 topK=1）。

### 4.2 回归**当场抓到一个真 bug**：构造之后赋值 = 静默空操作

第一版 `sacazx::withSacazAgent` 是"先 `new`，再 `sac.moeDense = true`"。而**建网发生在
构造函数里** ⇒ 赋值是静默空操作：`dense-tb` 实际跑的是**稀疏**（topK=1 / 3305 次前向），
而报告里那一行照样印"稠密"（拆分前是 topK=4 / 13804 次）。

这正是本工程已经栽过一次的坑（`sacazagent.h` 里 TanhNorm 那一段："开关写成了普通成员,
赋值发生在构造函数建网**之后** ⇒ 静默空操作"）。修法：`moeDense` 改成**构造参数**
（`denseMoe_`），并在头文件里把这条约束写死。

> 这条比"回归通过"更值钱：**如果只跑测试不跑指纹，这个 bug 会以"dense-tb 跑起来没报错"的
> 样子留在仓库里**，而它的读数会被当成"稀疏 vs 稠密的对照"。

### 4.3 测试与全量构建

* `test_sacaz`：**385 项断言, 0 项失败**（含 `[10]` 四变体扫描 / `[12]` TB 专项 /
  `[14]` 与还原版同权重同局面 **max|Δπ| = 0 / max|ΔQ| = 0** / `[17]` 共享骨干与头数口径）。
* 全量构建：**339/339 目标链接成功，0 编译错误**（`cmake --build ... -- -k 0`）。
* `ctest`：**13/14 通过**；唯一的失败是 `test_match` 的 **Timeout（不是断言失败）**，
  而且**不是本轮造成的** —— 改动前的 ctest 记录里就是同一条
  （`.r1build/ctest_after.log`：`Test #6: test_match ***Timeout 900.32 sec`, 93% passed）。
  单独跑实测 **314 项断言 0 失败、1608 s**（Release/AVX2 本机）⇒ 这是**预算过期**。
  已把该测试的 ctest `TIMEOUT` 从 900 放宽到 2700（留 ~1.7x 余量），并在 CMake 里写明
  依据（改动前日志 + 本次实测），不是"为了变绿而调表"。
* `test_match` 的两处**接口列举**补上了新 agent 类型（`AGENT_SACAZ_MOE_MLP`）：
  显示名与损失上报（`[2.6]` 那一组）+ 自检/权重状态（`getAgentSelfCheck` /
  `getAgentWeightStatus`）—— 这是"下拉框里选得到它"的**接口层证据**，不用开 GUI。
  加完之后：**318 项断言、0 失败**（原 314 项，多出来的 4 条正是新类型的），
  而且它**真的在跑**：`SAC+AZ-MoE-MLP 信号 10 次, 全部有限=1, 局数=1, 手数=10`
  —— 走 `ChessBoard::matchAgents` 打完一局、并且上报了 10 次有限的训练损失。
* 修完预算之后 `ctest -R '^test_match$'`：**100% passed，1559 s**（在 2700 s 预算内）。


## 5. 新的奖励方法在三支上的验证（用户口径）

`rewardShape=3`（按局面评估动态分配"吃子 / 杀将"权重）在拆分前就已经落地，而两个新类是
**逐字副本** ⇒ 代码上三支都有。但"代码里有" ≠ "跑得对"，所以：

* `[15b]` 的断言体抽成模板 `posRewardChecks<A>()`，**对三个类各跑一遍**
  （纯 MLP / MoE+MLP / MoE+TB），断言一字不改。
* 实测：三遍的读数**逐项相同** —— 满盘吃马 `0.044000`（默认口径 `0.029000`）、
  不变量 `吃光对方 0.525 < 终局 1.000`、残局将局 `±1.3333`、`m_mate + m_mat ≡ 2.5` 等。
* 断言总数 307 → **385**（多出来的正是那两遍重复实例化）。

### 5.1 顺带把"`done` 样本 = 0 ⇒ `mateBoost` 无效"这条发现在**新类上重验**了一遍

`rewardShape=3` 的杀将那一半只作用在 `terminalReward()` 上，而它进不进得了学习，
取决于训练里有没有 `done=true` 且分胜负的样本（见
[`sacmoetb_pos_reward_2026_09.md`](sacmoetb_pos_reward_2026_09.md) §10）。拆分之后
**这条结论要在新类上重新成立**才算数，所以重跑了两组权重哈希对照：

**（a）TB 那一支（`SACAZMoETbAgent`）** —— `bench_sacmoetb_train`（该工具现在建的就是新类），
2 局自对弈 × 120 手 × `--learn-every=1`，训练完存盘比 SHA256：

| 臂 | `mateBoost` | `matBoost` | actorhead 哈希 | trunk 哈希 |
|---|---|---|---|---|
| mb0 | 0 | 0.5 | `548B058BC189652F…` | `4BAD973F9E162AE8…` |
| mb10 | **10** | 0.5 | **`548B058BC189652F…`（相同）** | **`4BAD973F9E162AE8…`（相同）** |
| mat0（阳性对照） | 0.5 | **0** | `78846B23CF3D32E0…`（**不同**） | `60696CDF0E41BE1D…`（**不同**） |

终局通道读数（工具新打的那一行）：三个臂都是
`done 样本=0 (0.0000%) 其中分胜负=0 (0.0000%)`。

⇒ **把终局倍率从 0 开到 10，权重逐字节相同；而把材质倍率从 0 开到 0.5，权重立刻不同。**
这就是"杀将那一半在训练里是死的、吃子那一半是活的"在新类上的复现。

**（b）MLP 专家那一支（`SACAZMoEMlpAgent`）** —— 为它给 `bench_sacaz_vs_ab` 补了四个奖励
旋钮（`--reward-shape` / `--pos-score-mode` / `--pos-mat-boost` / `--pos-mate-boost`），
`--backbone=moe-mlp --warmup-games=2 --save=…`（AB level=1 锚点）：

| 臂 | actorhead 哈希 |
|---|---|
| mateBoost 0 | `F5AA3011DEE493E4…` |
| mateBoost **10** | **`F5AA3011DEE493E4…`（相同）** |
| matBoost 0（阳性对照） | `4848A2498D7314C7…`（**不同**） |

⇒ 同一现象、同一结论，**两支独立类都成立**。

> **一个额外的收获**：TB 那一支这次存下来的哈希与**拆分之前**那一轮（`SACAZAgent` +
> `Backbone::SparseMoeTb`）跑出来的哈希**逐字节相同**（`548B058B…` / `4BAD973F…`）。
> 也就是说"拆分只是搬家"这条，除了 §4.1 的推理期指纹，**训练侧也有逐字节证据**。


⇒ "新的奖励方法也应用到 MoE+MLP 专家"这句话现在是**跑出来的**，不是看出来的。

## 6. 顺带回答：MLP 专家用**独立骨干**（`TrunkMode::Separate`）会不会更好？

用户问句："mlp专家使用独立骨干会不会更好？"
这里的"独立骨干"= `Separate`（五张网各背一整套骨干）对 `Shared`（一份骨干 + 三个头）。

**实测（各 60 局自对弈训练 + 16 局 vs AB L1，同种子）**：

| 口径 | 唯一参数量 | 训练 60 局 | ms/步 (16 模拟) | vs AB L1 | 得分率 |
|---|---|---|---|---|---|
| **Shared**（共享骨干+三头） | **2,898,032** | **370 s** | **59.9** | 0 胜 / 12 和 / 4 负 | **37.5%** |
| Separate（独立骨干 x5） | 7,182,680 | 993 s | 300.1 | 0 胜 / 11 和 / 5 负 | 34.4% |

**结论（按证据强度分层）**：

1. **代价：Shared 完胜，而且这不是统计问题** —— 参数少 **2.48x**、每步快 **5.0x**、
   同样 60 局训练快 **2.7x**（`learnBatch` 与叶子前向都要把骨干算三遍 → 一份）。
2. **棋力：这一次测量里 Shared 高 3.1 个百分点（37.5% vs 34.4%），但 16 局分辨不了**
   （本库自己量过：32 局/锚点的区间宽到 ±8%）。**没有任何证据支持"独立骨干更强"**。
3. **机制上也不该更强**：`test_sacaz [17B]` 已经实测过 —— 把独立口径的三张网的骨干设成
   同一份权重之后，`π / Q / V` 与共享口径**逐位相同**。也就是说共享**不改变**给定权重下
   的函数，它改变的是**梯度流**（一份骨干同时吃策略 + 双 Q 三份信号、只更新一次）。
   这条在 TB 专家上已经量过（共享 + 头数修好后，等时间预算下模拟次数 8 → 55，
   对 MCTS 得分率 +9.4 个百分点、**显著**）——MLP 专家这边同理，只是绝对量级不同。
4. **所以真正的"更好"不是"独立"，而是"同样的时间预算下能跑几次模拟"**：
   上表是按"每步固定 16 次模拟"比的；换成**等时间**（界面 175 ms/步），Shared 那一支能跑
   的次数是 Separate 的 ~5 倍 —— 而这个变量在 TB 上已经被证明是**唯一**测得出棋力提升的旋钮。

### 6.1 这一节的诚实边界

1. **16 局/锚点 + 单种子 ⇒ 不是棋力结论**（要 80 局配对起）。
2. **没有跑等时间口径**（`--budget=175`）：上表低估了 Shared 的优势，因为"同样的墙钟能跑
   更多模拟"这件事被固定模拟数掩盖了。
3. **只测了 moe-mlp 这一支**；TB 支的共享/独立对照见
   [`dev_sacmoetb_strength_2026_09.md`](dev_sacmoetb_strength_2026_09.md) §5.2（等时间配对实测）。
4. **训练量都是 60 局**，两支都没有训练到"棋力可分辨"的量级（本库的既有结论）。

## 7. 这次拆分的代价（写在明处）

* **四份实现**：`SACAZAgent` / `SACAZMoEMlpAgent` / `SACAZMoETbAgent` / `SACAZLegacyAgent`
  各持一份 ~3000 行的 SAC+AZ+MCTS 实现（合计 ~1.3 万行，其中绝大部分是逐字重复）。
  用户口径要的就是这个（隔离必须是结构性的），但**加一条新读数要改四处** ——
  工具侧的那类改动被收敛到 `test/sacaz_variants.h` 一处，agent 内部的不行。
* **`TrunkMode` / `Transition` 等嵌套类型也各有一份**（类型互不兼容）⇒ 工具里不能用
  `SACAZAgent::TrunkMode` 去配 `SACAZMoETbAgent`（编译期就挡下来了，这是好事，
  但写工具时要记得）；`AnySac` 的 `visit()` 就是为这件事准备的逃生口。
* **"默认路径逐位不变"这条硬约定**在拆分里靠 §4.1 的指纹回归守住（四个骨干逐行相同）。

## 8. 用户报障复核："对 MCTS 胜率似乎大减，AGENT_SACAZ 似乎比 AGENT_SACAZ_MOE_MLP 高"

三条**先查事实、再下结论**的结果：

### 8.1 界面里**没有**在用新的奖励方法

`rewardShape` / `mateScoreMode` / `matRewardBoost` / `mateRewardBoost` 四个旋钮在
**整个 `src/` 里一次赋值都没有**（只有两处注释提到 `rewardShape=2` 的历史）。
默认值就是 `rewardShape = 0` = 旧口径（材质 ×0.1 + 每步代价 + 终局 ±1）。

⇒ **"胜率变化"不可能是新的动态奖励造成的 —— 那个开关在界面里根本没打开。**
新的动态分配目前只能从 bench 命令行开
（`--reward-shape=3 --pos-mat-boost=.. --pos-mate-boost=..`）；界面要不要加开关是另一件事。

### 8.2 界面里所有 SAC agent 都是**随机初始化**权重

`weights/` 下只有 `_temp_*` 草稿文件；
`weights/sacaz_agent_*` / `weights/sacaz_shared_agent_*` / `weights/sacaz_moe_mlp_shared_agent_*`
**都不存在**。所以界面上的"胜率"是**两个随机权重网络**的对比 ——
本仓库自己的口径是"随机权重下这个数字没有棋力含义"（工具报告里也照打这一句）。

### 8.3 预算差 6.4 倍是**界面常量如此**，不是缺陷

| 界面类型 | 决策模拟次数 | 一次模拟的代价 |
|---|---|---|
| `AGENT_SACAZ`（纯 MLP） | **`SACAZ_SIMS = 256`** | ~0.07 ms |
| `AGENT_SACAZ_MOE`（TB 专家） | `SACAZ_MOE_SIMS = 40` | ~5.4 ms |
| `AGENT_SACAZ_MOE_MLP`（MLP 专家） | `SACAZ_MOE_MLP_SIMS = 40` | ~2.9 ms |

### 8.4 受控实测（vs MCTS 400 迭代/步；固定 `--seed` 与 `--mcts-srand`；80 手上限）

工具：`bench_sac_mcts_min`（本轮为它补了 `--trunk`，否则复现不了界面的共享口径）。

| 臂 | 配置 | 比分（胜/负/和） | 得分率 | 95% Wilson |
|---|---|---|---|---|
| **A** | mlp + 独立骨干 + **256** 模拟 **= 界面 `AGENT_SACAZ`** | 8 / 2 / 30 | **57.5%** | [42.2, 71.5] |
| **B** | moe-mlp + 共享骨干 + **40** 模拟 **= 界面 `AGENT_SACAZ_MOE_MLP`** | 4 / 3 / 33 | **51.2%** | [36.3, 65.9] |
| **C** | mlp + 独立骨干 + 40 模拟（**等模拟数对照**） | 5 / 1 / 34 | 55.0% | [39.8, 69.3] |
| **D** | moe-mlp + 共享骨干 + 256 模拟（**反向对照**，16 局） | 4 / 2 / 10 | 56.2% | [33.2, 76.9] |

**读法**：A 比 B 高 6.3 个百分点，但**四个区间全部跨过 50%**（40 局 ⇒ 半宽约 ±15 点），
一条也分辨不了。而两个对照臂把原因摊开了：把 MLP 降到 40 模拟（C）只剩 55.0%；
把 MoE 抬到 256 模拟（D）回到 56.2% —— **差距跟着"模拟数"走，不跟着骨干走**。
这与本仓库既有实测一致（唯一测得出强度提升的旋钮是每步模拟次数：4/40/120 次
对 MCTS 是 37.5% / 42.2% / 62.5%）。

⇒ 用户看到的"`AGENT_SACAZ` 比 `AGENT_SACAZ_MOE_MLP` 高"是**界面预算 256 vs 40**
的必然结果（外加随机权重与局数太少），**不是新类或新奖励的缺陷**。

### 8.5 "胜率大减"的另一半：拆分有没有改 `AGENT_SACAZ` 的行为？—— 逐行证据说"没有"

把拆分前的二进制在 worktree（`9706e82`）里重新构建，与当前代码跑**同一条命令**逐行比：

| 骨干 | `--trunk=separate` | `--trunk=shared` |
|---|---|---|
| `mlp` | **逐行相同** | **逐行相同** |
| `moe-mlp` | **逐行相同** | **逐行相同** |
| `tb` | **逐行相同** | **逐行相同** |

`mlp + separate` 正是界面 `AGENT_SACAZ` 的配置 —— **这一条是上一轮遗漏的**
（上一轮只跑了工具的默认 `--trunk=shared`），本轮补上，6/6 全同。
另外 `createSACAZAgent(AGENT_SACAZ)` 的构造参数拆分前后逐字相同（老代码的 backbone
默认就是 `Mlp`、trunkMode 默认就是 `Separate`），代码路径也没动。

### 8.6 想把这件事变成结论，需要什么

1. **先训练权重再比**：没有训练过的权重，任何胜率都不是棋力（见 §8.2）。
2. **配对 + 足够局数**：固定开局集与随机流、80 局以上配对（本仓库既有判据：32 局/锚点
   的区间宽到 ±8%）。`bench_sacmoetb_train`（两锚点）/ `bench_sacaz_vs_ab`（AB 锚点）
   都是为此准备的，且**逐行可复现**。
3. **要比就得先说清预算**：`AGENT_SACAZ` 是 256 次模拟，MoE 两支是 40 次 ——
   不说明这一点，比较的是"预算"而不是"模型"。

## 9. 两组对照实验：MLP 专家的"共享 vs 独立主干"与"新 vs 旧奖励"

用户口径：**保留旧奖励**（默认口径不动），在 mlp 专家上把两件事量清楚；
并且指出锚点选择的要害 —— "**先使用 MCTS agent 对弈，才有可能在与 AB agent 对弈有胜率**"。

### 9.1 协议（2×2 因子 + 双锚点，先训练再评测）

```
四臂 = {共享主干, 独立主干} × {旧奖励(rewardShape=0), 新奖励(rewardShape=3)}
每臂: 先 60 局自对弈热身 (16 模拟/步) → 再评测
      评测 A: vs AB level=1, 80 局, 16 模拟/步
      评测 B: vs MCTS 400 迭代/步, 60 局, 120 模拟/步
口径: --learn-from-search=0 (对局中不再学) + 固定 --seed 与 --mcts-srand
      (同一开局集、同一对手随机流 ⇒ 可以配对)
工具: bench_sacaz_vs_ab (AB 锚点) / bench_sac_mcts_min (MCTS 锚点, 本轮为它补了
      --trunk 与 --learn-from-search) ; 权重由 --save 落盘后由 MCTS 那一支 --load 复用
```

### 9.2 结果

**锚点 A = AB level=1（80 局/臂）**

| 臂 | 主干 | 奖励 | 比分 (SAC胜/负/和) | 得分率 |
|---|---|---|---|---|
| sh_old | 共享 | 旧 | **0** / 23 / 57 | 35.6% |
| sh_new | 共享 | 新 | **0** / 21 / 59 | 36.9% |
| sep_old | 独立 | 旧 | **0** / 28 / 52 | 32.5% |
| sep_new | 独立 | 新 | **0** / 25 / 55 | 34.4% |

**锚点 B = MCTS 400 迭代/步（60 局/臂，同一批训练权重）**

| 臂 | 主干 | 奖励 | 比分 (SAC胜/负/和) | 得分率 |
|---|---|---|---|---|
| sh_old | 共享 | 旧 | **6** / 10 / 44 | 46.7% |
| sh_new | 共享 | 新 | **0** / 7 / 53 | 44.2% |
| sep_old | 独立 | 旧 | **4** / 11 / 45 | 44.2% |
| sep_new | 独立 | 新 | **9** / 8 / 43 | **50.8%** |

### 9.3 三条结论（按证据强度）

1. **用户对锚点的判断被实测证实**：AB level=1 上**四臂全是 0 胜**（得分率只能在
   "输多输少"之间动），而 MCTS 锚点上出现 0~9 胜 ⇒ **只有 MCTS（或更强的尺子）
   才量得出"胜率"**。所以练棋与量棋都应优先用 MCTS 当对手/基准。
2. **"哪个更优"两组都**没有**一致答案 —— 而且是"同锚点内翻号 + 跨锚点翻号"**：
   * **奖励**：共享主干上旧奖励更好（46.7% vs 44.2%；对"赢棋数"做配对 McNemar，
     只有旧奖励赢的 6 局 / 只有新奖励赢的 0 局，**p = 0.031**），
     独立主干上新奖励更好（50.8% vs 44.2%；9 / 4，p = 0.267）；
     AB 锚点上**方向又反了一次**（新奖励 +1.3 / +1.9 点，且配对材料差 +0.55 / −0.47 翻号）。
   * **主干**：旧奖励下共享更好（46.7% vs 44.2%），新奖励下独立更好（50.8% vs 44.2%）——
     McNemar 上两组都不显著（p = 0.754 / 0.267）。
   ⇒ 这是**交互项 + 噪声**的典型样子，与上一册"两个锚点给出相反排序 ⇒ 这一轮没有更优配置"
   完全同型。**任何"哪支更优"的单句结论在本轮数据上都站不住。**
3. **代价上共享主干是明确的**（这条不需要棋力显著性）：参数量 2.90 M vs 7.18 M（2.48x），
   60 局热身的墙钟 370 s vs 993 s（2.7x），一次模拟 ~0.08 ms（独立主干实测明显更贵）。
   ⇒ **在没有棋力证据之前，按代价选共享主干**。

### 9.4 一条必须更正的旧结论：`done` 样本不是"结构性为 0"

上一册 §10 写过"训练里终局通道是空的 ⇒ `mateBoost` 无效"。**那个结论是协议特定的，
本轮把它更正**：

| 协议 | 样本 | done（分胜负） | `mateBoost` 0 vs 10 的权重 |
|---|---|---|---|
| TB 类, 4 模拟/步, 120 手上限, 12 局 | 11296 | **0 (0.0000%)** | **逐字节相同**（当时那一轮） |
| TB 类, 16 模拟/步, 80 手上限, 12 局 | 7040 | 2 (0.0284%) | — |
| MoE-MLP, 16 模拟/步, 80 手上限, 60 局（本轮） | 37504 | **53 (0.1413%)** | **不同**（`221FB956…` vs `D419EF76…`） |

⇒ 正确说法是：**终局样本极其稀疏（0 ~ 0.14%），其数量取决于协议（每步模拟数 / 手数上限 /
骨干），可以恰好为 0 —— 一旦非 0，`mateBoost` 就真的会改变权重**。
所以"后期重杀将"仍然不是一条有效的路（信号量级在万分之一），但"它在训练里完全不存在"
这句话是错的，本轮已按上表更正。
（AB 锚点的 `--learn-from-search=0` 也让这件事可归因：不热身直接打 80 局时
`TrainDiag.n == 0`，说明评测阶段确实没再学。）

### 9.5 三条建议的落地

| 建议 | 状态 | 证据 |
|---|---|---|
| ① 用配对训练+评测流程给出可复现结论 | ✅ | §9.1 的协议（固定开局集/随机流 + 训练后评测 + 每局逐行可复现）；本轮四臂 × 双锚点全部按它跑 |
| ② 界面加显式奖励方法开关（默认关 = 旧奖励）+ "先训练 N 局再对弈"入口 | ✅ | `ChessBoard::setDynamicRewardEnabled`（四个旋钮是普通成员 ⇒ 对现有实例当场生效；三个构造点 + 后台 clone 都按当前值写一遍）+ `mainwindow` 的"动态奖励"复选框（`matchModeRow`，工具提示里写明三条边界）+"每轮训练局数"微调框（接 `setBackgroundTrainRound`）。`chess.exe` 构建通过 |
| ③ 上调 `SACAZ_MOE_MLP_SIMS` 并实测每步墙钟 | ✅ | 该支**几乎不吃模拟预算**：一次模拟 ~0.083 ms（共享主干），每步大头是那次 `learnBatch`（~47 ms）。实测 40/64/96/128/256 模拟 ⇒ 50.1/52.8/55.5/58.0/**67.8** ms/步（界面口径）。已把常数从 40 提到 **256**（与 `AGENT_SACAZ` 同档），仍在界面 175 ms 预算内 |

### 9.6 后续（2026-09）：人机对弈的终局通道是一个真的洞，已修

用户问"人机对弈里 agent 能不能从中学习"时核对出来：**人把 AI 将死的那一手，学习器
收不到 −1**（SAC+AZ 只在"自己那一手结束对局"时才写终局；人机里终结一局的那一手是
人走的，而三处 `emit sendResult` 原来只更新界面）。修法、三条设计细节、以及三层实测
证据（`test_sacaz [18]` / `test_match [2.21]` / `probe_hvai_flow [D]` 端到端真实点击）
见 `docs/sacmoetb_pos_reward_2026_09.md` **§11**。

与 §9.4 那条更正的关系：§9.4 说的是"自对弈里终局样本极稀疏"，而**人机对弈这条路
现在必然交付终局样本** —— 也就是说 `mateBoost` 在自对弈里仍然近乎无事可做，
但在人机对弈里从此有样本可作用。两者不矛盾，是两个不同的训练协议。
