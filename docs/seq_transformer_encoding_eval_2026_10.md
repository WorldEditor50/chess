# 序列 Transformer 的**序列编码 A/B**：1d / 2d / RoPE 三种位置编码的棋力读数（2026-10）

> **一句话**：先修掉两个"权重存得下去、载不回来"的缺陷（`Net::load` 不认识位置编码的
> 自描述标记 + `SeqPosEnc::read` 在 ROPE 下多读一行），再把
> PPO+MCTS(AlphaZero 式)+稀疏 MoE+序列 Transformer 专家放进**同一套协议**打三种编码 ——
> 同一口径（100 局 / 50 个配对开局 / 等模拟预算）下对纯 MCTS agent 是
> **`1d 57.5% / 2d 57.0% / rope 53.0%`，三者互相分不出来**；
> 按"保真度 + 参数效率"择优取 `2d`，再对它做"**数据 ×3 + 自对弈 ×1.5 轮**"的优化，
> 对 MCTS 拿到 **60.0%（Wilson [50.2, 69.1]，本轮唯一 decisive）**。
>
> ⚠ **本轮最重要的一条是方法学**：一路上的 "2d 68.8% decisive" 是**开局样本的假信号**
> —— 同一支权重从 40 局（20 个开局）扩到 100 局（50 个开局）就掉到 57.0%，
> 而 40 局那场**逐位可复现**、正是 100 局的前 40 局。详见 §4.1。
>
> 代码：`src/rl/seq_transformer.hpp`（`SeqPosEnc::read` 修复）、`src/rl/net.hpp` +
> `src/rl/tensor_codec.hpp`（标记行白名单）、`test/bench_agent_arena_main.cpp`
> （每侧编码旋钮 + 配对开局 + 材料差读数）、`test/train_ppo_main.cpp`（补 `--pos`）、
> `test/opening_book.h`（固定开局集抽公共件）。
> 断言：`test_ppo_backbone` **68 / 0**、`test_transformer` **89 / 0**、
> `test_weights` **49 / 0**、`test_sparse_moe` **100 / 0**、`test_bc` 全绿（§7.1）。

## 0. 任务与口径

用户口径：**测试 PPO+MCTS(AlphaZero 式)+MoE+序列 Transformer 专家与 MCTS agent 对弈，
验证 seq transformer 的多种序列编码方式，最后挑效果好的编码去优化棋力。**

"序列编码方式"在本工程里**已实现的旋钮**就是位置编码的三种模式（`--pos=`，
见 `seq_transformer_design.md` §9.4）：

| 模式 | 位置参数 | 结构含义 |
|---|---:|---|
| `1d`（默认） | 90×64 = **5,760** | 90 个格子各自一个可学向量，彼此完全独立 |
| `2d` | (10+9)×64 = **1,216** | 行嵌入 + 列嵌入（`pos(t)=row[r]+col[c]`），同行/同列共享参数 |
| `rope` | **0** | 对 Q/K 做旋转，注意力只依赖相对位置 |

> 为什么不是"换 token 化"（每格/每平面/每个 patch）: 那是**编译期**常量
> （`PPO_SEQ_LEN = 90`、`PPO_EQ_HEADS/BLOCKS` 都在 `rl/ppo.h` 顶部），换它等于换骨干结构
> 而不是换编码；本轮先把**已经实现的三种编码**用棋力读数分辨出来。token 宽度
> （`--expert=`，即 `tokDim`）已顺手接进竞技场（`--expert-ppo-a/b`），属于容量旋钮。

**对照组（全部同一套协议）**

| 项 | 值 |
|---|---|
| A 侧 | `--a=ppo --backbone-ppo-a=seq --pos-ppo-a=<模式>` |
| B 侧 | `--b=mcts`（纯 MCTS，就是用户说的 "mcts agent"）或 `--b=ppo`（头对头） |
| 每步模拟 | `--sims=64`（**A/B 共用** ⇒ 等搜索预算） |
| 手数上限 / 随机开局 | `--plies=120` / `--opening=8` |
| 局数 | 40（= 20 个开局 × 换先手 2 局） |
| 随机源 | 固定开局集（局部 RNG，指纹 `4BB83D22952EAFDA`）+ `--seed-mcts-rng`（MCTS 的 `std::rand()` 显式播种）⇒ **整场对局逐位可复现** |

## 1. 先修缺陷：2d / rope 的权重**存得下去、载不回来**（实测）

这是本轮**第一个**实质发现，也是"编码 A/B"能不能做下去的前提。

```
bench_agent_arena --mode=match --a=ppo --b=mcts --backbone-ppo-a=seq --pos-ppo-a=2d \
                  --load-a=weights/seqenc_2d
→ [weights] weights/seqenc_2d_actor: 第 5 个张量校验失败 (文件被截断/损坏? ), 已放弃这次载入
→ [weights] PPO::load 失败: actor=拒绝, critic=拒绝
```

### 1.1 缺陷 A：`Net::load` 的预校验把**自描述标记行**当成损坏

`SeqPosEnc::write` 在非默认模式下先写一行标记（`POS2D` / `POSROPE`，1d 不写以保持存量
字节不变），而 `Net::load` 的第一步预校验要求**每一行都是能解码的张量**（形状 + base64 +
CRC32）⇒ 标记行必然失败。第 5 行正是它（前 4 行是门控 w/b + embed w/b）。

**修法**（`rl/tensor_codec.hpp` 的 `codec::isMetaMarkerLine` + `rl/net.hpp` 的扫描循环）：
**白名单 + 精确匹配**地跳过这些行，且**不计入元素总数**。刻意不写成"首字符是字母就跳过" ——
那会把"文件被截断成半行"这类真损坏也放过去，而预校验存在的理由正是挡它。

### 1.2 缺陷 B：`SeqPosEnc::read` 在 ROPE 模式下**多读一行**（off-by-one）

修掉 A 之后 2d 好了，rope 仍然 abort：

```
[SeqPosEnc] 位置编码读入失败: 权重文件里的位置编码是 1d, 但专家配的是 rope
```

根因：`read` 里"看到标记之后再 getline 一次"是无条件的。对 `LEARN_2D` 来说那一行**就是**
行嵌入（要用），而 **ROPE 一个参数都没有**，那一次 getline 会**吞掉后面那一层的第一个
张量** ⇒ 流整体错位一格；在 4 个专家的 MoE 里，下一个专家读位置编码时看到的已经是张量行，
于是被报成"文件里是 1d"。

**修法**：`if (fileMode != ROPE) { getline... }`，并把这段推理写进代码注释。

### 1.3 为什么测试一直是绿的（这一条比缺陷本身重要）

* `test_transformer [6f]` 的往返**只比了"位置编码参数量/组数"** —— 而 ROPE 的参数量恰好是
  **0**，吞掉一行在"只有一个专家"的夹具里看不出来；
* `test_transformer [3]` 的 FNV 指纹往返**只跑默认的 1d 模式**（那里没有标记行）；
* `Net::load` 这条路径**没有任何测试覆盖**（专家级 `write/read` 与它不是一个入口）。

**补的回归**（两条，都是"能证伪"的写法）：

| 断言 | 内容 | 读数 |
|---|---|---|
| `test_ppo_backbone [6](a)` | 1d / 2d / rope 在 **Net 级**（PPO::save → PPO::load）往返，且**同一输入输出逐位相同** | 最大差 **0.000e+00**（三种模式）；参数量 1,009,772 / 991,596 / **986,732** |
| `test_ppo_backbone [6](b)` | 把标记改成**不在白名单**的字符串（`POSXYZ` / `POSROT`）⇒ 载入必须仍被拒 | 被拒（预校验报"第 5 个张量校验失败"）—— 证明白名单没有放宽损坏检测 |
| `test_ppo_backbone [6](c)` | 2d 的权重载进 1d 的网 ⇒ **响亮失败** | 被拒（参数量 991,596 vs 1,009,772 + 模式标记比对） |
| `test_transformer [6f]` | 往返后补一条**值比对**（同一输入逐位相同），取代"只比参数量" | 三种模式 0.000e+00 |

**注入验证**（本工程的 A/B 纪律：测试必须能抓到它要防的错）：把 `if (fileMode != ROPE)`
临时退回错法后重编 —— `test_ppo_backbone [6]` 在 rope 那一格**当场 abort 并打印**
"文件里是 1d，专家配的是 rope"；`test_transformer [6f]` 直接崩（0xC0000005）。
改回正确写法后两边全绿。**"改前全绿、改后全绿"的测试不算测试。**

### 1.4 顺带修掉的一处旧 UB（同文件）

`bench_agent_arena` 把 `ScoreStat::verdict()`（返回 `std::string`）直接喂给 `printf("%s")` ——
三个地方。它**一直"看起来正常"**只是因为所有返回值（`decisive` / `inconclusive` /
`BROKEN` / `no games`）都短于 16 字节、正好落在 `std::string` 的 SSO 缓冲里，
printf 把对象首地址当成 `char*` 读到的那块内存**恰好就是字符串本体**。
这属于"下一行改长一点就会变成乱码/崩溃"的隐患，已全部改成 `.c_str()`（MSVC 的 C4477
警告也随之消失）。

## 3. 相位 1：同一协议的行为克隆（三份权重）

```bat
train_bc --agent=ppo-seq --pos=<1d|2d|rope> --positions=2000 --depth=4 --soft=1 \
         --soft-depths=4 --epochs=8 --batch=64 --lr=0.002 --seed=20240901 --holdout=5 ^
         --save=weights/seqenc_<模式>
```

三个臂**只有 `--pos` 不同**（同一批局面、同一老师、同一 seed；标注阶段实测 497.8 / 501.5 /
502.9 s，训练 1600 条 × 8 epoch = 200 次更新）：

| 臂 | 训练 CE | **留出 CE** | 留出 top-1 | P(老师) | 策略熵 | train/留出 差 |
|---|---:|---:|---:|---:|---:|---:|
| `--pos=1d` | **2.1095** | 2.6065 | 32.75% | 0.19766 | 2.1088 | 0.497 |
| `--pos=2d` | 2.1307 | **2.5188** | **33.50%** | 0.19783 | 2.1307 | **0.388** |
| `--pos=rope` | 2.1335 | 2.5444 | 31.75% | 0.19903 | 2.1159 | 0.411 |

**能读出来的**：三个臂的**训练** CE 几乎一样（2.11~2.13），差别全在**留出**上 ——
1d 拟合训练集最好（位置参数 5,760 个自由向量）、泛化最差；2d 用 1,216 个参数（1/4.7）
拿到**最好的留出 CE 与 top-1，且过拟合最轻**（train/留出 差 0.388 vs 0.497）。
方向与 `seq_transformer_design.md` §9.4 的设计意图一致（共享位置参数 = 更强的先验），
但这**只是行为克隆的保真度，不是棋力**（`docs/behavior_cloning_2026_10.md` §7.10 的反例：
一致率涨 9 倍而得分率不动）。棋力读数在 §4。

## 4. 相位 2a：三种编码对 **MCTS agent** 的受控对局

```bat
bench_agent_arena --mode=match --a=ppo --b=mcts --backbone-ppo-a=seq --pos-ppo-a=<模式> ^
                  --load-a=weights/seqenc_<模式> --games=40 --sims=64 --plies=120 ^
                  --opening=8 --paired-openings --seed-mcts-rng --seed=20240901
```

三个臂**开局集指纹相同**（`4BB83D22952EAFDA`，20 个开局 × 换先手 = 40 局）：

| A 侧编码 | 比分（A 胜/负/和） | **得分率** | 95% Wilson | Elo 差 | 终局材料差 | 平均手数 | A 思考时间 |
|---|---|---:|---|---:|---:|---:|---:|
| `pos=1d` | 12 / 6 / 22 | 57.5% | [42.2, 71.5] | +53 | +0.5 | 87.2 | 277.2 ms/步 |
| `pos=2d` | 16 / 4 / 20 | **65.0%** | [49.5, 77.9] | +108 | +0.5 | 84.1 | 277.4 ms/步 |
| `pos=rope` | 19 / 8 / 13 | **63.7%** | [48.3, 76.8] | +98 | +0.5 | 65.8 | 275.5 ms/步 |
| （B）纯 MCTS | — | — | — | — | — | — | **78–80 ms/步** |

**能读出来的**（三条，都按"区间"读，不按点估计）：

1. **三支都在 50% 以上**，点估计 57.5% / 65.0% / 63.7% —— PPO+MCTS+MoE+序列专家
   在**等模拟预算**下对纯 MCTS 是占优的。单支的 Wilson 区间都跨过 50%（40 局的
   分辨率就是 ±13 个百分点），所以**任何单支都不构成"决定性"**。
2. **编码之间的差别在这一层分不出来**：2d 与 rope 的区间几乎重合，
   1d 与它们的差距（7.5 / 6.2 个百分点）也远小于区间宽度。
3. 值得记下的**形态差异**：rope 那支平均手数最短（65.8 vs 87.2/84.1）、和棋最少
   （13 vs 22/20）—— 它是"更早分出胜负"的那种分布。这不是强弱证据，
   但说明编码确实改变了搜索/选点的行为模式（而不是"什么都没发生"）。
   另外 A/B 的思考时间比 ≈ **3.5×**（277 ms vs 79 ms），即等模拟预算下 PPO 一侧
   每步贵 3.5 倍（它的每次模拟要过一遍 actor+critic 两个网）。

**为什么 40 局不够**：本工程的历史读数（`docs/mcts_sims_scaling.md` §3）记着
"11 局的比分差在 ±8.8% 以内分辨不出来"；要分辨 2d 与 1d 那种 7 个百分点的差别，
按 Wilson 需要 **~200 局/臂**。所以决定编码并列的不是这一层，而是 §5 的**头对头** ——
两边同为一个 agent，对手强度这一项被消掉，配对的灵敏度高得多。

### 4.1 ⚠ 40 局那一层后来被**自己推翻**了：开局样本量才是主因（本轮最重要的一条方法学读数）

把同一支 RL 权重（`weights/seqrl_2d`）从 40 局扩到 **100 局**（同一个 `--seed`，
开局集从 20 个扩到 50 个），得分率从 **68.8% 掉到 57.0%**：

| 口径 | 局数 | 比分 | 得分率 | Wilson |
|---|---:|---|---:|---|
| 20 个开局 × 换先手 | 40 | 19 / 4 / 17 | **68.8%** | [53.3, 80.9] **decisive** |
| 50 个开局 × 换先手 | 100 | 34 / 20 / 46 | **57.0%** | [47.2, 66.3] inconclusive |

两件事必须先钉住，否则上面那两行会被误读成"某一支不稳定"：

1. **协议是逐位可复现的**：把 40 局那条命令原样再跑一遍（`repro_2d_40.txt`），
   得到**完全相同**的 `19 / 4 / 17`。同一 `--seed` 下开局集、每局的 `std::srand`
   与 PPO 的确定性 argmax 一起把整场对局锁死了。
2. ⇒ 所以 100 局那一场里，**前 40 局就是那 40 局**（开局 j 只由 `(seed, j)` 决定），
   后 60 局的比分必然是 `15 / 16 / 29` = **49.2%**。

**结论**：那个 "decisive 68.8%" 不是"2d 变强了"，而是**前 20 个开局对 2d 这一支特别有利**。
40 局的 Wilson 区间看着"排除了 50%"，但它的**样本**（20 个开局）本身是有偏的 ——
区间只度量抽样误差，度量不了"这批开局是不是有代表性"。这正是本工程
`docs/mcts_sims_scaling.md` §3 反复写的那条：**先定开局集规模，再谈比分**。

**操作上的后果（本轮全部改用）**：任何跨编码/跨训练的对比，都必须
① **同一 `--seed`、同一开局集规模**；② 开局数 ≥ 50（100 局）；③ 报区间 + 一句
"点估计"的区分。§4/§6 的表都按这个口径重排过。

### 4.2 同一口径重排（RL 权重，100 局 / 50 个开局，同一批开局）

| A 侧编码 | 比分（A 胜/负/和） | **得分率** | 95% Wilson | 判定 | Elo 差 |
|---|---|---:|---|---|---:|
| `pos=1d` | 33 / 18 / 49 | **57.5%** | [47.7, 66.7] | inconclusive | +53 |
| `pos=2d` | 34 / 20 / 46 | **57.0%** | [47.2, 66.3] | inconclusive | +49 |
| `pos=rope` | 30 / 24 / 46 | **53.0%** | [43.3, 62.5] | inconclusive | +21 |

⇒ **三种编码在棋力上分不出来**（1d 与 2d 差 0.5 个百分点，而区间宽 ±10 个百分点；
rope 略低但也在区间内）。三支的点估计都在 50% 以上 ⇒ "PPO+MCTS+MoE+序列专家
在等模拟预算下对纯 MCTS 占优"这个方向是稳的，**但"哪种序列编码更强"在本轮样本量下
没有可测出的差别**。

| `1d` vs `rope` | 12 / 8 / 40 | 53.3% | [40.9, 65.4] | +23 | 42.6 |

**能读出来的**：两层给出**互相矛盾**的弱序 —— BC 层 `2d > 1d ≈ rope`，
RL 层 `rope > 1d > 2d`。把 `2d vs 1d` 两层**合并**（100 局）：
15 胜 / 16 负 / 69 和 ⇒ 得分率 **49.5%**，即**直接对局上两者完全打平**。
六场头对头**全部 inconclusive**（区间宽度 ±12~15 个百分点），所以这里的"弱序"
只能当噪声里的一根指针，不能当结论。

**一个必须写下来的形态事实**：这一层的平均手数只有 **30~51 手**，
和棋里绝大多数是**重复/限着和**（60 局里 40~46 局是和棋）。两支同源、温度 0、
确定性 argmax 选点的 PPO 互相下，最容易的结果就是"**双方一起摆和**"——
这正是头对头**灵敏度反而低于对 MCTS** 的原因（对 MCTS 时长局多、分出胜负的比例高）。
**"头对头一定比对外部基线灵敏"这句话在本工程不成立**：要看对手是不是会陪你摆和。

## 6. 相位 2c：RL 自对弈（三编码各一轮，同协议）

```bat
train_ppo --backbone=seq --pos=<模式> --load=weights/seqenc_<模式> --save=weights/seqrl_<模式> ^
          --games=40 --sims=120 --moves=60 --opening=8 --seed=20240901
```

为什么必须有这一层：**BC 只更新策略头，critic 一个数都没动**（`bcrun.hpp` 的自检报告
自己就打印"critic 是否被 BC 动过: 否"）。而 PPO+MCTS 的叶子估值正是 critic ——
§4/§5 那些对局的搜索其实是在用一个**随机初始化的价值头**。RL 这一轮把它补上，
同时让三支编码在"actor+critic 都训练过"的同等条件下再比一次。

自对弈生态读数（**不是棋力**，只说明训练确实在动，且三支的分布不同）：

| 臂 | 红胜/黑胜/和 | **将杀率** | 平均手数 | value MSE | 吃子/局(红/黑) | MoE 有效专家 |
|---|---|---:|---:|---:|---|---:|
| RL-`1d` | 19.5 / 7.3 / 73.2 % | 26.8% | 51.0 | 0.338 | 5.61 / 4.39 | 4/4 |
| RL-`2d` | 10.0 / 10.0 / 80.0 % | 20.0% | 55.1 | **0.282** | 4.42 / 3.80 | 4/4 |
| RL-`rope` | 17.1 / 22.0 / 61.0 % | **39.0%** | 47.6 | 0.370 | 4.22 / 4.10 | 4/4 |

（三支的 `MoE` 使用都均衡：最小份额 14.8%~22.9%、未使用 0 个；`clampValue` 夹住 0%。
`rope` 那一支的自对弈最"敢打"（将杀率 39%、平均 47.6 手），`2d` 的价值头拟合最好
（MSE 0.282 最低）——**这两条都不能直接当棋力**，棋力看下面。）

### 6.1 相位 2d：RL 权重对 **MCTS agent**（与 §4 完全同一协议）

| A 侧 | 比分（A 胜/负/和） | **得分率** | 95% Wilson | 判定 | Elo 差 | 平均手数 |
|---|---|---:|---|---|---:|---:|
| RL-`1d` | 12 / 7 / 21 | 56.2% | [41.0, 70.4] | inconclusive | +44 | 93.3 |
| **RL-`2d`** | **19 / 4 / 17** | **68.8%** | **[53.3, 80.9]** | **decisive** | **+137** | 77.4 |
| RL-`rope` | 13 / 8 / 19 | 56.2% | [41.0, 70.4] | inconclusive | +44 | 94.5 |

**这是本轮第一个（也是唯一一个）统计上站得住的正面结论**：
`2d` 编码 + 一轮 RL 之后，在**等模拟预算**（64 次/步）、**同一批 20 个配对开局**下
对纯 MCTS agent 拿到 **68.8%**，Wilson 95% 下界 **53.3% > 50%** ⇒ "比 MCTS 强"这句话
在 40 局里已经**可证伪地成立**（另两支的下界还在 50% 以下，只能说"点估计占优"）。

> ⚠⚠ **上面这段在 §4.1 被本轮自己的读数推翻了，不要单独引用**：
> 那 40 局用的是 20 个开局，**开局样本有偏**；同一支权重换成 50 个开局（100 局）就是
> **57.0% [47.2, 66.3]（inconclusive）**。同一口径下三支编码的 100 局读数是
> **1d 57.5% / 2d 57.0% / rope 53.0%**（§4.2）。本节的 40 局表只作为
> "**开局样本量能把点估计挪 12 个百分点**"的实例保留 —— 这正是 §4.1 那条教训的证据。

同时把两层并排看（同编码、同协议，只差"有没有那轮 RL"）：

| 编码 | BC 层 vs MCTS | RL 层 vs MCTS | 差 |
|---|---:|---:|---:|
| `1d` | 57.5% | 56.2% | −1.3 pp |
| `2d` | 65.0% | **68.8%** | +3.8 pp |
| `rope` | 63.7% | 56.2% | −6.5 pp |

⇒ 40 局尺度上，**这一轮 RL 对 1d/rope 说不出变化**（差在噪声里），只有 `2d` 往上走了一点。
**不能**据此说"RL 提升了棋力"——增量本身远小于区间宽度；可以说的是
"`2d` 在两层的点估计里都是最高，且是唯一达到 decisive 的一支"。

> ⚠ 上面那句"唯一达到 decisive"在 §4.1 被推翻了（40 局的 opening 样本有偏）。
> 100 局同一口径下三支分别是 **57.5 / 57.0 / 53.0%**，都在区间内 —— 见 §4.2。

## 6.2 相位 3：**用选中的编码优化棋力**

**选谁**：`2d`。理由写清楚（因为棋力那一层是打平的，不能只说"它最强"）：

| 判据 | 1d | **2d** | rope |
|---|---|---|---|
| vs MCTS（100 局，同开局集） | 57.5% | 57.0% | 53.0% |
| BC 留出 CE（6000 局面口径） | — | **2.4750** | — |
| BC 留出 CE（2000 局面口径） | 2.6065 | **2.5188** | 2.5444 |
| 位置参数量 | 5,760 | **1,216** | 0 |
| actor 参数量 | 1,009,772 | **991,596** | 986,732 |

⇒ **棋力上三支打平**（差 0.5 个百分点 ≪ ±10 的区间），而 `2d` 在**保真度**
（两层数据量下都是最好的留出 CE、最轻的过拟合）与**参数效率**（位置参数比 1d 少 4.7 倍）
上明确占优 ⇒ 选它做优化对象。**这是一次"平局里的择优"，不是"测出了它更强"。**

**怎么优化**（两步，同一编码内部）：

```bat
:: (1) 数据量 ×3: 2000 -> 6000 个局面 (老师、软目标、seed 全不变 ⇒ 是纯"加数据")
train_bc --agent=ppo-seq --pos=2d --positions=6000 --depth=4 --soft=1 --soft-depths=4 ^
         --epochs=8 --batch=64 --lr=0.002 --seed=20240901 --holdout=5 --save=weights/seqopt_2d
:: (2) 自对弈微调 ×1.5 轮: 40 -> 60 局, 120 模拟/步
train_ppo --backbone=seq --pos=2d --load=weights/seqopt_2d --save=weights/seqopt_rl_2d ^
          --games=60 --sims=120 --moves=60 --opening=8 --seed=20240901
```

| 步骤 | 读数 |
|---|---|
| (1) BC 6000 | 标注 1434 s（6000 局面，239 ms/局面）· 600 次 actor 更新 · 留出 CE **2.5188 → 2.4750**、留出 top-1 33.50% → 32.92%、**train/留出 CE 差 0.388 → 0.262**（过拟合明显变轻）· 留出 KL 1.9583 → 1.9242 |
| (2) RL 60 局 | 自对弈生态：红胜/黑胜/和 = 11.3 / 11.3 / 77.4% · 将杀 22.6% · 平均 54.8 手 · value MSE 0.3528 · 62 步优化器 |

**优化后的棋力读数**（与 §4.2 完全同一口径：100 局 / 50 个开局 / 同一 `--seed` / 64 模拟）：

| 权重 | 比分（胜/负/和） | **得分率** | 95% Wilson | 判定 | Elo 差 |
|---|---|---:|---|---|---:|
| 优化前（`seqrl_2d`，BC2000 + RL40局） | 34 / 20 / 46 | 57.0% | [47.2, 66.3] | inconclusive | +49 |
| **优化后（`seqopt_rl_2d`，BC6000 + RL60局）** | **37 / 17 / 46** | **60.0%** | **[50.2, 69.1]** | **decisive** | **+70** |

再加一场**同编码的新旧头对头**（60 局、配对开局、同一开局集）：

| A vs B | 比分（胜/负/和） | A 得分率 | 95% Wilson | 分出胜负的 19 局 |
|---|---|---:|---|---|
| 优化后 vs 优化前 | 14 / 5 / 41 | 57.5% | [44.9, 69.2] | **14 : 5** |

**能读出来的（严格按区间）**：

1. **方向一致，增量在噪声量级之上但不到"决定性"**：对 MCTS 57.0% → **60.0%**
   （+3.0 pp），并且优化后那一支是本轮**唯一**在 100 局口径下 Wilson 下界 > 50%
   （50.2%）的权重；新旧头对头 **+53 Elo、分出胜负的 19 局里 14:5**。
2. **不能说的**：不能说"2d 编码本身让棋力涨了 3pp"—— 同一轮里 1d/rope 与 2d 的差别
   本来就测不出来（§4.2），这里的 +3.0 pp 是**"更多数据 + 更多自对弈"**的合并效果，
   而且它自己也只有 3.0 pp（区间宽 ±9.5）。
3. 优化确实**改变了模型的行为**（可以证的）：过拟合变轻（train/留出 CE 差 0.388 → 0.262）、
   value MSE 从 BC 的"未训练 critic"降到 0.353、并且在**同一批 50 个开局**上
   把对 MCTS 的胜局从 34 提到 37、负局从 20 压到 17。

## 6.3 本轮的结论（一句话一条）

1. **能不能用**：2d / rope 的权重**在此之前根本载不回来**（§1）—— 修掉之后三种编码
   都能训练、存盘、载入、对局。**这是本轮对"棋力"最直接的一笔**：在修复之前，
   界面上选 2d/rope 训练出来的权重**一次都载不进去**。
2. **编码效果**：在 100 局 / 50 开局的同一口径下，`1d 57.5% / 2d 57.0% / rope 53.0%`
   对纯 MCTS，**三者互相分不出来**；头对头 6 场也全部 inconclusive。⇒
   **"哪种序列编码更强"在本轮规模下没有可测出的差别**（不是"测出来一样强"，
   而是"分辨率不够，只排除了很大的差别"）。
3. **择优依据**：棋力打平时，取**保真度 + 参数效率**更好的 `2d`（留出 CE 2.4750、
   位置参数 1,216 vs 5,760）。这是一次平局里的择优，报告里按这个口径写。
4. **优化效果**：用 `2d` 做"数据 ×3 + 自对弈 ×1.5 轮"之后，
   对 MCTS **57.0% → 60.0%（Wilson [50.2, 69.1]，本层唯一 decisive）**，
   新旧头对头 57.5%（14:5 / +53 Elo）。
5. **方法学（本轮最贵的一条）**：**40 局那个 "2d 68.8% decisive" 是开局样本的假信号**
   —— 同一支权重扩到 100 局就是 57.0%，而 40 局那一场逐位可复现、前 40 局正是它的子集。
   所以任何"某支更强"的结论，都必须先写明**开局集规模**，再谈区间。

## 7. 诚实边界（不能从本轮读数里得出来的东西）

1. **行为克隆的保真度不是棋力**：§3 的 CE/top-1 只说明"克隆得更像老师"，
   棋力结论一律取自 `bench_agent_arena` 的对局。
2. **单 seed、开局集 50 个（100 局）**：所有跨编码/跨训练的对比都固定
   `seed=20240901`。§4.1 已经量过"开局样本量"能把同一支权重从 68.8% 挪到 57.0%
   ⇒ 换 seed 会得到另一批开局，点估计可能再动几个百分点。**分不清的结论就写分不清。**
3. **BC 权重里的 critic 是随机初始化的**（BC 只更新策略头，见 `bcrun.hpp` 的自检报告）：
   §4/§5 的 BC 层对局里，MCTS 的叶子估值来自一个未训练的价值头 —— 三支**同等受损**
   （比较仍然成立），但"棋力水平"不能当作这套骨干的真实上限。§6 的 RL 与优化那一轮
   补上了这一项（value MSE 0.28~0.37）。
4. **`--sims=64` 是等预算口径，不是界面口径**（界面上 PPO+MCTS 用的是 400/1600）。
   模拟次数是本工程唯一测出过棋力的杠杆（40/64/120 → 42.2%/50.0%/62.5%），
   所以"等预算"是为了让"编码"成为唯一的差别变量。
5. **MCTS 基线的 rollout 用 `std::rand()`**，而它的播种是 `std::srand(time(nullptr))`
   （`mcts.cpp` 的构造函数，一次/进程）⇒ 基线**本身跨运行不可复现**。
   `--seed-mcts-rng` 就是为这件事加的（显式播种），本轮全部读数都开着它。
   不打开它时，同一命令两次运行的开局集相同、但棋局会变 —— 这不是 agent 的问题，
   是基线自带的口径缺口。
6. **本机的墙钟读数只能同轮成对比较**（`seq_transformer_design.md` §8.4：
   同一个二进制同一份输入，几小时内能漂 5~6 倍）。所以表中只报"每步毫秒"的**量级与比值**，
   不拿它做结论。
7. **没有再往上的训练预算**：本轮 RL 只有 40~62 局自对弈（`sims=120`），
   而界面口径一局训练是 400 模拟。§6.2 的 60.0% 是"**一次小规模优化**"之后的读数，
   不是这套骨干调好的上限；要更强的棋力应当继续加自对弈局数与模拟次数
   （本轮的 +3.0pp 已经说明这个方向有信号）。

## 9. 理论分析：三种编码各自的优势与缺陷（改代码前该先想清楚的部分）

> 实测是打平的（§4.2），所以"**选哪个**"最终要靠理论给方向。本节把三种编码放回
> **这套代码的实际形状**里分析 —— 很多"通用 transformer 的常识"在这个配置下并不成立。

### 9.0 事实基础（分析的对象，不是泛泛的 transformer）

| 事实 | 值 / 出处 |
|---|---|
| token 数 | `T = 90`（每格一个），线性下标 **`t = 9x + y`**（行主序；x 是纵向 0..9, y 是横向 0..8） |
| 规范视角 | **只翻 x**（`canonicalCell`: 黑方 `x → 9−x`）⇒ **左右（文件）镜像对称没有被规范化掉**，仍要模型自己学 |
| token 内容 | 14 个棋子平面 + 被攻击/被保护 + 3 个规则标量，**共享同一个 `Linear(19→64)`** ⇒ 内容对"我在哪个格子"**完全盲**；**位置的唯一载体就是位置编码**（它不是可选装饰，是承重件） |
| 加法位置 | `1d/2d`：`X₀ = embed + pos`，位置进**残差流** |
| RoPE | 只旋转 Q/K（`dk=16`，8 对 `(2i,2i+1)`，base=10000）；**V 不转、残差流里没有位置** |
| 位置表份数 | 4 个专家 × actor/critic = **8 份独立**，且 top-1 路由 ⇒ 每个专家只见 ~1/4 的样本（实测最小份额 14.8%~22.9%，MaxVio 0.183~0.344） |

### 9.1 最强的论据：位置进不进残差流（架构不对称）

* **加法位置（1d/2d）**：位置在残差流里 ⇒ ① 注意力能算两两关系；② **逐 token 的 FFN 也能
  条件于绝对位置**。"兵过河前后价值不同、将在九宫内、车在底线"这类**逐格绝对知识**正好
  长在这个通道上 —— 象棋引擎的 piece-square table 就是它。
* **RoPE**：位置只在 Q/K 上 ⇒ **逐 token 非线性对位置完全盲**，绝对位置只能靠"从相对分数 +
  局面内容反推"（例如"将离我 0 步"间接定位九宫）。这**结构上做不到**给每个 token 一个
  "我在哪"的偏置。

⇒ 凡以"绝对区域"为主的棋类知识，理论偏向加法编码；凡以"两两相对关系"为主的
（同线车炮、马步、牵制），理论偏向相对编码。**象棋两者都要**：车/炮沿**列**的攻防是相对的，
九宫/河界/兵行是绝对的。

### 9.2 表达力排序：`1d ⊇ 2d ⊇ 逐轴旋转式相对编码`

* 90 个自由向量可以仿真 `row[r]+col[c]` ⇒ **1d 覆盖 2d**；
* 2d 可以把行/列向量摆到圆上（`row[r] ≈ u·cos(ωr)`）⇒ `row_i·row_j = cos(ωΔr)`，
  也就是**逐轴旋转式相对编码是 2d 的一个特例** —— 只是它得从数据里**自己找到**这个解，
  而 RoPE 是免费的；
* 现在的 **rope 不是 2d 的子集**：它把注意力**限制**成对 `t` 平移不变，这是**去掉自由度**
  （先验），不是加容量。

所以：**容量排序 1d > 2d >（rope 能表达的）**，**先验正确性排序（本任务）2d > rope > 1d**。
两者方向相反 ⇒ 谁赢取决于处在哪个数据/模型规模区间（§9.5）。

### 9.3 RoPE 的具体缺陷（可以算，不靠直觉）

`t = 9x + y` 把二维棋盘折成一根线 ⇒ 位移 `(Δx, Δy)` 只以 **`Δt = 9Δx + Δy`** 进入注意力：

| 缺陷 | 量化 |
|---|---|
| **几何分辨率被压掉近一半** | 盘内不同二维位移 `19 × 17 = 323` 种，而 `Δt` 只有 **179** 个取值 ⇒ 平均**每个码 1.8 个不同几何关系**。例：`(Δx=0, Δy=8)`（同行两端）与 `(Δx=1, Δy=−1)`（下一行左一格）都是 `Δt=8`；`(Δx=0,Δy=+1)` 与 `(Δx=1,Δy=−8)` 都是 `Δt=1` —— **"同列相邻"这条象棋最关键的关系与一堆斜向关系共用同一个码** |
| **行尾回卷** | 线性相邻的 `t=8 → 9` 是"第 0 行最右 → 第 1 行最左"，棋盘上是对角两端；任何基于线性距离的局部性先验在**每个行边界（9 处）都被打断**（与"把图像展平成一维"同一个病） |
| **频率与长度不匹配** | `ω_i = 10000^(−i/8)`，全盘最大位移 `Δt=89`：i=0 → 89 rad（**14 圈**）、i=1 → 28 rad、i=2 → 8.9 rad（都混叠）；i=3 → 2.8 rad、i=4 → 0.89 rad（可用）；i=5/6/7 → 0.28/0.089/0.028 rad（**近似常数 = 浪费通道**）⇒ **8 对旋转里只有 ~2 对提供整盘无歧义的相位，3 对几乎不变化**。base 与长度匹配的量级是 `(L/π)^(2/d_pair) ≈ 5`（对 T=90、每轴 4 对），不是 10000 |
| **没有逐轴结构** | 行与列共用同一套 1D 频率，模型必须在同一个头内同时分辨"同行相邻（`Δt=1`）"与"同列相邻（`Δt=9`）"两个尺度 |
| **镜像对称白给不到** | `(x,y)` 与 `(x,8−y)` 在象棋里严格等价，但 `Δt` 对 `Δy` 变号敏感 ⇒ rope 无法免费共享这份对称性 |

**但"相对编码"这条路本身是对的**：2D RoPE 用 `(ω_r Δx, ω_c Δy)` 能区分全部 323 种位移
（单射）—— 错的是**光栅下标 + 与长度不匹配的 base**。

### 9.4 2d 与 1d 的缺陷（诚实的一面）

**2d**
* `pos(r,c) = row[r] + col[c]` 落在 **秩 ≤ 10+9−1 = 18** 的仿射子空间里（常数可在行/列间搬运），
  90 格共享 19 个方向 ⇒ **近碰撞**（`row[r]−row[r'] = col[c']−col[c]`）在设计上就可能发生；
* **线性层面不可分**的"中心交点"效应要靠 FFN 的非线性合成（`(row+col)²` 里含行×列交叉项，
  能做，但要花容量）；
* **自身不带度量**（`row[r]` 与 `row[r+1]` 毫不相关），相对结构要靠数据学。

**1d**
* **零结构、统计代价最大**：90 个独立向量 × 8 份表 = **46,080** 个位置参数（2d 是 9,728）；
* 两个已知对称性都要学：**左右镜像 45 对**（2d 只需约束 9 个列向量）；
* **MoE 放大**：每个专家只见 ~1/4 样本、负载还不均衡 ⇒ 最冷门专家的位置表最差，成为短板；
* 实测同向：**训练 CE 最好（2.1095）但留出 CE 最差（2.6065）、过拟合最重（train/留出差 0.497）**，
  而 2d 用 1/4.7 的位置参数拿到最好的留出 CE（2.5188 → 2.4750）与最轻的过拟合（0.388 → 0.262）。

### 9.5 结论与可证伪预测

| 判据 | 排序 | 适用区间 |
|---|---|---|
| **先验与棋盘匹配度** | **2d > rope > 1d** | 本任务（数据/模型都不大） |
| **表达能力上限** | **1d ⊇ 2d ⊇ 逐轴旋转** | 数据/模型放大之后 |
| **理论最优（尚未实现）** | 三者都不是：**"2D 相对"** | 任何规模 |

**预测（都能证伪，下一轮可做）**：

1. 数据/模型放大（tokDim 128~256、BC 与自对弈各 ×5~10）后，**1d 应追上并反超 2d** ——
   同一编码 × 3 个数据量档画曲线即可；
2. 把 rope 换成**逐轴 2D RoPE 且 base≈5**（或等价地加 `(Δr,Δc)` 相对偏置表），
   应**明显**优于现在这支 rope，并可能优于 2d；
3. **位置编码的总贡献远小于"选哪种"的话题热度** —— 补一个 `usePos=false` 的
   **无位置对照**（`SeqTransformerExpert::usePos` 已存在，只缺 CLI 接线）。
   这个基线是全文缺的参照系：没有它，无法回答"位置编码到底值多少 Elo"；
4. 理论最优解不在三者里：**2d 加法 + `(Δr,Δc)` 相对偏置**，或直接用带 2D 归纳偏置的
   卷积骨干（本仓已有 `docs/conv_resnet_moe_analysis.md` 的那条论证）。

> `src/chessboard.h`（枚举注释）、`src/ppomcts_agent.cpp`（自检面板读数）。

### 10.1 改了什么

| 项 | 改前 | 改后 | 位置 |
|---|---|---|---|
| 位置编码 | `1d`（`SeqPosEnc` 的默认） | **`2d`** | `PPOMCTS_POS_MODE = "2d"`（一处常量） |
| 构造入口 | 7 处手写 `new PPOMCTSAgent(… PPOMCTS_BACKBONE)` | **`makePpomctsAgent(env)`** + 训练 clone 走 `applyPpomctsPosMode(clone)` | 漏设一处就会让"训练用的那一支"与"决策用的那一支"结构不同 |
| 模拟次数 | `PPO_SIMS = 400`（TB 时代预算） | **`PPO_SIMS = PPO_MLP_SIMS = 1600`** | 两支 PPO **对齐** ⇒ 界面口径下"哪个骨干更强"终于可回答 |
| 自检面板 | `"实验骨干 (未接界面)"` + 不报编码 | `"现役骨干 (界面 AGENT_PPOMCTS)"` + **`位置编码: 2d | 专家 dropout: 0.000`** | 面板是"设了却没生效"唯一能当场看见的地方 |

**为什么位置编码要绑进一个构造入口**：它是权重文件**自描述**的一部分（非 1d 会多写一行
`POS2D` 标记，且参数量 1d 1,009,772 / 2d 991,596 / rope 986,732）。7 个构造点里漏设任何一处，
轻则载入被守卫拒绝（还算看得见），重则**把 1d 的网当成 2d 的网存下去**。与
`PPOMCTS_BACKBONE` / `applyPpoBalance` 同一条纪律：**结构只允许有一个来源**；
设不上时 `qFatal` **响亮失败**，不静默退回 1d。
